# Agent Content

编写、重构或只读评价给 Agent 读取的文档：项目指令、Skill 正文、角色说明和参考资料。只读评价保持目标文件不变。

内容必须来自用户材料、项目事实和已确认决定，不编造项目政策，保留硬安全边界与许可归属。目标不是字数更短，而是让执行者在真实脆弱点上改变默认动作。

## 上下文指针

上下文指针是在已读内容中指向未读资料、并写清命中条件的文字（Skill description、项目指令入口、正文 reference 链接）。

把有区分度的动作或分支放前面，同时说明目标是什么、何时读：
- 差：“需要时参考资料。”（没有选择依据）
- 好：“核对历史数据时读取兼容规则，按数据版本选择字段映射。”（给出分支和用途）

同一种条件的多个同义说法合并为一种，不把目标正文已有背景重复塞进入口。必要资料被漏读时，先修指针的条件和位置；仍不可靠时，再前置最小必需信息。

## 两种负担与跳数控制

- **Context load**：常驻上下文和每次必读内容。常驻入口命中率再低也持续消耗注意力，须比正文更精炼。
- **Cognitive load**：人需要记住哪些入口存在、何时选用的负担。保留有价值的人工判断与授权，移除只有记忆和导航成本的选择。

同时区分**串行跳转深度**与**按需单跳隔离**：
- **同分支必读、高共现或相对入口无实质增量的短规则**拆成独立文件，只会增加二次读取和漏读风险，应合并共置或直接并入入口；**正交、低共现的条件分支**（如按需展开的单条原则或场景）即使篇幅较短也保持单文件隔离，避免合并后命中一条就加载全部无关规则造成上下文污染。
- 长索引表（如原则表、分支表）尽量自带**0 跳可执行判据**——读者扫表就能改变初步判断，深层步骤、反例或脚本再按单跳条件披露。
- 常见路径需要串联 4–5 跳以上才能拿到核心动作时，说明层级过碎，应合并或前置。

## 信息层级与共置

先区分**步骤**（有序动作）与**参考**（判断用的定义、规则、事实）。同层完整规则可以直接平铺，不必套成流程。

| 层级 | 放什么 | 何时读取 |
| --- | --- | --- |
| 文内步骤 | 当前任务的动作与必要先后关系 | 推进主线 |
| 文内参考 | 当前任务紧邻查阅的定义、规则与例外 | 同一任务内 |
| 条件披露的参考 | 仅部分分支需要的深层细节 | 命中指针后 |

- **渐进披露**：按真实分支拆分，不按篇幅平均切分；所有路径都需要的共同方法放主文。在步骤流里塞入无关分支参考，会把主线步骤埋掉，让模型是否执行主线退化成抛硬币。
- **共置**：同一概念的定义、规则和例外放在一起。重复的合并，散落的聚合。
- **规则上提**：多个分支/Playbook 共享的底线、权限、停止或位置规则，只在唯一入口写一次，不在每个分支重复粘贴。
- **警惕稀释（Sprawl）**：即使每一行都有效且不重复，单文档过长仍会稀释注意力；把仅属部分分支的细节沿层级下沉到指针之后。

## 具体机制与完成标准

写清**可观察信号 → 改变默认行为的具体动作**，并用**清晰度**和**要求强度**两个维度写实完成标准：
- **清晰度（Clarity）**：让执行者一眼分清“做到”与“没做到”。模糊边界会诱发**提前结束**——上下文里可见的后续步骤会拉着模型草草收尾跳向下一步。防线按顺序用：**先收紧完成判据**；只有判据本质模糊且实测观察到抢跑时，才跨**真实上下文边界**（交接或子代理）拆分序列。
- **要求强度（Demand）**：决定模型肯挖多深（legwork）。“列出变更清单”很清晰但要求很低，随便写两条也算完；“逐一核对每个受影响模型并说明后果”才迫使穷举排查。全参考文档同样需要强度约束（如“逐条核对下方每条规则”），防止模型抽两条应付了事。

| 抽象空话 / 低要求（无效） | 具体机制 / 可检验高要求（有效） |
| --- | --- |
| “已经理解字段需求。” | “每个源字段已映射到目标字段，无法映射的逐项列出原因。” |
| “列出变更清单。” | “逐一核对每个受影响模型，标明字段变化与调用方影响。” |
| “保证性能数字可信。” | “交替跑至少 5 轮报中位数和极差；改动环节仅占总耗时 10% 时，提速超 ~11% 即判定测错。” |
| “安全、兼容、错误恢复、性能与体验不能省略。” | 指出当前任务具体要守哪条不变量、触发什么错误时怎么处理。 |

遵守三条写作纪律：
1. **锋利在判断，不在常识命令**：压缩字数时保留红灯信号、硬检验、阈值和反例，不压成抽象上位词；对模型已熟知的通用工具，锁结果不变量而非死板指定常规命令参数（参数本身是易踩陷阱时除外）。
2. **换项目测试**：一句话把业务名词换掉后，放到任意其他项目都“永远正确”，就大概率没有增量价值——要么具体化，要么整句删掉。
3. **一句一个判断**：不把 6–8 个抽象名词塞进一句法条式长句迫使读者解码。

## 引导词与正向表达

**引导词**是借用模型预训练里已有强先验的紧凑概念（如“回归”“基线”“幂等”“红灯”）：少付定义成本，同时锚定**正文执行**与**跨 prompt/文档/代码的指针触发**。少造新词和晦涩缩写；重构时把多处反复展开的同类短语折叠成单个锚定词（如把“快速、确定、低开销”收敛为“紧凑”，把“能真实复现缺陷的校验”收敛为“红灯”）。弱引导词（如“仔细”“认真”）打不过模型默认基线，本身就是 No-op，应换成更强锚点或具体要求强度。

**正向表达**：写出被禁止的行为会先在上下文激活该行为，而否定词在注意力里权重偏弱（“别想大象”），禁令常反过来把注意力拉向错误动作。因此优先直接说期望动作（“只汇总已提供记录”）；硬安全边界无法正向表达时保留明确禁止项，但紧贴可行替代，让注意力落到该做什么，不为了肯定句式削弱权限和约束。

## 剪枝

- **单一事实源**：同一含义只维护一处完整定义，其余位置留指针。
- **环境事实**：命令参数、配置和目录优先从真实文件或 `--help` 读取；只缓存查询昂贵、难到达或执行前必须避开的陷阱。
- **按真实用途保留输出格式**：用户要手动复制的 JSON、程序 parser 读取的字段或跨上下文交接材料，都算真实消费者；仅为同一会话自说自话制造的协议字段应删除。
- **防沉淀与三类明确 No-op**：文档天然会因“加规则安全、删规则怕出事”而积累过时**沉淀（Sediment）**。No-op 判定是**相对当前模型基线**而非读者主观口味——争论一句规则是否多余，靠实跑对照决断而非纸面辩论；确认是 No-op 就**整句删掉**，不缩成更短的废话。以下三类直接删除或重写：
  1. **通用职业常识**：如“编写清晰可读的代码”“仔细思考边界条件”。
  2. **多概念平铺清单**：一口气罗列 5 个以上正确但无对应动作的好词。
  3. **防卫性免责尾句与卸力退路**：在每个子文件或规则后反复粘贴“不自动授权 / 局部通过不替代整体 / 仅作线索不强制”。系统级底线只在权威位置写一次；例外条件写成**具体可判别的跳过条件**，避免尾句直接卸掉前面指令的行为张力。

失效规则和无执行用途的编写过程讨论应删除；用户明确要求保留的设计决策记录按其用途交付。

## 重构已有内容

改造已有文档、去空话、压减多跳链或重组多文件时，读取 重构手法（`references/refactoring-methods.md`），先定位具体病灶再选用对应手法，并完成保真核对。

## 核对修改

用 1 条代表性常见任务和 1 条独立分支走完新文本，确认指针能到达目标，原有主体、条件、单位、顺序、权限与例外没有因改写丢失。静态走读只说明材料和路径判断，行为收益需实际运行验证。

只读评价需要固定人读版式时，采用 内容评价模板（`assets/content-review-template.md`）的适用部分。
