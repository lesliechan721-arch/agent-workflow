# Skill 设计、行为抓手与验证

新建、实质重写、移植外部方法，或评审一个 Skill 是否真正有价值时读取。局部改错字或修路径无需走完整设计流程。

## 1. Failure-Mode First：从模型基线脆弱性反推

设计正文前，先从真实素材（先跑一轮实际任务提炼人类纠正，或直接收集 PR 评审意见、事故单、runbook、git 修复记录与失败轨迹）回答两个问题，避免脱离领域上下文凭空生成通用套话：
1. **领域盲区**：有哪些模型单靠常识绝对猜不到的业务事实？（字段含义、工具限制、隔离规则、兼容约束）
2. **默认坏习惯**：如果不给这个 Skill，前沿模型在这个任务上具体会犯哪 **3–5 个高频错误**？（例如：不查版本对着旧构建瞎调、把代码逻辑事后脑补成作者意图、单次跑分就宣称提速、遇分歧就打断用户而不先跑实验、为了凑审查数制造风格 nitpick）

**逐条对账**：Skill 里的每条核心规则，必须能指明它补的是哪条领域盲区，或对抗的是哪个默认失败模式。两条都不沾边的“正确最佳实践”，默认删掉，不写入 Skill。缺少领域事实时保留缺口，不用通用质量提醒填空。每次真实运行中人工纠正了模型的非显然错误，优先直接沉淀进正文前置陷阱（Gotchas）。

## 2. 把脆弱点做成“行为抓手（Forcing Functions）”

告诉模型“注意质量”不会改变行为；把关键脆弱点转化为下面 4 类具体抓手之一（按实际需要选用）：

| 抓手类型 | 做法 | 反例 vs 正例 |
| --- | --- | --- |
| **可观察红灯信号（Tells）** | 把抽象风险写成一眼可识别的症状，直接绑定改道或停止动作（信号停止通常优于固定“最多 N 轮”） | 差：“避免死循环”<br>好：“同一前提连续两次修补失败，立刻停手写下该前提并做反证实验” |
| **硬产物 / 不可糊弄的检验** | 用具体产出或机械校验替代口头宣称 | 差：“先设计再写代码；验证脚本可靠”<br>好：“先写带 `not implemented` 体的类型签名文件；用可撤销负例确认检查真会报红再恢复基线” |
| **显式决策分流器** | 针对模型最易走错的分叉，写死二元判定准则 | 差：“合理决定是否询问用户”<br>好：“凡运行一次实验就能观察出答案的问题，直接验证，不向用户提问” |
| **输出级防幻觉约束** | 对调研/审查类任务，用结构分栏或语言约束拦截脑补和迎合 | 差：“区分事实与推测”<br>好：“直接证据与推断分节，禁用无引用的‘显然/因为’，必须列出未覆盖与未知项” |

非显然陷阱要在执行者遇到前可见（不要等报错后才指去读规则）。有依赖的多步工作可用简短清单防漏，每项对应真实产物而非“已理解”。

### 执行前验证计划与校验闭环

- **验证闭环（Validation loop）**：对存在确定性校验器（脚本或参考核对表）的生成/修改任务，显式要求“执行 → 跑校验 → 按报错修正 → 重验通过后再继续”，不把一次性输出当终点。
- **执行前验证计划（Plan-validate-execute）**：批量写入、破坏性修改或错误会向后传播的动作，先产出可核对的执行计划，对照真实字段、类型或目标清单校验后再执行。预览（打算做什么）、计划校验（动作是否成立）和执行后核对（实际产物）三者不能互相替代；缺少校验工具时明示未核验项。

## 3. 提炼方法与外部移植的“机制保真”

- **提炼而不是复写案例**：保留可推广的判断依据与失败陷阱，不把单次输入的目录名、阶段数或答案固定为通用要求。
- **移植外部方法/规范时保真机制**：以给定规范或上游方法（如团队既有流程、外部成熟 Skill 体系）为基础改编时，除了核对核心概念、关系与例外，**必须逐项盘点原方法中真正改变模型行为的硬机制**（具象算术、红灯信号、硬产物、过滤框架、具体反例）。
- 本地化裁剪只裁**环境/平台耦合**（特定模型名、专有平台工具、外部组织流程），不得以“精简”或“通用化”为名把锋利机制抽象成温吞概括。

## 4. 证据门槛与缺陷类型匹配

设计审查、验证或门禁类 Skill 时，验证标准必须匹配对象形态与缺陷类型，防止“单一极端门禁导致高危问题失明”：
- 能低成本复现的运行时缺陷与行为契约，优先要求实测反例或真实运行证据；
- 设计缺口、架构腐化、需求遗漏、难稳定复现的并发/安全风险，保留调用链与具体维度检查，同时配套**误报过滤准则**（区分真实可达路径与拍脑袋假设、区分真实缺陷与个人风格偏好），防止噪声通胀。

## 5. 表达选择与停止静态打磨

- **载体选择**：共同方法与前置陷阱放正文；条件分支放有明确指针的 reference；固定且确有消费者的输出用模板；重复、精确或脆弱的机械操作沉入脚本。例子必须能消除一个难以用文字说清的歧义，不写基础编程教程。
- **控制强度与讲清因果**：只有唯一安全顺序或错误代价高时固定步骤；多种方法均合理时给默认选择和改道条件，不抛无默认值的选项菜单。对需要临场权衡的弹性规则，写清**为什么**（“做 X，因为否则会触发 Y 失败”）比堆砌 `ALWAYS/NEVER` 硬指令更易泛化。
- **停止纯静态打磨，按轨迹做减法迭代**：静态结构检查与措辞修订只用于收口明显缺口。一旦改稿变成“为假想边界不断叠加免责尾句和防御补丁”，立刻停止纯文本迭代，选 3–5 个易触发模型弱点的代表性任务，在同条件下对比“无 Skill 基线 vs 当前草案”。复盘时**不只看失败样本，也要看通过样本的执行轨迹**——反复试探往往说明指令模糊，跑进无关分支说明多余规则在误导，摇摆不决说明缺少默认路径。若不断加规则但通过率停滞，往往是**过度约束**，应反向尝试删规则做减法验证。结果出错先归因（知识缺失、指针未到达、方法错误、工具接口、用例前提还是评价规则），修对应根因，不为单次失败给全局加规则。
