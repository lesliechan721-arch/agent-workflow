# Skill 中的脚本设计

需要创建、修改随包脚本，或编写正文调用说明时读取。

## 什么逻辑值得下沉脚本

- **适合固化**：执行轨迹反复出现的解析、转换、计算或校验逻辑；参数组合易错或要求精确确定性的操作；能显著减少模型反复试探的机械步骤。
- **留给模型**：语义判断、上下文综合与开放式内容生成（例如不要用几个关键词去判定业务文案是否成功）。已有 CLI 工具只需少量参数时直接以一次性命令调用并**锁定版本**（如 `npx pkg@ver`、`uvx pkg@ver`），在正文或 `compatibility` 声明运行前提，不必强造脚本；命令参数复杂到易写错时再沉入脚本。

## 面向 Agent 的脚本接口

| 关注点 | 接口要求 |
| --- | --- |
| 输入 | 支持参数、stdin 或明确文件；使用封闭枚举拒绝模糊输入而不替模型瞎猜；缺必需输入时返回可操作错误，禁止等待交互提示 |
| 帮助 | `--help` 简明说明用途、参数、典型调用和关键退出码含义，常规使用无需读源码 |
| 输出 | 数据走 stdout，诊断走 stderr；机器消费用 JSON/CSV/TSV 等明确结构，不同失败类型用差异化退出码区分 |
| 报错 | 错误信息指明具体问题、合法值或缺失项，使模型下一次调用就能修正 |
| 大输出 | 提供摘要、分页（如 `--offset`）或文件导出（如 `--output`），防止关键结果被工具输出截断 |
| 重试与副作用 | 尽量幂等以允许安全重试；破坏性或有状态写入按风险提供 `--dry-run` 预览、显式确认参数（如 `--confirm`/`--force`）与恢复路径 |
| 依赖 | 优先标准库零依赖；确需三方库时优先单命令自包含的内联依赖声明（如 Python PEP 723 + `uv run`、Deno/Bun 锁版本导入），在最终交付布局验证，不依赖源码目录偶然环境 |

批量或破坏性写入配合 执行前验证计划与校验闭环（`references/design-and-validation.md#执行前验证计划与校验闭环`）：接口应把拟执行内容与真实字段、类型或目标清单对照并返回具体差异。

## 正文如何接入脚本

在命中分支处写明**脚本相对路径（见 `references/skill-format.md#资源引用`）、调用条件、输入来源与结果用途**，不把完整源码或整段 `--help` 复制进正文。例如：

```markdown
整理用户提供的发票记录时，运行：
`node scripts/merge-invoices.mjs <input-file> --format json`
按结果中的 `totals` 输出分币种汇总；将 `unresolved` 中的记录交回用户确认。
```

正文只补脚本不知道的业务含义与特殊结果处理。若模型频繁读脚本源码才能用对，先修 `--help`、报错或输出结构。

## 验证交付

通过公开入口实跑正常输入与关键错误输入，核对 stdout、stderr、退出码与实际文件副作用；写操作补测重复执行或部分失败，并在交付目录核对依赖可达。语法检查不能代替真实执行。
