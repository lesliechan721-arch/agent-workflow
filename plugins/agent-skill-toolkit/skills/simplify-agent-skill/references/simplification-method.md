# 选择简化候选

先写清本次改变预计减少什么，以及什么行为必须保留，再决定删、合并、迁移或改写。

## 从实际负担找候选

| 发现 | 候选动作 | 需要排除的误判 |
| --- | --- | --- |
| 同一路径重复同一规定 | 保留权威定义，调用处留必要提示 | 不同角色的独立核验可能确有用途 |
| 同一概念需要跨文件拼合 | 共置定义、规则与例外 | 独立分支的资料不必全部内联 |
| help 或配置已经提供完整可变信息 | 改为读取事实源 | 稳定理由、昂贵查询摘要仍可能必要 |
| 未命中分支占据共同路径 | 条件披露并改善指针 | 分出去但无人知道何时读取，会丢失能力 |
| 步骤不影响任务结果 | 删除或放宽，检查对照 | 高影响恢复和领域约定不能凭直觉删除 |
| 简单关系被长段叙述隐藏 | 使用短表、树或流程表达 | 不借改写改变原有顺序、责任和范围 |
| 执行者反复读实现才能使用脚本 | 修 help、诊断或调用处 | 不把源码复制到主文件 |

一族变化可以跨多个文件，例如迁移规则同时更新所有指针。一次改多个无关机制则难以归因；先处理收益明确且风险可核对的变化。

## 保真重组

改写前确定原有决定的条件和强度：必须与建议、并行与顺序、缺值与零、保存与生效等不能合并。关系图标明是包含、调用还是执行次序；采用方法不是自动增加一个执行者。

保留解释非显然决定所需的原因、领域定义和关键例子。模型已经擅长的基础教程可以删除，消除接口歧义的例子可能仍有价值。保留/删除价值有争议时，将它作为对照问题，而非直接断言无用。

多次小改也应检查最终被读取的整体。把内容移到其它文件却仍然每次加载，不能称为降低上下文；把长期必要依据变成不可达私有记忆，更不是简化。

## 衡量收益

选择与问题相符的指标：共同路径和条件路径实际读入、查找跳转、重复工具调用、错误试探、人工介入、任务耗时或维护位置。字符数可以描述体积，不单独说明注意力或质量。

比较相同任务与领域资料；无 Skill 基线移除悬空调用，但不同时移除完成任务所需的来源。若工具变化本就是候选的一部分，单独记录该变化，避免混入额外数据或权限。

单包范围内不能为减少入口擅自改变其它公开能力。发现组合层问题时指出相应范围和证据，不用局部删减掩盖它。
