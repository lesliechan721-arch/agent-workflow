# Skill 调用、触发边界与 Description

设计、重构或评审 description、默认适用范围和调用属性时读取。具体字段写法见 格式参考（`references/skill-format.md`）。

## 选择谁来启动

| 场景 | 调用策略 | 代价与约束 |
| --- | --- | --- |
| 模型应自行识别，或其它 Skill 需要组合调用 | 保持模型可调用，description 写清决定性条件 | 独立发现的价值必须抵得上常驻上下文成本 |
| 只在用户主动选定时机启动（如发布、破坏性批处理、专项宏） | 关闭隐式调用，保留用户显式入口；`description` 改为面向人的一句话用途摘要，删去模型触发分支列表 | 用户需自行记住入口；不能作为模型自动调用的必要下游 |
| 模型需要背景规则，但用户无需手动触发 | 隐藏用户入口，保留模型调用（客户端支持时） | 切勿把隐藏用户入口误配为关闭模型调用 |

关闭隐式调用不等于禁用整个 Skill；各客户端对手动开关和 description 的读入行为以实际环境为准。

## 写清 Description 与高发反模式

区分三件事：Skill **能完成**的任务、**值得模型默认选择**的任务，以及**交给普通执行或其它能力**的任务。按连贯结果、决定性输入、约束和独特方法写清边界，不要靠 `issue`、`fix`、`实现` 这类载体词或动作词圈地。

description 回答三点：**做什么、何时触发、最高价值的 near-miss（何时不用）**，并注意两条实测机理：
- **面向用户意图而非内部实现**：用用户想达成的目标与任务语境触发（覆盖用户未直呼领域专有名词的隐式表述），不要把内部脚本、步骤或实现机制塞进 description；同时靠高价值 near-miss 守住多 Skill 环境的精度边界。
- **简单单步请求常不触发 Skill**：模型用基础工具即可一步做完的普通请求，即使字面匹配 description 也常不会加载 Skill。不要拿这类单步常识题测触发并误判为 description 失效，进而乱堆关键词制造误触发。

重点规避两类触发架构反模式：

1. **大网式宽泛主动 Skill**：如果一个主动 Skill 的 description 几乎覆盖 80%+ 日常同类操作（如“任何写代码/改配置/写测试任务”“任何工程判断”），它会失去区分度——要么常驻加载持续稀释注意力，要么被模型随机跳过。
   - 修正方向：所有常规任务都该遵守的极简常驻纪律，放进项目规则（`AGENTS.md`/Rules）或具体工作流主入口；主动 Skill 聚焦有清晰触发场景和独特高价值方法的任务边界。
2. **高摩擦两跳纯索引主动 Skill**：单独暴露一个宽泛的索引表主动 Skill，要求模型先自行触发它、扫长表、再二次读取极短条目文件——没有上游强调用约束时，命中率极低且工具调用成本不划算。
   - 修正方向：把高频核心判据直接内联到真正消费它的入口（0 跳生效），或把条目本身做成自带 0 跳可执行判据的精炼参考。

## 能力组合中的指针

正文中的“使用 `<skill-name>`”是能力指针：同一上下文已有足够材料直接复用，有必要才补本次范围与目标，不发明统一参数/返回值包装。

如果必需下游只允许用户手动启动，上游不得写“自动调用它”，应改为提示用户显式启动或采用当前可用的替代路径。

## 触发评估的区分

触发测试里，“是否加载”“是否首个入口”“是否作为合法辅助能力”“加载后任务是否做对”是四个独立问题。加载后做错要修执行方法，不要继续往 description 堆关键词。只有 description 静态对照时，结论仅限于设计判断，不代表真实触发召回率。
