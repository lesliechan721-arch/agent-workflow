# Eval 审核标准

源用例审核、正式准入和运行结果解释共享此标准。先判断用例有没有资格评价 Skill，再解释分数；不以通过率倒推标签。

## 用例资格

检查测试层（触发、入口、组合、执行、结果、成本）、被测对象、所需前提、Oracle 依据、允许差异及最小反例。标签必须能从用户目标、Skill 规则和明确 fixture 推出。参与案例设计的上下文只能自检，不能提供独立准入。

用户文字可以表达需求，不能凭一句“执行已完成”“输入已验证”证明机器状态。预期输出只是 Oracle；原始 trace、fixture 和验证凭据才能证明执行条件。输入准入拒绝和有效输入下的错误 Oracle 是两个 case。

加载存在性、首次入口和允许组合必须按实际 observer 区分；不是主入口不代表不能作为下游使用。字段和观测支持来自目标 runner profile，不能把其底层能力假定为外层格式已支持。

## 现实性、覆盖与错误代价

用例应代表现实场景族、真实回归或高影响可达边界。合成样本可以使用，但写明模拟范围；机制探针、challenge 和真实回归不得混成一个发布权重。同义句不算多个独立场景族，关键词命中不等于正确行为。

正负数量近似平衡只服务诊断。分别解释 FN 与 FP 的影响、频率依据和用户政策；未知分布不编精确权重。一个罕见但不可逆的失败可以重要，一个刻意设计且低影响的例子不应绑架正文。

检查决定性边界的 minimal pair。例子“改变任何条件就会不同”不合格；应指出改变哪项条件会使标签或动作翻转。允许多个正确方法，不按输出词汇、内部分阶段或模型是否复述规则评分。

## Fixture 与 grader

- 需要具体文件/状态/命令结果时，fixture 必须真实建立它们；空 workspace 只适合不依赖文件的任务。
- test double 明确标注并拒绝未知操作，只证明其覆盖的编排行为；不能声称真实产品 CLI 或远端已通过。
- 写操作列允许范围和实际产物断言。只读原则通过足够工具权限下不写及调用证据验证；单靠 sandbox 禁止写入无法证明模型主动遵守。
- 能机械检查的结果交给 parser/文件/调用日志；语义判断可人工或模型复核。schema 通过、validator 存在与运行成功是不同事实。
- 正式准入需当前 runner 验证的执行输入；源设计审核不要求它。缺失输入先归因为 fixture/coverage，不诱导 Agent 补造事实。

## 运行解释

保留按 case、场景族、正负类型、旧版/候选、模型与环境划分的结果。分别报告 recall/FN、specificity/FP；不要用原始总通过率隐藏高成本错误。3 次可以初筛，但 1/3 与 2/3 表示证据有限，不等于真实概率固定。9/10 也不自动要求修到 10/10。

比较固定用例和 grader 的旧版/新版，说明样本量与不确定性。增加运行必须获得相应授权；若预算结束则 inconclusive。若测试未执行，只评价设计，不声称稳定效果。

## 失败与修改

先排除 Oracle、fixture、grader、runtime、陈旧输入、方差和预期取舍，再判 skill-defect。修复需支持一个实际场景族，在最近正负边界和固定回归集上验证净收益，并计算增加的上下文/维护成本。

错误 Oracle 先修测试并使旧准入失效，不能拿新 Oracle 证明旧候选无回归。无可复现问题或重要前提不足时提出补证据，不升级为生产 Skill 必改。不存在“每个失败都修复”目标。

## 交付强度

源设计审查：哪些标签/前提成立、具体问题、未验证部分。正式准入：与当前执行输入绑定并经实际运行器验证的准入产物。运行诊断：归因、风险、accept/reject/collect-more-data/fix-eval-first 等建议及依据；这些词是语义结论，不要求新增 JSON。
