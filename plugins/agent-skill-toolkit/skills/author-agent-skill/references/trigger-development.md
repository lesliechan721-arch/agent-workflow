# 触发问题的诊断与修改

用户报告漏触发、误触发，或要求改变显式/自动调用时读取。调用含义使用 `references/skill-invocation.md`，字段使用 `references/skill-format.md`。

## 确定需要改变的结果

读取实际请求、现行 description、metadata、相关 caller 和可取得的加载记录。区分只解释、只诊断和允许修改。记录一个应使用的代表性请求和一个相近但不同的请求；涉及显式调用或下游组合时加入该路径，不固定例子数量。

| 可观察现象 | 先核对 | 最小修改位置 |
| --- | --- | --- |
| 没有出现在本次能力清单 | 已提供的能力清单、解析结果与加载记录 | 先定位可用性问题，不扩大 description |
| 用户要求手动，但模型自行启动 | 客户端调用属性与 caller 强制调用 | 对应 metadata 和 caller |
| 已发现且允许选择，但匹配范围不对 | 真实任务、方法价值、near-miss | description 与必要的适用说明 |
| 已加载但任务做错 | 输入、方法、资料、脚本与完成边界 | 执行方法，不继续加触发词 |
| leaf 已收窄，caller 仍要求全部调用 | 上层条件与用户政策 | caller，保留 leaf 合法使用能力 |

没有记录时，可以给候选归因和静态修正，但不声称误触发已复现。只修改授权目标；源/生成关系明确时修改 source，由调用方重建 final。

## 修改 description 与调用策略

表达连贯结果、决定性输入与约束。例如，“处理所有日志问题”可按真实职责改为“摘要用户已提供的日志，归纳错误与缺失信息；需要登录服务调查时不使用”。这是示例，不将单文件限制施加给其它技能。

不要把全部负例复制进 description，也不因出现 issue、task、fix 就推导必须采用本方法。保留显式选择、有依据的辅助使用和普通处理路径。

按目标调用方式修改字段，并保留无关正文和 metadata。常用开关的位置与语义见格式参考；真实调用效果按目标环境观察。

## 触发实验与候选选择

只解释或静态改写时，不自动运行本分支。实验需要已有预算与运行条件；用运行器实际提供的加载记录判断触发，不能以正文提到技能名称代替加载。首次入口、允许辅助与最终任务质量另行观察。

1. **固定比较条件。** 按真实任务族收集正例与相近反例，将用于修改的训练请求与用于评价、选版的验证请求分开，两边保留关键正负边界。固定划分、标签、观测方法、原版及候选正文、模型、工具和权限。只比较 description 时，其它正文与调用属性保持相同；需要改变它们时另记干预。
2. **重复观察。** 在预算内对同一请求作重复独立运行，记录每次是否实际加载。触发率为加载次数除以具有有效观测的运行次数，同时保留计数，例如 2/3；启动失败、记录缺失和超时分别报告，不当作未触发。需要阈值时在比较前按用户或测试政策确定，不从结果反调阈值；没有依据就报告计数与不确定性。运行次数和划分比例不固定为通用要求。
3. **从训练失败改写。** 分别定位漏触发与误触发的任务族，修正可泛化的适用边界，不把每个失败查询的关键词塞进描述。保留每个候选的准确文字与结果，核对字段合法及无关内容不变。多轮没有收益时先检查标签、可达性与任务价值，不继续机械加长描述。
4. **用验证结果选版。** 按事先确定的错误代价与比较规则查看验证表现，必要时分别报告正负结果及取舍；最后生成的版本不一定最好。不要把验证请求的具体失败交回改写过程继续修词。差异不足以支持选择时保留基线或报告不确定，不为选出赢家追加未授权运行。

用未参与改写和选版的新请求检查最终候选的泛化。验证集已经参与选版，不等于最终未见测试；若又据其具体失败改写，记录其已被使用的事实，不继续声称它提供独立泛化证据。样本比例只是本次观察，不能当作稳定成功概率。

## 交付

给出实际采用或建议的候选文字、选择理由、原版与候选的正负结果、未覆盖场景和已用预算。没有运行条件时交付静态修改及待验证请求。触发改善不证明加载后任务质量，必要的行为检查按原委托继续。
