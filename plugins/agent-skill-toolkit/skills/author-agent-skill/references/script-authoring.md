# Skill 中的脚本

选择或修改随包脚本，以及编写调用说明时使用。

## 什么逻辑值得固化

优先使用已有、适合任务的可靠工具。执行轨迹反复出现相同的解析、转换、计算或校验代码时，可将它做成经过测试的随包脚本。参数组合容易出错、结果必须精确，或复用能够减少反复试探时，也值得固化。

语义判断留给模型，机械处理交给脚本。按明确字段计数可以自动化；判断一段文字是否代表业务成功，不能仅靠几个关键词。一次性简单命令直接使用，不因 Skill 可以包含 scripts 就一定创建它。

## 面向 Agent 的接口

| 关注点 | 接口要求 |
| --- | --- |
| 输入 | 参数、stdin 或明确文件均可；必需信息缺失时返回可操作错误，避免等待交互提示 |
| 发现参数 | `--help` 给用途、参数和典型调用；常规使用无需先读源码 |
| 输出 | 数据与诊断分开；机器消费采用明确结构，退出码区分成功与失败 |
| 纠错 | 错误说明实际问题、允许值或需要补充的输入，使下一次调用可以修正 |
| 大结果 | 提供适当摘要、分页或文件输出，避免关键信息被工具输出截断 |
| 重试与副作用 | 明确重复执行是否会重复写入；有状态或破坏性动作提供适合风险的预览和恢复方式 |
| 依赖 | 随包提供所需资源，声明额外依赖；在实际交付布局验证，不借用源码目录的偶然环境 |

这些要求约束可消费接口，不规定实现语言、内部函数、固定字节上限或每个脚本都必须有 dry-run。上限、覆盖策略和恢复动作由当前数据与副作用决定。

批量或破坏性写入采用 执行前计划验证（`references/design-and-validation.md#执行前验证计划`）。接口应能把拟执行内容与真实字段、类型或目标清单对照，并给出可修正的具体差异。只有预览、JSON 可解析或参数合法，不足以证明业务计划有效；校验逻辑仍需真实依据。

## 在 Skill 中怎样介绍

在会用到它的步骤或分支给出脚本路径、调用条件、输入来源及结果怎样用于下一步。只列文件名不足以说明用途；复制整个实现或完整 help 又会增加普通路径的负担。

随包脚本路径遵循资源引用规范（`references/skill-format.md#资源引用`）。

例如已有的归并工具可这样接入业务方法：

```markdown
整理用户提供的发票记录时，运行：
`node scripts/merge-invoices.mjs <input-file> --format json`
用结果中的 totals 编写分币种汇总；将 unresolved 中的记录交给用户确认。
```

这类例子展示的是调用与业务方法的连接。实际脚本的参数、字段和状态必须来自其真实接口。例子中的文件名不是应生成的通用模板。

完整参数交给 help；普通错误交给诊断。正文只补脚本不能知道的业务选择，以及会改变后续行为的特殊结果。发现执行者反复读实现才能继续时，先修 help、错误或输出结构，而不是把源码搬进 reference。

## 验证交付

通过公开入口执行代表性正常输入与关键错误输入，检查 stdout、stderr、退出码和实际产物；写操作增加重复执行或部分失败对照。再从交付目录验证一次依赖和资源可达。测试保护真实接口和副作用，不以代码存在或语法正确代替运行证据。
