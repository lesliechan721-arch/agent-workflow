# 从任务经验形成 Skill

新建、实质重写或改变职责时使用。已有的局部修改不重新建立完整设计。

## 取得真正的增量知识

读取实际任务材料、领域规则、用户纠正和已有执行结果。找出专家会使用而目标执行者未必知道的信息：如何解释字段、怎样选择方法、哪些看似合理的做法会失败，以及完成结果应满足什么约束。

来源可以是规范、已有工作流、真实轨迹或已接受样本。现有 Skill 也是待核对材料；不要以它已经写了某条规则为充分理由。缺少领域事实时保留缺口，不能用通用质量提醒填补。

先回答：没有这个 Skill 时，执行者还缺什么？只剩一般编程常识或用户已经说清的动作时，通常不需要额外方法。真实规范知识即使模型可能见过，也可为当前任务提供稳定依据；实际收益仍需验证。

## 提炼而不是复写案例

从成功任务保留可复用的选择依据，从失败和纠正中保留能改变行为的陷阱。区分这一次的数据、当时选择的方法与可以推广的条件。不要把一个输入的固定答案、目录或阶段数当作所有任务的要求。

选定连贯用户结果及相近边界。一个 Skill 可以包含多个条件分支，但它们应服务同一类结果；独立能力、权限或证据生命周期发生变化时，再按组合方法判断边界。

用代表性输入检查：执行者从哪些材料作出哪些决定，产物如何核对，哪项条件改变后需要换方法。重点不是每个任务都建立完整流程，而是把非显然判断写清。

任务要求以给定方法或规范为基础时，按适用主题核对核心概念、概念关系、选择依据和例外。产物应表达这些含义，或通过明确条件到达完整来源；未采用的部分应能由当前范围解释。只列术语不算保留方法，单个正常输入走通也不能证明其余适用主题已经覆盖。局部修改只核对受影响部分，无需另建映射文件。

## 选择表达与资源

共同知识和必须立即知道的陷阱进入正文；条件分支放有明确指针的 reference。外部公开规范可提供完整事实源，正文保留当前任务需要的稳定摘要与选择依据。

模板适合固定且确有用途的输出；脚本适合精确、重复或脆弱的机械操作。基础程序结构不需要教学例子；接口用法、输出特征或难以用文字准确描述的差异，才值得示例。例子解决哪个歧义应能说清。

操作只有一种正确顺序或错误代价很高时，固定必要步骤。多个方法都合理时，给默认选择及何时改变它，保留执行自由。普通错误让工具诊断和模型排查，正文补工具无法知道的业务含义。

## 按脆弱性安排检查

非显然陷阱应在执行者遇到前可见。例如，同一业务标识在两个接口中的字段名不同，不能只写“映射失败时再读字段规则”；应在映射步骤说明差异，或在进入该分支前要求读取依据。一般报错仍交给工具诊断，不把所有罕见错误搬进共同路径。

有依赖的多步工作可用简短检查清单保持覆盖：每项对应实际对象、前置结果与可检查的完成依据。标记已完成应来自真实检查，不能以勾选或“已理解”代替结果。清单服务防漏，不必另外保存进度文件。

### 执行前验证计划

批量写入、破坏性动作或错误会向后传播的操作，适合先把拟执行内容组织为可检查的计划，对照事实源验证后再执行。预览只展示打算做什么；计划验证检查这些动作是否成立；执行后检查确认实际产物。三者不能互相替代。

例如，批量填写表单时先读取真实字段及类型、必填要求，形成字段和值的映射。用可用校验工具对照两者检查未知字段、类型不符和遗漏必填项；失败就修正映射并重验，通过后才填写，最后检查实际输出。没有相应校验工具时，应说明哪些检查能直接完成、哪些仍缺依据，而不是编造验证成功。

执行使用刚核对的计划与依据；其中之一改变时重验受影响部分。计划是否落盘由工具输入或实际交接需要决定。普通小改和纯参考任务不因这个模式增加审批、持久状态或新的阶段。

## 用任务核对

先检查字段、引用与脚本入口，再让代表性任务检查方法是否足够。观察实际产物、无用步骤、查找和重复试探；需要证明增益时比较同条件下的基线。没有运行只能报告设计分析。

结果出错时先定位：知识缺失、指针未到达、方法错误、工具接口、用例前提还是评价规则。修对应部分，不为每次失败新增共同规则；改变一个方法后检查相近正确任务是否仍成立。

交付当前 Skill 与实际验证。设计依据只在用户要求或后续独立实施需要时保存，不强制生成中间设计协议。
