# 公开能力与插件边界

用于判断用户应该看到哪些入口，以及这些入口应怎样组合。

## 从用户意图归组

用用户会请求的结果归并任务，例如创建、评审、简化、运行，而不是先按目录和内部对象拆分。为每组确定代表性输入、产物和所需知识，再检查当前入口是否多于或少于实际需要。

一个公开入口应能完成连贯结果，或提供真实可复用能力。只有对象不同、方法与权限相同的分支，可以由同一个入口按条件读取参考资料；具有独立裁决、执行环境或权限边界的能力则可能应分开。

## 检查发现与组合

比较相近入口的 description 是否给出决定性条件。用户能直接请求的结果可以公开；只服务一个上层步骤且没有独立用途的碎片，应比较合并或内部参考的方案。

增加统一入口前，检查它能否可靠选择下游，是否只是重复说明现有入口。用户专用宏不能被包装成自动调用的必要下游。入口更少不自动证明更易用，入口更多也不自动证明职责清晰。

多个手动入口难以记住时，导航型 router 可以列出各入口用途和选择条件，让用户只记一个起点。它帮助人选择，不因此获得代替用户启动下游的能力。若现有索引已经够用，无需再包一层 Skill；模型路由则要求所选下游确实允许模型采用。

## 检查插件边界

独立安装价值、不同受众、运行依赖、权限或发布节奏可支持拆分。只有源码目录不同，不足以支持独立插件。方法共用也不等于必须合并插件；资源复制、安装依赖和运行调用是不同关系。

检查共享资料放在哪个领域层。所有 Skill 都能使用某条 Skill 机制规则，不意味着普通 Agent 文档也应该加载它；通用内容方法和包装、调用机制分别处理。

## 比较净收益

沿真实常见任务比较公开 description 的常驻成本、用户选择、实际正文与参考读入、工具调用、交接和维护位置。保留有价值的人工作出判断，不把全自动或最少入口当成唯一目标。

只有减少的使用负担或独立权限、证据收益超过新增发现和维护成本时，才建议拆分、合并或增加 facade。结论说明受影响的任务族和能力；不为当前局部问题顺带重构全部公开面。
