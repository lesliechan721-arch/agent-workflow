# 深入评审 Skill

完整评审或需要细查特定问题时采用对应主题。

## 任务价值与范围

从真实请求、领域资料或失败记录确定 Skill 补足的知识，比较不用 Skill 的合理处理路径。方法应覆盖一类连贯结果，而不是把一个案例的答案固定化。规范与领域经验可以支持设计；实际增益仍需对照。

检查 description 是否表达用户意图与真实分支，正文是否完成同一任务。关键词重叠只说明可能匹配；加载后失败要检查方法，而不是继续扩大 description。

## 方法与脆弱点

沿输入到产物检查所需依据：字段的业务含义、选择默认方法的条件、例外会怎样改变动作，以及什么结果表示完成。问题要指出具体缺少的判断；“不够详细”本身不是缺陷。

以给定方法或规范为基础的 Skill，另从来源逐主题核对适用的核心概念、关系、选择依据和例外。检查它们是否表达充分或有明确可达的引用；未采用部分是否确属范围之外。一个正常任务成功不能代替来源覆盖；问题应指出丢失的含义及受影响场景，而不是要求逐句复制原文或固定目录。

反向检查多余控制。每个强制步骤是否对应顺序依赖、真实风险或输出需要？可以由模型自由选择的方法不必固定成唯一过程；有实际错误代价的约定不能仅因可外查就删除。

批量或脆弱动作采用计划时，核对计划是否与真实字段、类型或目标范围验证，执行是否使用已验证内容；预览不等于计划有效，事后检查也不替代可行的事前校验。陷阱应在遇到前可达，检查清单应对应实际覆盖；普通小改没有这些阶段并不构成缺陷。

例子应消除一个难以准确表达的歧义，或给出实际接口的使用方式。模型已会的基础实现无需演示。现成工具需要可发现的用途和调用，通常不需要在 reference 中复制源码。

## 内容与资源

采用 `agent-content` 的层级与剪枝方法，沿常见路径和独立分支检查实际读取。必要资料不能只存在于磁盘；短正文也可能因为弱指针而无效。完整同层参考无需机械拆分，共同方法也不应为了缩短主文件再增加必读跳转。

检查外移后是否仍保留条件、单位、例外和来源。配置、help 与文档之间出现重复时，判断执行者是否确实需要这份缓存，而不是奖励资料数量。

## 包、工具与输出

按实际被消费的包判断资源完整性，再通过映射定位修改源。可选组件的正确省略不是缺陷；工具未覆盖的扩展也不能当成客户端拒绝。

脚本重点看可用接口和实际执行：输入、输出、错误、重复调用及交付依赖。语法检查不等于运行测试；一次成功不覆盖全部分支。

固定输出的用途可来自用户格式要求、实际程序消费或跨上下文交接。沿真实生成物和读取点核对；只有一个 validator 不能证明业务用途，静态搜索未找到也不能证明不存在。

## Eval 与效果

分别检查是否命中、是否首次入口、是否允许辅助使用、是否真正完成任务。用例需提供决定性前提；已知缺陷修复不代替自主检出，限制修改不代替正向能力。

需要判断增益时，比较相同资料、工具、权限和环境下的基线与候选；检查轨迹中的无用步骤、重复实现和人工介入。实际产物、语义质量及成本分别评价。正确对照限制误报，高影响回归不能被平均通过率抵消。

提出修改前定位根因属于正文、脚本、用例、评价器、调用者还是环境。只对有实际根据且能改善目标任务的问题补规则。
