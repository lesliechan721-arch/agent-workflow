# 设计 Skill Eval

创建或修改 Eval 用例、fixture 与断言时读取。

## 1. 先定清楚要证明什么

挑少量有区分度的真实场景族，分别验证**触发、正确使用、最终产物与成本**——只测“别多做”不能证明会完成任务。旧回归、常见任务与机制探针分开记录，不拿同义请求堆数量。

- **Oracle 来源**：预期与允许差异必须来自用户需求和领域规则，不能倒推自“当前 Skill 恰好怎么写”。首轮可先写清真实输入与高层预期，观察真实输出后再细化客观断言，但细化依据仍须锚定需求而非迁就草案输出。
- **边界配对与真实上下文**：prompt 放入真实路径、字段名、口语或隐式意图等上下文；正例配最小条件变化且共享领域概念的 near-miss 负例（禁用毫无关联的送分负例），同时保留等价正确对照，防模型过度修正。
- **触发标签含义**：`expectedLoad` 只看观测期是否加载，不等于必须是首次入口，也不要把合法辅助使用标成 `false`。

## 2. 构造真实可达的 Fixture

- **服从消费者格式**：有实际运行器或调用方格式合同时严格采用，不外加未要求字段；无格式依据时输出人读案例，不自造通用 JSON。
- **前提真实落盘**：测文件处理、工具或修改范围时，fixture 必须真实提供文件、脚本或权限，不只在 prompt 里写一句“环境已准备好”。
- **区分正常与非法输入**：正常包满足基本前提；有意非法包只测拒绝，不同时假装测后续方法。只读规则要在“模型有写工具但主动不写”时验证，不能只靠环境禁写。
- **交接链路真实串联**：测跨组件交接时，让下游消费本次上游实际产物，不拿两边手工好样本冒充整链。

## 3. 写有区分力的断言

- **机械检查归程序，语义判断归评审**：文件存在、精确字段、数量和修改范围交给确定性检查；内容质量写清可观察目标与允许差异，不锁固定措辞、标题或无用协议。写作质感、排版审美等难以客观二值化的维度，不必强拆成脆弱断言，留给人工直接审阅产物或盲评对照。
- **不泄露答案**：检出用例不提示缺陷位置；测自主设计时只给原始资料和目标，不在 prompt 里暗示删哪段或用什么目录，也不把目标完整正文作为依赖提前塞入上下文。
- **写清翻转条件**：说明为什么该条件决定结果、什么最小改动会翻转预期。

## 4. 对照与归因

比较基线与候选时，固定同一套资料、权限、工具、用例与评分规则。无 Skill 基线删掉对已移除能力的悬空调用，但必须保留完成任务所需的原始领域资料。

用例全过先查是否只测到模型常识，用例全挂先查 fixture、Oracle、评价器和运行环境，最后才改生产 Skill。改过 Oracle 后，受影响的旧对比作废。

交付用例、fixture、允许差异与判定依据，明确结构检查、独立审核与模型运行的实际状态；作者自检不代替 `audit-agent-skill-evals` 的独立准入。
