# 形成可实施设计（Design）

覆盖需求对齐、工程结构设计与按需规格记录，**停在用户要求的设计范围，不自动开始产品实施**。只读评审请求只给判断，不改文档。

## 1. 盘点现有依据与真实缺口

先读原始请求、补充要求、既有代码、真实消费者及已接受原型（核对版本与适用范围）。**能靠代码、历史或最小实验确认的事实先自行查明**，只把真正影响行动的缺口按类别分派：

| 当前缺口 | 采用能力 | 产出 |
| --- | --- | --- |
| 现行机制、限制或历史动机不明 | `dev-investigate` | 带引用的事实链、约束与记录空白 |
| 产品目标、业务规则、范围或优先级未定 | `decision-grill` | 真实用户答复、委托边界与开放问题 |
| 界面、信息层级或状态交互需体验校准 | `decision-prototype` | 绑定版本与接受范围的原型结论 |
| 跨模块接口、状态所有权或迁移结构未定 | `dev-architect`（大争议走 `dev-arena`） | 调用示例、具体类型签名、边界与迁移顺序 |
| 已有复杂材料或当前复杂设计妨碍人审理解 | `explain-clearly` | 高可读清晰讲解、图示或一次性交互探索页（不冒充新候选） |

先广后深检查范围内主题（目标、角色、正常与关键失败/恢复、状态归属、兼容、验收）；尚未展开不等于排除。发现需求前提矛盾或投入产出失衡时，直接提出反对与替代（Candor）。

多轮用户来源、替代关系或原型接受范围复杂时，读取 `references/spec.md` 的来源保真条款防止遗漏原始约束或把推荐误写成硬要求。主题对齐需要持久化记录时，可参考 `assets/shape-template.md`。

## 2. 交付形态：以“接手可直接实施”为标准

设计是否完整看**下一位实施者是否还需猜测会改变行为的关键条件**：目标与保持条件、真实正常/失败/取消调用示例、具体数据形状与接口签名、状态与资源所有者、迁移退出条件及真实表面验证入口。

- **默认轻量交付**：直接输出调用示例、具体类型草图、接受原型指针与关键决策说明，不必为形式汇编长篇同义文档。
- **按需保存或完整规格**：需要跨会话保存、暂停交接，或用户/项目明确要求完整规格时，读取 `references/spec.md`（可采用 `assets/spec-template.md`）输出文档；明确完整规格请求必须覆盖全部所要求范围，不得只交第一个切片。

## 3. 检查与收口

作者先自检来源覆盖、新增硬约束依据与结构一致性。需要独立审查设计或计划时，调用 `dev-review`（**走常规需求/结构/调用链审查；纯抽象设计禁止启动实测对抗模式，争议技术假设优先用最小实验或原型定案**）。

发现要求矛盾或工程事实推翻产品承诺时，交回具体后果由用户决定，绝不改写有效需求去迁就方案。

**回复**：当前设计结论与可实施依据（或文档路径）、区分已接受产品要求 vs 授权内工程基线 vs 待证假设、关键检查结果与剩余未决项，停在设计。
