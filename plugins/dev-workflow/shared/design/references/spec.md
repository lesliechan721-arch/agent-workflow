# 保存规格与来源保真

仅在需要跨会话保存、暂停交接，或用户/项目明确要求完整规格文档时读取。已有可读材料足够就直接引用，不把文档保存变成实施前置门槛。

## 1. 规格结构与四类分级

1. 按接手者实际需要组织，可采用 `assets/spec-template.md`；保存或交接只写接手必需章节，明确完整规格请求须完整覆盖所要求范围与可观察验收。
2. **组织人审呈现时采用 `explain-clearly`**：复杂多主题、多状态机或长规格按认知瓶颈采用清晰受控短句（80% ASD-STE100）、具象正常/失败贯通示例、结构图/SVG 或一次性交互探索页，降低人审负担且不丢失精度与单位。
3. **四类内容严格区分**，严禁混写：
   - **用户已接受要求**：绑定精确来源或原型接受版本；
   - **授权内工程基线**：工程侧选定的结构约束（可直接约束实施，但不得冒称用户逐项指定）；
   - **未验证假设 / 未决项**：写明阻塞范围与验证方式；
   - **可等价调整细节**：留给实施者的自由度。

## 2. 来源与设计保真

多轮用户要求、明确替代关系或原型接受范围复杂时，逐项核对以下四条：

- **保留原貌与时间序**：按原角色、顺序和完整正文核对原始要求与后续修正，不把多次重复压缩成无时间背景的结论；按有效优先级与明确替代关系判断当前约束。
- **不降级也不私自加码**：核对每条要求的主体、条件、例外、精确值和强弱度（必须 vs 建议）；既不漏掉限制，也不把助手建议写成用户硬要求。
- **原型绑定精确边界**：接受原型必须记录具体 revision、适用页面/状态、必须保持的关系与允许变动的细节；视觉近似不等于交互关系一致。
- **双向核对与版本保留**：每条实质来源都有对应设计、未决项或明确排除依据；每条新增硬约束都有真实来源或授权。不用“后续补充”掩盖范围内缺口，也不把“没人反对”当成批准。替换旧版规格前，确保旧交付对应版本与接受原型仍可按原版取回。
