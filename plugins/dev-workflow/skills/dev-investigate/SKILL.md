# Dev Investigate

只读建立事实链，回答“怎么工作（How）”与“为何如此（Why）”。不修改产品代码。

## 1. How：解释当前机制

- **小范围直接追踪**：直接从真实入口或消费者顺藤摸瓜，不要为此启动子代理。
- **跨多模块或大代码库**：用 `spawn-subagent` 派 1 名只读子代理一步完成探索与解释，把大段文件阅读留在子上下文；主代理核对关键路径后整理呈现。
- **追踪抓手**：从真实调用入口追到数据与状态权威（谁能写、何时失效），追完正常完成、异步完成、失败、取消与资源释放；不把目录清单当架构说明。
- **区分源码与单次运行**：源码只证明“可能行为”；解释某次具体运行必须核对对应实例、构建版本与实际观测。

## 2. Why：查证历史理由（反事后脑补）

**从历史记录回答，绝不从代码倒推作者动机。**

1. **固定代码锚点**：锁定具体文件、符号和引入该逻辑的提交，沿文件重命名和移动追溯原始提交（`git blame` 最后修改者往往不是原设计者，顺父提交继续追）。
2. **完整阅读一手史料**：通读引入与演进提交的完整 commit message、diff、PR 讨论、关联测试和事故单，不凭标题或单句切片定性。记录不足时才向其他已授权来源扩展。
3. **反迎合与反虚构**：把用户提问里的猜测和 How 推出来的“合理逻辑”一律当作**待检验假设**，不得当已证事实复述；搜索为空只说明该范围未命中，不证明理由不存在；多处转述同一条记录只算一条独立证据。
4. **逐项标注证据强度**：每条关键结论必须标明属于以下哪一档：
   - **直接记录**：作者或同期讨论明确写下的理由（引原话与出处，并注明当时前提今天是否仍成立）；
   - **推断**：与已知事实吻合但无直接动机记录（显式标为推断并给可反驳条件）；
   - **记录未答**：历史材料缺失或存在矛盾解释，明确留白。

## 3. 运行现场与固定捕获

分析日志、CPU profile、堆快照、trace 或固定捕获文件时，先读取 `references/runtime-evidence.md`。

## 交付

先给直接答案，再附关键路径/沿革、具体 `file:line` 或提交引用、证据强度与**记录未回答的空白项**（缺空白项说明可能存在未披露的脑补）。仅当本次调查为后续改动铺路时，末尾追加简短的 `Preserve（仍须保留）/ Change（前提已变可改）/ Avoid（历史坑）/ Risk（未明风险）`。
