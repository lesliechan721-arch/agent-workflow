# Dev Review

只读审查产品对象，只报告有实据的问题，绝不直接改产品代码。**零发现是完全合法的结论**，不要为凑条数制造风格吹毛求疵。

## 1. 定范围、独立性与模式选择

先固定：被审对象与版本（代码默认包含分支 diff 及工作区未提交改动）、原始意图与有效约束。意图不明时先用自己的话复述确认。

**独立视角**：若被审对象由当前会话刚编写且需要正式独立审查，用 `spawn-subagent` 派 1 名干净上下文子代理按本方法审查（不把作者私有推理喂给它）；若无独立执行条件，如实标明“作者自查覆盖”。

**快捷分流**：
- 用户或工作流要求**“只做实测压测 / 零噪声找可复现 bug / 尝试打穿实现”**，且对象为**可运行代码或可执行原型** → 直接跳去执行 `references/adversarial-interrogate.md`，跳过下方的常规结构审视。
- 其他所有审查（代码、设计、计划、小 diff 安全影响面） → 先执行下方常规与影响面审查，再按第 4 节二元条件决定是否升级对抗实测。

## 2. 五档证据阶梯（每条发现必须标明档位）

1. **口头猜测**（“这里可能为 null / 也许有竞态”）→ **禁止提交**。
2. **指到真实 `file:line` 或依赖库源码**。
3. **沿真实调用链证明坏路径可达，或对照原始要求证明具体违约/遗漏**。
4. **运行最小脚本/测试调用真实代码并复现错误**。
5. **在运行中的应用实例复现**。

- **需求遗漏、架构/所有权缺陷、状态机/兼容缺口、难稳定复现的并发与安全风险**：最低需达到 **2–3 档**（给出真实代码路径、违约条款与实际后果）。
- **声称的运行时 bug、边界崩溃、回归或安全前提**：凡能低成本运行验证的，必须推到 **4–5 档**，不停留在纸面推演。

## 3. 影响面排查（Blast Radius，代码改动必做）

**列 grep 调用方不是审查，真正的任务是找出 grep 看不见的破坏：**

1. **追过 grep 边界**：核查 JSON/线格式、数据库列、配置键、字符串/动态注册、卸载与异步时序（microtask/teardown）、下游三跳消费者，以及被调第三方库当前锁定版本的真实源码。
2. **逼出“它之所以安全的 1–2 个唯一前提”**：把主要精力花在验证这 1–2 个决定生死的事实（推到尽可能高的证据档位，并诚实写明停在哪一档），而不是罗列一长串“也许会坏”。
3. **盯紧自供状线索**：把 diff 里新增的 workaround 解释注释（`IMPORTANT`、`do not remove`、`fine for now`）以及正确性/安全类的 lint/TS 抑制（`@ts-ignore`、`@ts-expect-error`、`eslint-disable`）当高危缺陷线索追查根因。

## 4. 升级对抗实测的硬条件（二元分流）

**前置铁律**：仅适用于**可运行代码或可执行原型**。**纯抽象设计或实施计划禁止进入实测对抗**（读不到可运行对象只会逼审查者编造玩具假设；请停在常规审查，并对未决技术假设建议先做原型）。

对象可运行且命中**任一**条件时，必须读取并执行 `references/adversarial-interrogate.md`：
- 用户或上游工作流明确要求对抗压测 / 独立实测破防；
- 改动触及高代价运行边界：并发/锁/异步取消、鉴权/权限边界、持久数据格式/迁移、或多消费者共享核心契约；
- 常规审查中出现**读代码无法定案、但运行即可证伪**的关键运行时争议。

## 5. 去噪过滤与输出

提交前逐条自查并果断驳回：不可达的假想输入、需要“未来某次修改”才会触发的担忧、纯代码风格或命名偏好。按三段交付：

- **安全核心前提（代码改动）**：陈述 1–2 个核心安全前提、验证到的证据档位（1–5）及实据（无法证明直接标 `未证明`）。
- **已确认问题**：按严重度分 `阻塞/真实风险` 与 `可权衡项`，每条含位置、证据档位、具体复现/调用链与违背的目标；零发现直接写 `无已确认问题`。
- **已驳回与覆盖限制**：简列排查后确认安全或被滤除的候选项及原因，并注明未检查/未运行范围。
