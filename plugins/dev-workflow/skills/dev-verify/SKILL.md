# Dev Verify

直接检查真实产物与用户触达的表面。**“能编译”“端口在听”“测试文件多”“子代理自述完成”都不是通过证据。**

## 1. 按承诺匹配真实表面（反代理指标）

先固定待证明的承诺、对象版本、预期来源及允许动作，核对启动的确实是本次修改后的构建和实例（防止命中旧进程或错误端口）。

| 变更类型 | 必须验证的真实表面 | 严禁冒充通过的代理指标 |
| --- | --- | --- |
| CLI / 脚本 | 用真实参数跑编译/安装后的命令，检查 stdout、stderr、退出码与文件副作用 | 只看 `--help` 或单测 mock |
| API / 服务 | 向真实实例发请求，核对响应体、错误码与实际持久化副作用 | 只看健康检查 200 或端口监听 |
| UI / 交互 | 在运行应用中走完变更流程，观察视觉状态、反馈与交互结果 | 只看无 JS 报错或仅存了一张未核对的截图 |
| 存储 / 迁移 | 写完后从真实存储读回验证，并按承诺方向回放旧/新数据 | 只看写入函数未抛异常 |
| 异步 / 后台任务 | 等到真实完成信号并检查最终产物与失败/取消清理 | 只看任务“已入队/已受理” |
| `--dry-run` / 模拟模式 | 实测确认它确实跳过了文件/网络/git 副作用 | 轻信参数名本身 |

## 2. 执行、归因与清理

1. 先写可观察预期与失败判据，再操作真实表面；保存完整命令、版本、原始输出与状态证据。
2. 失败时保留首次现场，清晰区分：**产品缺陷**、**验证驱动错误**、**环境前提缺失**、**文档/入口漂移**或**预期已过期**。严禁放宽有效预期或删场景换取绿灯。
3. 只清理本次自建的进程与临时数据（绝不按进程名误杀），清理后确保原始证据仍可读取；未知外部副作用先只读核对，不盲目重放。

## 3. 条件分支

- 承诺包含已接受的页面布局或交互原型：读取 `references/design-fidelity.md`，在等价数据、身份与视口下对照真实运行画面。
- 涉及性能数字可比性或异常提速：调用 `dev-benchmark`。
- 项目已有形式化属性或模型需核验：读取 `references/formal-check.md`。
- 项目缺少可靠验证入口时：完成当前范围可行的直接验证并如实报告缺口，**不要自动升级去建设整套项目验证资产**（那属于用户显式启动的 `dev-verify-author`）。

## 交付

逐条承诺标明 `通过 / 失败 / 阻塞 / 证据不足 / 未运行`，附命令、关键原始输出与未覆盖范围。入口可靠抓出了产品 bug 只能说明入口有效，产品仍判失败。
