# 创建、维护与修复运行验证

从用户能力选择覆盖范围，复用已有可用脚本。写出的入口要让冷启动 Agent 无需依赖作者记忆就能跑通真实验证。

## 1. 先访谈仓库，再问人

先读入口代码、开发脚本、配置与文档，只把代码里观察不到的事项问用户：用户触达的表面（CLI/API/UI/桌面/库）、本地启动方式（端口/环境变量/种子数据/登录）、可编程驱动（优先既有 harness，其次浏览器/CDP、PTY/tmux 或 HTTP）、可捕获证据、以及能否多实例隔离并行（不能隔离就明确拒绝双驱，避免污染用户会话）。

## 2. 五段闭环

| 部分 | 必须写清的知识 | 常见伪通过 |
| --- | --- | --- |
| Launch | 目录、命令、依赖、空数据目录初始化/迁移/种子、隔离与就绪判据 | 只发现端口监听，但初始化数据或依赖服务未就绪 |
| Doctor | 构建/版本身份、健康状态、端口归属与鉴权只读自检 | 命中了另一实例或未重建的旧进程 |
| Driver | 真实 CLI/API/UI 驱动，优先稳定句柄（ARIA、data 属性、路由、提示符）而非坐标 | 绕过真实入口调内部 helper 或测试后门 |
| Evidence | 预期、实际输出/状态/副作用与原始产物路径 | 只有截图、零退出码或“看起来正常” |
| Cleanup | 精确停止与清理本次自建资源（绝不按进程名强杀） | 误删共享资源，或清理时把失败证据一并删掉 |

这五段是职责划分，不强求建五个脚本；简单项目写在一份入口内，多功能项目按条件链接场景。

## 3. 功能地图

按用户能力（而非源码目录）建索引与每功能一页，说明：子功能、用户到达路径、驱动方法、可观察通过标准与已知坑（Gotchas）。同一功能从启动到清理跑通才标为有效；未覆盖项如实列出，严禁放宽场景迁就缺失前提。

## 4. 核验检测路径与维护

1. 跑通代表闭环，并在安全隔离的试验数据上注入可撤销错误（负例）确认检查真会为目标问题报红，再恢复基线确认变绿（严禁改真实用户数据）。
2. 维护旧资产时，对比上次适用版本与当前改动（含新增入口、重命名、空状态与异步流程）；先证是入口/文档错误才修入口，产品回归直接报产品失败；修完文档后必须按新文档实跑受影响路径。
3. 清理完成后再次确认原始证据仍在约定位置保留可读。
