# 形式化验证与模型维护

仅在存在来源明确的高危属性（如并发交错、锁租约过期、乱序状态转移），且形式化方法与工具适合当前问题时采用。

## 1. 从危害与合同选属性与工具

从真实危害、用户合同或核心不变量写出属性，保留例外与适用对象；输入假设不能直接等价于待证结论。按问题选工具：状态交错与并发优先模型检查（如 TLA+/TLC）；代码级属性用语言对应验证器；只适合生成式/属性测试时如实称为测试，绝不改称形式化证明。

## 2. 建立可审查的模型对应

| 必须记录 | 重点防错 |
| --- | --- |
| 状态、初始条件、输入 | 确认目标风险真能发生，未过度限制环境造成空洞通过 |
| 转换与实现符号 | **核对模型的一步原子操作在实现里是否分多次写入**，以及反向避免造不可能交错 |
| 属性与假设 | 区分待证属性与外部假设；假设须可在实现中维持 |
| 抽象与省略 | 写清省略的数据、并发、故障与时序及其后果 |
| 搜索边界 | 记录深度、状态规模、数据大小、超时设置 |
| 同步基准 | 记录模型版本、对应实现 commit/diff、覆盖文件与符号 |

## 3. 执行、负例验证与维护

按 `references/formal-check.md` 执行属性集并做可撤销负例测试（从未见过失败的检查证明不了任何事），负例恢复后重跑基线。

实现或环境变动时，对比上次同步基准检查全部影响（含新增写者、重命名、原子边界与恢复路径；“旧模型仍绿”不证明新实现正确）。逐项归因：合同变更 → 更新属性并记原因；模型漂移 → 修映射并重跑负例；实现违约 → 报产品失败；工具阻塞/超时 → **绝不推进同步基准**。

交付时分别写明三件事：入口能否复跑、属性在所声明模型与边界内的判定、模型与真实实现的对应程度。
