# 代码审查

独立审查代码改动、阶段结果、diff、branch 或 PR 的需求符合度和工程质量。可以单独调用，审查期间不修改代码、测试、Spec 或共享工作状态。

默认由两个 fresh 独立 reviewer 分别主责需求与设计符合度、工程质量，工具支持时并行，否则顺序审查。必需 reviewer 不可用、未完成或目标变化时，说明覆盖限制，继续报告已确定的问题。

审查依据原始需求、有效决定、Spec、已接受设计和实际代码。涉及界面时，在可比较的数据、视口和状态下检查设计关系与真实行为；功能测试通过不能代替设计对照，等价的 DOM/CSS 改变可以接受。

报告分别给出两轴判断、范围、版本、证据及问题的关闭条件，区分确定缺陷与证据不足。默认在对话中交付；明确要求保存时采用指定位置或确认的项目约定。复审使用新的干净上下文核对累计变化和旧问题关闭情况，允许复用仍有效的旧证据，但不恢复上轮 reviewer 会话作新判断。新上下文不要求每次全面重审。

工程审查同时检查新机制的当前用途、实现的完整影响面与测试价值。复杂度问题须说明具体成本或风险，不按行数、测试数量或个人架构偏好强制扩展。

```text
使用 dev-review-code 审查当前权限核心的需求符合度和工程质量，说明问题与覆盖限制，不修复代码。
```

阶段推进、修复预算、交付采用和报告历史由调用者负责；审查不授予修复、提交或后续执行权限。执行说明见 [SKILL.md](SKILL.md)。
