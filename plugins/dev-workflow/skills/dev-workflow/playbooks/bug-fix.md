# 故障修复（Bug Fix）

**核心纪律**：每一行进入最终 diff 的代码都必须追溯到运行证据。“也许有用”的防御补丁不进入交付；证据推翻的假设必须连带回滚它引发的全部改动。

## 步骤

1. **亲手复现原故障**：按原始版本、配置与表面亲自跑出失败，保存完整复现命令与失败输出。只有确认工具/环境确实无法触达目标表面时才请用户复现，并说明卡点。
2. **科学二分锁定根因**：原因未明或存在竞争解释时，调用 `dev-debug` 二分排除假设并确认最早出错决定（必要时用 `dev-investigate` 查回归历史）。根因机制未获运行证据前，禁止直接打补丁。
3. **清理实验现场并设计修法**：撤回全部临时日志或探针。若修复跨越函数/模块边界，先用 `dev-architect` 定形状；排查授权范围内是否还有同类根因路径。
4. **先红后绿（条件 TDD）**：具备廉价稳定本地测试路径时，按 `dev-tdd` 先提交/写好针对该缺陷的失败测试并确认真红灯，再做最小根因修复并重跑变绿；若需昂贵 harness，跳过烂测试，用原复现命令或定向脚本取证。
5. **同表面复验与回归**：在**原故障同一表面**重跑复现确认通过（单元测试绿不能替代原表面复验），并检查邻近合法输入与错误恢复路径（必要时用 `dev-verify`）。
6. **高危审查**：涉及共享基础、状态机、并发或高回归风险时，用 `dev-review` 检查影响面与安全前提。

**回复**：原始故障现象、运行证据锁定的根因、最小修复内容，以及**原样粘贴修前失败 → 修后通过的复现输出**。
