# 重构、迁移与代码简化（Refactor）

**铁律：结构变，有效行为不变。** 若清理途中发现新需求或真实 bug，拆出去单独处理，先在锁定行为的前提下完成结构变更。大型跨多期重构改走 `playbooks/compose.md`。

## 1. 先锁定行为基线，再动结构

1. **定位真实负担**：说明这次到底要消除什么具体理解或迁移负担（追踪决定要跳几层、改一条规则要同步几处、要记多少隐藏状态）。行数变短本身不等于简化；代码已经清楚就直接报告并结束。
2. **钉死行为合同**：先有表征测试、快照或等价性检查脚本锁定现行外部行为（**类型检查和 lint 不是行为基线**）。涉及动态入口、持久格式、序列化、公开接口或新旧共存窗口时，先读取 `references/behavior-preservation.md`。

## 2. 先减后建、小步绿灯迁移

1. **定目标形状**：跨模块边界或涉及所有权调整时，先用 `dev-architect` 明确目标类型与边界。
2. **先做减法**：删死代码、折叠单调用方 wrapper、去多余状态与冗余校验，再引入新结构。
3. **小步保绿 + 一波清旧**：每一步保持行为基线绿灯。内部 API 改型时在同一波迁完所有消费者并删旧入口，**主动抽查字符串、配置、生成源和文档示例**（防重命名漏网）。
4. **顺手清剿“自供状注释”**：检查范围内新增或存量的 workaround 注释（`IMPORTANT`、`do not remove`、`fine for now`）和正确性/安全类 lint 抑制；属自有代码怪癖的优先改结构消除，确属外部不可改约束的保留最小出处说明。

## 3. 证明等价且读者负担净下降

1. 在真实消费者或等价性脚本上证明行为不变（共存迁移按合同方向回放新写旧读/旧写新读）；必要时用 `dev-verify` 或 `dev-review`（查 Blast Radius）。
2. 用步骤 1 同一个维护任务对比改前/改后追踪层数、隐藏状态与同步点：**若读者负担没有真实下降，回滚自有改动并如实报告**。

**回复**：改变了什么结构、行为基线与等价证明、读者负担的前后对比、已退出或仍保留的兼容窗口。
