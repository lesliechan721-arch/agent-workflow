# 功能与行为变更（Feature）

负责人持续持有整体目标、共享合同、集成与整体验证；委派只交出具体工作单元。

## 1. 建立最小可执行依据

读取请求、issue、接受原型（绑定版本与范围）、调用示例、工程草图或既有规格，固定原代码比较基线。已有足够依据直接开工，**不重写规格**。

若存在会改变后续行动的真实缺口：
- 机制/历史事实不明 → `dev-investigate`
- 产品行为或体验未定 → `decision-grill` / `decision-prototype`
- 跨函数/模块接口或状态所有权未定 → `dev-architect`（大争议或高返工代价直接 `dev-arena`）

大任务按就绪单元滚动推进：先敲定约束多单元的全局合同与共享状态权威，已就绪单元可先行实施，其余部分继续细化；未决项只阻塞真正依赖它的单元。

## 2. 吞吐检查点（非平凡分派前必答 4 问）

动工拆解或派发子代理前，必须显式回答四问（单文件/单人闭合也须保留条目并写 `n/a: <原因>`，不得省略）：

1. **先决阻塞（Blocking first steps）**：哪些基础类型、共享合同或验证门禁必须先落地？
2. **独立工作流（Independent workstreams）**：哪些文件、模块或层在输入与验证上真正解耦、可并行？
3. **共享可变状态（Shared mutable state）**：默认拆目标避免共享写；若必须共用，谁是唯一写入者与集成者？
4. **最小安全拆分（Smallest safe decomposition）**：单执行者闭合是否反而更稳，为什么？

## 3. 实施、集成与验证

1. **执行或委派**：独立单元可使用 `assets/implementation-task-template.md` 经 `spawn-subagent`（默认中性角色）按复杂度委派全新干净上下文子代理；任务里明确文件边界、先定好的数据形状与成功标准。实现形态存在多种实质合理方案时，可用 `dev-arena` 生成对比。
2. **条件 TDD**：有廉价稳定本地测试路径或关键新行为时，按 `dev-tdd` 先锁定行为回归。
3. **真实验证**：用 `dev-verify` 在真实消费者表面核验正常、关键失败与恢复路径（含接受界面的等价对照），不以编译通过或子代理自述当验收。
4. **独立审查**：按风险或请求调用 `dev-review`（高危并发/鉴权/持久化/共享核心契约改动自动升级对抗实测）。
5. **共享基础放行**：底层共享变更向多个消费者推广前，先用至少 1 个真实代表消费者贯通正常与关键失败路径，确认无阻塞再放行依赖单元。

## 4. 按根因回环

实现违约直接修并重验失效证据；同类结构摩擦反复出现回到 `dev-architect` 重看边界；工程事实推翻产品前提则交回具体取舍。最终从原比较基线核对累计 diff 与跨单元完整行为。

**回复**：做了什么、关键设计取舍与原因、4 项吞吐检查结论、实测证据（含命令与关键输出）及剩余未决项。
