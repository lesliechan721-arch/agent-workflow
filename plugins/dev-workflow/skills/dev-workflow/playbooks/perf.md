# 单次性能排查与优化（Perf）

**核心纪律：每一处改动都绑定真实测量，绝不靠读源码臆测瓶颈或宣布提速。** 需要多轮持续寻优改走 `playbooks/hillclimb.md`。

## 1. 先抓并验真基线

在代表负载上抓取基线数据，并用 `dev-benchmark` 完整核验基线（限制因素、生产调优对齐、错误/工作量计数、Amdahl 上限与波动极差）。只要求性能分析时，交付瓶颈证据与改善上限后即停。

## 2. 按成本从低到高过七条性能口诀

基于实测 profile 定位真实热点，严格按以下顺序构思候选（越靠前收益往往越大、改动越干净；**靠前口诀已达目标立刻停止**）：

1. **Don't do it**：直接删掉结果没人消费的无用工作，而不是把它算快。
2. **Do it, but don't do it again**：安全复用/缓存结果（明确失效与内存上限）。
3. **Do it less**：减少数据规模、频率或遍历范围（不改比较合同）。
4. **Do it later**：延迟到真正需要时执行（懒加载/惰性求值）。
5. **Do it when they're not looking**：移出用户关键路径到异步/预计算（必须确认后台实际完成）。
6. **Do it concurrently**：对真正无共享争用的部分并行（警惕锁争用、限流与尾延迟恶化）。
7. **Do it cheaper**：换更优算法、数据结构或底层实现。

## 3. 实施、同口径复测与归因

1. 一次只落一个机制明确的候选；跨边界改法先过 `dev-architect`。
2. 用与基线完全相同的命令和条件重测，过 `dev-benchmark` 七问核对：若差值未超波动极差、错误数上升、完成量减少或端到端占比无意义，**立刻回滚该候选**，保留失败记录。
3. 保留有效改动后跑 `dev-verify` 核验功能无回归；涉及高危并发/缓存失效或核心路径改动时用 `dev-review` 审查。

**回复**：基线与优化后数字（含轮数、中位数、极差）、实测限制因素、采用的口诀与改动，以及测量产物路径。
