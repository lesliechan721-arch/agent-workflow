# 持续迭代优化（Hillclimb）

用于针对单一可测量目标的有限预算科学寻优。**铁律：一次只改一个假设、测一次、赢过噪声且门禁全绿才保留，否则完整回滚；严禁叠加未验证改动。**

## 1. 定负载、指标与硬停止条件

先追踪架构并确定能复现用户痛点的真实负载维度（数据规模、并发、历史状态）。找不到复现负载就先修复现，不要盲目爬山。固定：单一指标、改善方向、质量回归门禁、有限预算（候选数/耗时上限），以及可检查的停止条件（若用户给出了最低尝试轮数，防止早期侥幸小涨提前收手）。

## 2. 检验敏感性后冻结 Harness

1. 构建或复用一条可一键复跑的测量命令（输出目标指标、**错误计数**与**实际完成工作量**，采用多轮中位数而非单次跑分）。
2. **敏感性验真**：用一组明显不同难度的对照负载试跑，确认 harness 能拉开差距且反映真实痛点；再过 `dev-benchmark` 七问验真。
3. **冻结 harness**：记录基线指标和一次全绿的回归门禁；此后寻优期间不得悄悄修改 harness 或放宽门禁（若发现 harness 本身有错，单列修正并重取基线，计入原预算）。

## 3. 初始化并严守追加式决策日志

在工作目录建立 gitignore 的 `decisions.tsv`，每次迭代都通过随包脚本维护（`init` 与首次 `append` 自动写入表头）：

```sh
node scripts/decision-log.mjs init <logfile>
node scripts/decision-log.mjs tail <logfile> --n 10
node scripts/decision-log.mjs append <logfile> --phase hillclimb --decision "<假设与改动>" --why "<机制>" --evidence "<命令或路径>" --result "kept|reverted: <before> -> <after>"
```

- **每次动手前必先读最后几行日志**，杜绝 3 轮后失忆重复试失败思路。
- 只追加、不改写历史行；失败与回滚同样记入日志。

## 4. 假设循环与平台期破局

1. 每个假设必须基于架构机理写具体（如“把 X 移出启动热路径”而非“试着缓存一下”）；性能类按 `playbooks/perf.md` 的 7 条口诀由廉价到昂贵排序。
2. 独立假设可经 `spawn-subagent`（默认中性角色）交全新子代理在各自隔离工作区尝试，使用 `assets/implementation-task-template.md` 传入目标、边界与工程底线；执行后用冻结 harness 测量并跑回归门禁。
3. **保留条件**：收益明确超出波动区间 **且** 回归门禁全绿 → 保留并记 `kept`；否则**完整回滚自有改动**并记 `reverted`（不留“可能有点用”的微调）。
4. **撞平台期破局**：**连续 3 次被拒**时禁止继续同类微调——必须切换假设大类、组合两个接近成功的方案、重读源码找被忽略的瓶颈，或尝试**指标持平但删减复杂度的简化**（持平简化直接保留）。正确性与简洁度始终高于微小数字波动。

## 5. 收尾复核

满足停止条件、预算耗尽或剩余想法收益不值代价时停止；对最终保留组合跑完整场景与回归门禁，高危变动用 `dev-review` 核查。

**回复**：目标指标、基线到最终值及百分比变化、总轮数（保留 vs 回滚）、每条保留改动一行摘要、`decisions.tsv` 路径、停止原因，以及若继续投入最值得试的下一个假设。
