# Dev Workflow

你是可选的开发流程编排器。专业 Skill 可以独立调用；只有用户需要风险分级、跨阶段推进或恢复已有任务时才使用本 Skill。

## 1. 选择最低足够保障

- **Fast**：请求明确、范围小、可逆、预计一个上下文完成，并且有可靠验证。
- **Standard**：中等范围、存在材料决定、需要 Prototype、跨会话、正式批准或 Review。
- **Assured**：安全、权限、支付、持久数据、迁移、生产副作用、不可逆操作、多 Agent 或缺少可靠测试。

Assured 沿用 Standard 的能力，但使用项目已有工具增加持久证据、回滚点、隔离、授权和独立最终 Review。不要把这些保障重写成自然语言状态机。

## 2. 确定任务目录

优先使用用户路径或仓库约定。Standard 和 Assured 都没有约定时使用：

```text
docs/dev/<task-slug>/
```

文件按需出现。Fast 路径不创建流程文档。

## 3. 从最早未完成阶段继续

根据用户目标和已有 artifact 选择一个当前能力：

- 仍需用户取舍 → 决策访谈。
- 必须通过体验、实验或测量取得证据 → 决策原型。
- 决定稳定但没有 Spec，或 Spec 需要修订 → `dev-spec`。
- Spec 尚未正式审查 → `dev-review-spec`。
- Spec 审查通过但尚未批准 → 请求用户明确批准。
- 请求已明确、走 Fast，或 Spec 已批准 → `dev-implement`。
- 已有完成实现、diff、branch 或 PR → `dev-review-code`。

专业 Skill 返回的“需要决定”“需要证据”“需要修订”“可以继续”只用于选择阶段。不要在入口维护更细的状态表或复制专业 Skill 的内部规则。

## 4. 人类检查点

只在材料决定、Prototype 反馈、Spec 批准和高风险动作授权处暂停。用户原始请求已经授权后续非人类阶段时，可以在检查点之间继续推进。

## 输出

```text
保障等级：Fast / Standard / Assured
当前阶段：<阶段>
任务目录：<路径 / 无>
下一能力：<能力>
原因：<关键缺口或风险>
人类检查点：<无 / 材料决定 / 原型反馈 / Spec 批准 / 高风险授权>
```

选择能力后加载并执行它，而不是只返回能力清单。
