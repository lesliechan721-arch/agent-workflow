# Dev Workflow

负责当前开发任务的阶段推进、共识依据、资料位置和用户检查点。专业能力按本次分工完成各自结果。

## 阶段主线

| 阶段 | 工作与主要产物 | 推进条件 |
| --- | --- | --- |
| **需求对齐** | 调查项目事实，确认结果、范围、条件、重要取舍和实施自由；保存需要交接的决定、原型与接受范围 | 当前交付所依赖的材料问题已获实际确认或明确委托；开放问题的影响可辨 |
| **形成并确认规格** | 用 `dev-spec` 综合当前规范及必要附件，`dev-review-spec` 独立核对来源、可实施性和人审完整性；呈现完整审阅路径与实质变化 | 重要决定和约束保真，必要审查覆盖充分，用户已确认适用内容与版本 |
| **准备实施** | 交给 `dev-build` 调查实施上下文，按需使用 `dev-breakdown` 形成下一批 Ticket、真实依赖、验证方式与保存基线 | 一个合适实施者仅凭任务、可达资料和项目事实就能开始；所选保存方式已处理 |
| **实施与集成** | 由 Build 直接执行或委派子代理，接纳真实结果、集成验证，并处理实际 milestone 的保存与审查 | 当前交付实现完成，相应验证与依赖条件满足 |
| **交付核验** | Build 对原始任务范围组织完整 Code Review、有界修复及复审，交付结果、证据和限制 | 当前完整结果有充分独立覆盖，实质问题已关闭；外部动作仍按授权执行 |

阶段是结果与交接顺序，不要求一阶段一文件。已有有效结果直接复用；Build 唯一协调后三阶段及代码修复，Workflow 采用其已有有效最终审查结果。

## 开始与恢复

读取原始请求、当前确认、规范、任务、项目事实及证据，说明当前阶段、依据、缺口和下一步。按最早缺失或已失效的必要结果继续；文件存在和模型自述完成不能代替实际确认与证据。用户只要求某一项工作时，完成该范围即结束。

局部选择直接询问；有界访谈使用 `decision-grill`；必须体验或实验的问题使用 `decision-prototype`；多个关联决定或问答与证据往返使用 `decision-shape`。事实自行查明，需用户取舍时说明背景、推荐与后果，等待真实回答再开展依赖该决定的正式产品修改。

需要持久资料、跨上下文交接、长原型迭代或保存点时读取 [任务资料与交接](references/task-artifacts.md)，统一当前任务位置、审阅入口和可访问来源。

## 小任务路径

范围局部、关键行为与验证能在当前有效实施上下文完成，且没有实际的持久交接或正式规格需求时，可在对话中对齐并表达完整要求，以一个自然工作项进入 Build。默认不生成流程文档；源码、测试或临时原型仍可产生。最终验证、独立代码审查和实际风险授权继续适用。

需要长期恢复、重要决定的正式审阅、多个实施上下文或持久风险证据时，先保存已确认内容，再从对应阶段继续。风险直接对应权限、隔离、备份、验证与回滚措施；代码量小不减少这些要求。

## 决定变化与有限修订

任一阶段的新事实使已定依据失效或产生材料选择时，暂停受影响修改和派发，说明原决定、新证据、后果及选项，重新对齐相关主题。取得结论后更新受影响规范、任务和验收，完成相应审查与确认；相关执行者收到当前依据后恢复。其余有效决定复用，已有修复额度和人类停止点保持。

已有实质 Spec 问题且修订在当前授权内时，读取 [规格修订](references/review-repair.md)，由当前协调者按证据决定继续或暂停。规格质量判断、用户批准和 Git 保存分别成立。完整交付授权涵盖合理本地实施与检查，材料选择、显著成本和外部副作用遵循各自授权。
