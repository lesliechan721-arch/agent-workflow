# Dev Workflow

负责完整交付的范围、阶段衔接和用户检查点，按实际成果恢复，不重复已有有效工作。

## 阶段与交接

| 阶段 | 责任与成果 | 继续条件 |
| --- | --- | --- |
| 需求对齐 | `dev-design` 使用 `decision-shape` 补足共识，已确认的领域知识按需由 `project-context` 维护 | 当前目标、材料决定、条件和委托有实际依据；充分有效的共识可直接复用 |
| 形成并确认规格 | `dev-design` 使用 `dev-spec` 原位修订项目规范，完成必要的独立审查和用户确认 | 当前规范完整可读，必要设计可达，确认覆盖实际版本与范围 |
| 准备实施 | `dev-build` 从当前规范与项目事实准备下一批可执行工作，按需使用 `dev-breakdown` | 新实施者能读到真实规范版本、任务和验收，实施授权明确 |
| 实施与集成 | Build直接实施或委派子代理，验证集成结果和实际milestone | 当前承诺范围完成，相关验证和独立阶段审查充分 |
| 交付核验 | 同一Build组织完整Code Review、有界修复和交付 | 完整结果有两份独立判断和实际验证，实质问题关闭 |

项目资料直接维护当前目标和长期知识；过程资料按需保存在本地 `.dev-workflows/<task>/`。需要落盘、恢复或交接时读取 [本地任务与项目资料](references/local-workspace.md)。阶段不要求一阶段一文件。

## 开始与推进

1. 读取当前请求、相关项目规范与决定、实际代码和本地任务。明确本次是完整交付、设计还是局部工作；用户只请求某部分时，在该范围结束。
2. 有材料缺口、冲突或需要形成正式设计时使用 `dev-design`。它先通过Shape取得真实回答或委托，再更新适用项目资料。当前请求已经明确的内容直接作为依据，文件自称已批准或模型推断不能补造确认。
3. 设计已有充分依据且用户已授权实施时交给 `dev-build`。传递当前目标、规范入口、真实确认范围和必要本地任务位置；设计完成或用户认可设计本身不新增实施授权。
4. 采用Build的实际最终判断，不再次启动同范围审查。完成后按用户授权处理提交与外部交付；开发未完成默认不推送，过程资料始终留在本地。

## 小任务与具体风险

范围局部、当前共识和验收能留在有效上下文时，直接复用请求并进入Build，通常无需完整Spec或任务目录。小任务仍有材料选择时，由Design使用Shape短问答完成即可。验证、独立最终核验及必要风险授权保留。

风险按实际行为落实隔离、备份、权限和恢复条件，代码量不能代替这些条件。资料或交接需要增加时，先保存已确认内容再继续。

## 新证据与恢复

新事实影响已定行为、接受设计或风险时，暂停相关写入和派发，将受影响主题交回Design对齐和修订；未受影响任务可继续。取得当前确认并同步规范、Ticket与在途执行者后恢复。

原始任务基线、未关闭问题、已有修复预算和用户停止点跨会话保持。取消任务时处理本次未完成的项目资料变更，保护原有用户工作；本地文件不因任务结束自动删除。
