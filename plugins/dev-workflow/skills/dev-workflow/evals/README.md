# Dev Workflow Eval

本目录保留与当前手动工作流入口、产品对齐和直接实施边界对应的回归。按实际 suite 与 profile 准备用例，不复用旧工作流的固定步骤、角色或历史来源绑定。

| Suite | 评价目标 |
| --- | --- |
| `trigger` | 显式调用与普通请求的区别；自然语言的设计、审查、简单实施请求不隐式启动手动入口 |
| `independent-delivery-trigger` | 用户显式选择工作流和独立小任务的边界 |
| `independent-delivery-behavior` | 沿用当前任务位置；短任务使用实际用户回答并在要求的位置停止 |
| `continuous-alignment` | 同一请求的两种真实用户答复、已明确要求、明确委托、无依据的规格确认标记、新事实导致的受影响产品选择与规范修订 |

## 运行与判据

`project-default` 使用 Codex project profile 及被测插件的实际依赖闭包；常规子代理基线为宿主原生。各 suite 的 `strict` 参与列表仅声明当前可用能力，不要求固定加载组合或独立角色。触发只观测被测入口是否加载，不评价整项任务是否完成。

Conversation 用例采用内置 provider。注入的用户答复必须通过实际交互到达；评分应核对问题、答复、修改的时间顺序，而不是只看最终自述。需要写入时明确允许路径和 artifact；其存在性不代替语义。只读或等待用户决定时使用可写环境与空允许列表，借助工具轨迹核对主动不写的边界。

导出场景核对最终实现内容及实际验证命令和输出，既有列表筛选测试通过不证明导出功能完成。内置 provider 未独立执行导出函数或验证子代理角色；涉及运行语义和独立性的结论以实得证据为准，不能由文档、角色自称或测试名称推断。

以上为作者定义的待评测用例，不表示模型已经通过。正式运行前须重新 prepare 并取得独立 EvalAudit。参与能力、fixture、判据或 provider 变化后，不将旧评测结果当作当前通过证据。
