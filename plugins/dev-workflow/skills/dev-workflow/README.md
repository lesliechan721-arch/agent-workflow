# 开发工作流

从当前共识、风险和已有工件判断开发任务的下一步。适合启动或恢复跨阶段任务；只需实现、分解或审查时，可以直接使用对应 Skill。

小任务可以先澄清一个选择，再保持 Fast 完成实施、验证和正式代码审查，默认不创建流程文档。需要正式规格、批准或跨会话交接时，使用 Standard；高风险任务采用 Assured，并落实项目要求的保障。

普通局部问题直接提问，有界访谈使用 decision-grill，独立体验问题使用 decision-prototype；复杂塑形或持续维护共识使用 decision-shape。已有确认决定直接复用。

Standard/Assured 的 Spec 经独立审查，必要覆盖充分且影响批准的问题已关闭后，请用户批准当前规格与纳入的设计。获准修订时由当前协调者在预算内组织 dev-spec 修订与独立复审，新授权未指定次数时默认最多三轮；根据证据继续或提前暂停。审查通过仍须用户批准。可实施后由 dev-build 负责实施、集成和代码审查闭环。遇到材料决定、批准或修复停止点时，会说明缺口并交还用户；恢复任务不会刷新修复预算。

```text
使用 dev-workflow 继续这个任务，依据现有 Spec、工作记录和 Review 判断下一步。
```

首次转交会保存或迭代产物的能力前，先确定当前任务位置，并让原型、规格、Ticket 和审查沿用。优先使用用户给定位置、当前任务位置或仓库约定；纯对话澄清不预建目录。实现、子代理、Git 和外部动作遵守现有授权。执行说明见 [SKILL.md](SKILL.md)。

## 当前共识

新需求先读取已确认要求与委托边界，选择会影响用户结果时取得实际答复；已有充分依据则继续。新证据影响旧决定时只重新对齐受影响部分，同步规范、任务与在途执行者后恢复。局部工程自由和材料决定分开，用户不必点名 decision-* 才能触发必要对齐。
