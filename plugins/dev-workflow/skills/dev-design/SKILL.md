# Dev Design

把当前需求推进到可理解、可审核、可交接的设计。当前代理负责用户交互和进度，专业Skill各自完成对应结果；这里不安排产品实施。

## 恢复目标与位置

读取请求、项目已有领域词汇、相关决定与规范、当前代码及实际确认。确认本次设计范围与文档编辑权限。先复用已有等价文档；没有对应规范时再采用项目约定或 `docs/design/<主题>.md`。

需要持久恢复、长原型或资料交接时读取 [本地任务与项目资料](references/local-workspace.md)。沿用现有任务位置，默认 `.dev-workflows/<task>/`。记录尚未归位的决定、开放问题和确认依据，已进入项目规范的内容用链接引用；需要新建记录时可用 [任务入口模板](assets/task-template.md)。

## 形成当前设计

1. 当前范围的材料决定不充分或出现冲突时，必须使用 `decision-shape` 对齐；已有有效共识直接复用。Shape选择短问答、Grill或Prototype，重要后果在用户答复前可见。事实自行调查，产品选择依据实际回答或明确委托。
2. 项目术语发生歧义、形成长期重要决定或需维护相应知识时，使用 `project-context`。一批决定明确后即可在授权范围内写入其长期位置，无需等全部设计结束；一般行为要求由规范承载，完整问答留在当前过程。
3. 需要可实施设计时，使用 `dev-spec` 综合或修订对应项目规范与必要设计附件。原位维护完整目标，保留条件、例外、精确技术语义和实施自由；当前代码与目标之间的未完成部分在本地任务说明。实际命令、性能和兼容结论以验证事实为准。
4. 按本次范围使用 `dev-review-spec` 取得独立判断；重要ADR、接受设计和相应未修改合同都作为必要依据。已有实质问题且修订获准时读取 [有界规格修订](references/review-repair.md)。修订预算归当前设计协调者，不交给审查者。
5. 向用户呈现当前完整阅读入口、实质变化和风险，取得适用确认。接受的视觉或逻辑若将长期约束产品，保留在稳定项目设计位置，明确版本、范围和演示边界；长期规范不以临时会话或本地过程文件作为唯一依据。

## 结束与再次使用

用户要求仅讨论或局部设计时，在该范围交付；不为凑流程生成所有文档。正式设计完成意味着当前材料要求可从项目规范与必要证据恢复、相关审查充分且确认真实，不意味着实现已完成。

交付规范与知识的实际修改位置、当前确认范围、未决事项和可恢复的下一步。在设计边界结束；外层已有实施授权可接续Build，独立设计请求需后续实施请求。提交和推送分别需要适用授权。

新证据只重开受影响决定。资料和任务同步后再交回实施，原修复预算和停止点保持。取消或改向时核对本次项目文件差异，处理不再有效的目标，保留无关工作和仍有效的决定。
