# Dev Design

形成有依据的当前设计，不启动产品实施。

## 先建立当前共识

读取当前请求、相关项目事实与实际确认。新功能或行为变更先使用 `decision-shape` 建立当前共识。当前请求或有效确认已经明确目标、关键行为、边界与验收，且没有新的材料冲突时可直接复用；用简短说明呈现所用依据及实施自由。模型提出的合理方案仍是提案。

对齐结果应让用户看见：哪些结果已确定、哪些取舍仍会改变当前方案、哪些选择已明确委托。取得真实回答或明确委托后，再细化依赖这些取舍的完整规范。获准的调查、原型和候选稿可帮助用户决定，按当前问题提供足够证据并保留未定性质。

## 选择足够的交付

| 当前需要 | 设计结果 |
| --- | --- |
| 必要对齐、边界与验收能留在有效上下文，没有持久批准或交接需要 | 在对话中明确当前结果与实施自由；无需单独创建 Spec 或流程文件 |
| 多决定、长原型、正式规格或跨上下文实施 | 使用 `dev-spec` 形成完整规格与可达附件，再以 `dev-review-spec` 独立核对并取得适用确认 |

规模不免除实际风险、权限或恢复要求。需要落盘或转交原型前读取 [工作目录](references/local-workspace.md)，沿用当前位置。普通任务规格留在本地；明确指定的公共合同在其位置维护。

## 设计与恢复

- 新领域术语、非显然的重要决定需要长期维护时，使用 `project-context`；普通任务行为由当前规格及适用合同承载。
- 长对齐或原型前，在已授权的 Spec 草稿或相应原型 brief/verdict 中保存已确认内容、来源及开放问题。草稿可恢复但不表示批准；正式交付前核对其当前依据。
- 已有实质规格问题且修订在授权内时，读取 [规格修订](references/review-repair.md)。沿用本次设计授权与累计预算。
- 复杂取舍或长稿需要用户理解、定位并反馈时，使用 `explain-for-review` 呈现当前材料；提供读者要完成的判断、来源状态、完整依据和当前输出位置。简单情况直接清楚说明。视图只帮助理解，材料选择仍由当前对齐方法取得真实答复。
- 向用户呈现需其判断的完整结果、风险和实质变化；采用实际答复或明确委托。已经确认的同一含义直接复用，新增材料解释再核对。正式规格的必要独立审查与批准分别成立。来源改变后，先核对用于本次决定的视图仍对应当前内容。

交付当前设计及可访问位置、确认范围、开放问题和下一步。仅设计请求到此结束，当前完整规格与必要接受证据保留可达。

新证据只重开受影响主题；更新相关资料后交回调用者，已有预算与停止点保持。取消或改向按实际授权处理本次不再有效的项目文件变更，保护无关工作；提交、推送和资料清理分别需要授权。
