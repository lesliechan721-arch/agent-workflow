# Dev Design

连接需求对齐、规格与用户确认，不复制下游方法，不启动产品实施。

## 恢复或取得有效决定

读取原始请求、补充要求、已有设计、项目约束与授权。核对目标、关键行为、边界与验收是否完整，重要选择是否有用户要求、实际确认、适用合同或明确委托支持。无冲突或新选择的有效范围直接复用，说明依据与实施自由；草稿完整或自称批准不等于共识成立，部分明确不代表全部确认。

接收实施缺口或交付后变更时，先读 [任务变化与后续工作](references/task-changes.md)，依据实际完成状态与历史基线确定本次修订对象。

需要对齐或新证据改变重要选择时，使用 `decision-shape`，交付完整请求、可达来源、当前位置、已定内容和开放问题。整体覆盖、问答、原型与知识维护由 Shape 组织；保留其决定、接受证据、知识入口和缺口，不压缩成丢失条件的摘要。

落盘或转交原型前读取 [工作目录](references/local-workspace.md)，沿用位置并传递写入边界。长对齐、原型或跨上下文前，在授权范围内把决定、来源与开放问题保存到现有草稿或原型记录。未决状态保持，不推进依赖未决答案的正式规范或实施。

## 选择足够的交付

| 当前需要 | 设计结果 |
| --- | --- |
| 当前结果、边界与验收可留在有效上下文，没有持久批准或交接需要 | 在对话中交付设计与实施自由，不创建额外流程文件 |
| 多决定、长原型、正式规格或跨上下文实施 | 使用 `dev-spec` 形成可直接人审的完整规格，再组织 `dev-review-spec` 独立核对 |

向 Spec 提供原始要求、完整决定及确认／委托边界、开放问题、接受原型、知识与项目合同入口，以及读者任务和输出位置。Spec 负责完整规范及其人审呈现，Review 负责独立判断，Design 负责授权、修订协调和用户确认。显式正式规格请求不因任务小而降为口头总结。

## 审阅、修订与交付

采用 Spec 提供的主文与必要审阅呈现，不在规格完成后另补一套阅读版。尚未形成规格的复杂候选或跨主题取舍需要解释时，可直接使用 `explain-for-review`，提供读者任务、完整来源、状态与输出位置。解释反馈中的新选择交回 Shape，视图不替来源定案。

已有实质问题且修订获准时使用 [规格修订](references/review-repair.md)，沿用累计预算。复审范围与执行者由 Review 按影响和证据决定，不默认每轮重新全面审查；缺少独立能力时披露限制，不以作者自检替代。

交付当前完整入口、必要附件与接受证据、实际审查覆盖、确认范围、实质变化、风险、自主空间和开放问题。复用含义未变的有效确认；正式规格按适用要求取得批准，阅读或下载不构成批准。仅设计请求到此结束。

新证据只重开受影响主题，同步相关规格与已生成视图后交回调用者；预算与停止点保持。取消或改向只按授权处理本次失效变更，保护无关工作；提交、推送和清理分别需要授权。
