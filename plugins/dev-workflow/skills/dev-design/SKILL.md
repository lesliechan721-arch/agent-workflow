# Dev Design

负责从需求对齐到设计交付的协调，不复制对齐方法，不启动产品实施。

## 交给 Shape 对齐

读取本次原始请求、补充要求、已有设计、项目约束与授权。需求尚需对齐，或行为变化引入新的重要选择时，使用 `decision-shape`，交付完整请求与可达来源、当前设计位置、已确认内容和未定事项，不先压缩成几个功能名。整体需求覆盖、问答、原型选择与知识维护由 Shape 组织。

已有有效设计或当前请求本身已完整说明目标、关键行为、边界与验收，且无冲突或新选择时，直接复用并说明依据与实施自由。只明确一部分，不代表其余要求已确认。Shape 返回的决定、证据、知识位置和缺口一并保留；会改变方案的未决内容先交回 Shape，不替用户补成默认产品要求。

需要落盘或转交原型前读取 [工作目录](references/local-workspace.md)，沿用当前位置并把写入边界交给 Shape。长对齐的已确认内容与开放问题保存在获准的现有草稿或相应原型记录中；草稿可以恢复，不表示批准。

## 选择足够的交付

| 当前需要 | 设计结果 |
| --- | --- |
| 当前结果、边界与验收可留在有效上下文，没有持久批准或交接需要 | 在对话中交付设计与实施自由，不创建额外流程文件 |
| 多决定、长原型、正式规格或跨上下文实施 | 使用 `dev-spec` 形成完整规格与可达附件，再以 `dev-review-spec` 独立核对并取得适用确认 |

向 Spec 提供原始要求、完整当前决定及确认／委托边界、开放问题、接受原型及边界、知识与项目合同的实际入口。规格编写者核对来源覆盖，审查者独立核对完整规范；不要只交一个丢失条件的摘要。普通任务规格仅本地保存，明确指定的公共合同在原位置维护。显式正式规格请求不因任务小而降为口头总结。

## 审阅、修订与交付

复杂候选或长稿需要用户理解、定位与反馈时，使用 `explain-for-review`，提供读者任务、当前来源与状态、完整入口和输出位置；简单说明直接呈现。视图用于理解，新的需求选择仍交 Shape。获准的候选稿可用于帮助决定，未定状态保持，不先细化依赖未决答案的正式规范。

独立审查与用户批准分别成立，缺少独立能力时说明限制。已有实质规格问题且修订获准时读取 [规格修订](references/review-repair.md)，沿用累计预算；新问题改变需求、领域含义或接受设计时，只把受影响主题交回 Shape，再同步当前规格和审阅视图。

交付当前完整设计入口、必要附件与接受证据、确认范围、实质变化、风险、自主空间和开放问题。已确认且含义未变的内容直接复用；正式规格按适用要求取得批准，视图阅读和下载不构成批准。仅设计请求到此结束。

新证据只重开受影响主题；更新相关资料后交回调用者，已有预算与停止点保持。取消或改向按实际授权处理本次不再有效的项目文件变更，保护无关工作；提交、推送和资料清理分别需要授权。
