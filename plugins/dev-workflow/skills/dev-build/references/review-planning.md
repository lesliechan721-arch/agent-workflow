# 里程碑审查与推进

选定实施 milestone，或需先核对公共基础、重要风险、代表性设计与集成结果再展开下游时读取。这里的阶段是当前里程碑范围，并不等同于完整开发流程的每个阶段。

## 选定范围

协调者说明本阶段交付结果、适用 Spec 与设计、阶段起点、验收和依赖它的后续工作。共享基础解锁多个下游、风险/迁移转换点、设计模式即将推广和高返工代价的集成结果可形成 milestone。普通局部任务只做相称验证。

选定milestone后，记录本地任务中的阶段范围、基线和依赖。审查对象可为已有commit或稳定工作区；有实际保存需要时才采用 [Checkpoint与提交](checkpoints.md)。

## 当前阶段闭环

1. 先确认阶段要求仍由当前有效决定支持，再集成并运行验收相关验证。新材料问题按 Build 的对齐要求处理。通过后明确本轮实际版本、当前diff和证据，协调相同范围的并发写入；若使用已有授权的checkpoint则采用其真实结果，否则直接审查稳定工作区。
2. 使用 dev-review-code 审查该阶段的完整累计结果及必要依赖。提供固定版本、原始依据、已接受设计和验证证据。后续尚未承诺交付的功能明确为本次范围外。
3. 有实质问题且修复在授权内时，按 [Review 修复](review-repair.md) 处理。每批修复验证后重新固定实际审查范围与内容，再完整复审当前阶段。同一次复审既结束该批修复，也判断阶段能否继续。
4. 阶段验收、必要独立覆盖和问题关闭满足后，解锁依赖；未创建commit本身不是阻塞。存在问题、证据缺口或用户明确要求却尚未满足的额外条件时，暂停相关依赖；真正独立且风险不受影响的工作可在原授权内继续。

## 整体交付

决定变更使阶段依据失效时，按更新后的验收重新检查受影响结果；先前保存的提交仍是历史事实，既有通过结论不覆盖新要求。最终从任务原始基线审查完整集成结果，阶段通过只证明其实际范围。记录实际版本、报告与验证位置；报告结果由协调者用于后续判断，审查能力本身不授予提交、修复或发布权限。
