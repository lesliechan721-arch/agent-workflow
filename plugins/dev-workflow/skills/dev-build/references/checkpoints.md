# Checkpoint 与历史

有持久资料需要实施交接、选定 milestone，或用户要求保存/整理历史时读取。当前协调者选择保存点，Git 能力执行实际提交。

## 保存方式与授权

实施前的持久基线与 milestone 的已验证集成结果默认形成本地 checkpoint。第一次需要保存时，检查授权是否覆盖本次资料或代码；缺少时主动说明范围、用途及“仅本地提交”，请求覆盖本任务同类保存点的一次授权。原有较窄授权继续有效，确认后无需逐阶段重复询问。

明确不提交的用户要求或项目约束继续有效。采用已明确选择的无提交路径，记录未创建 Git 保存点、当前基线和可复核证据，保留阶段验证与审查。尚未取得授权或明确选择时，等待该决定；无法使用 Git 的环境应说明限制并确认可用的保存方式。

## 实施前基线

首次产品修改前，有持久规范与任务需要交接时，将已确认Spec、规范性附件/设计引用、批准依据和首批可派发任务作为同一基线。只准备当前可执行任务；已有等价保存直接复用。外部权威资料记录可访问版本，明确不能归档的限制。

资料质量检查包括：决定及限定保真、引用可达、文件一致、任务可派发、确认范围清楚和敏感内容隔离。它不同于代码测试，也不要求创建尚未产生的实施证据。资料到实施存在变化时，基线对应实际将使用的版本；材料变化重新对齐及确认。

## 创建并核对

- 使用现有 Git 提交能力，在相关验证通过、结果连贯且提交范围可精确隔离时创建 checkpoint。精确暂存本任务变更并正常运行 hooks，保留无关的已有修改。
- 记录实际 commit、阶段范围和验证结果。hooks、生成步骤或并行变化改变了已验证内容时，重新核对变化并补相称验证，再把实际版本交给审查。提交失败先报告 HEAD、index 与工作区事实。
- 修复后的已验证结果追加提交，再审当前累计阶段范围。已有提交已经完整覆盖本次结果且无新变更时复用它；审查报告和进度更新不要求产生另一个空提交，也不要求引用尚未存在的自身 hash。
- WIP 仅在明确授权保存未完成工作时使用，并披露失败或未验证状态。它不作为已验证 milestone。

本地提交权限不包含 push、历史重写、分支删除、部署或回滚用户数据。checkpoint 保存版本，独立审查、备份与生产回滚分别负责各自保障。

## 最终历史

默认追加提交。用户/项目要求整理时，优先在最终验证和审查前完成，也可使用平台已有 squash merge。

整理后核对文件内容、Spec、设计依据与目标基线。仅提交身份变化且审查上下文可证明一致时，更新引用并执行项目要求的检查；内容或集成影响变化时重新验证和审查相关范围，无法确认一致时保守复核。长期审计按组织政策保留明确引用或外部记录。
