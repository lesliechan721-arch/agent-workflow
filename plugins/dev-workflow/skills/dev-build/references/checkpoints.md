# Checkpoint与提交

需要可回退的本地版本、用户要求提交或整理历史时读取。过程落盘、独立审查和Git提交分别提供不同保障。

## 默认与授权

本地 `.dev-workflows/<task>/` 足够保存当前任务进度，不作为Git提交内容。设计和任务准备完成可直接实施；milestone按其实际验证与审查条件推进，不强制创建commit。

当前集成结果有显著回退价值，或用户明确要求时，协调者说明拟保存的项目文档/代码范围。已有适用本地提交授权则执行，否则请求该动作授权；用户只允许实施或设计不等于允许commit。阶段默认没有提交，不需要先请求一次“无提交豁免”。

## 执行与检查

采用项目已有Git能力，精确暂存本任务拟交付的文档、代码和测试，核对工作区及索引中的其他用户修改。过程目录、临时反馈、运行日志和凭据保持本地，不使用force-add纳入它们。

相关验证通过且结果连贯时可创建checkpoint，正常运行hooks；hooks改变内容时补相称验证。明确要求保存WIP时说明未完成/失败状态，不能当作已审查通过。失败报告实际HEAD、索引与工作区状态；已有等价提交复用，不造空提交。

当前审查可以针对已有commit或稳定工作区与明确diff。提交本身不代替Review；没有commit也不能假称快照稳定，审查期间协调相关写入，结束时核对目标未失效。

## 最终交付

需求完成后，按用户授权提交实现、测试及本次确需长期维护的项目资料。本地Spec、Ticket和过程证据继续留在本地。设计已确认、代码已完成和已发布分别有依据；默认完成前不推送，完成后也需实际push授权。

本地commit不授权历史重写、force push、分支删除、部署或数据回滚。需要整理历史时按项目政策与明确授权执行，优先在最终验证和Review前完成；仅身份改变且内容/范围可证明一致时更新引用，否则复核受影响结果。保留原始任务审查基线。
