# 委派子代理实施

多个工作项有独立交接价值、单项局部实施负担会挤占主线协调，或用户要求子代理时读取。

## 准备与选择

复用已有 ticket/issue，必要时使用 dev-breakdown 补足结果、真实依赖、资料入口、接口与设计边界、验收和允许写入范围。代码事实先调查；新行为或已有决定失效时，由当前用户协调者取得答复或明确委托，再派发依赖它的工作。任务正文与验收保持可重派，状态附着其后。

按歧义、依赖耦合、验证难度和遗漏代价选择足以可靠完成的子代理能力。较弱子代理获得必要领域事实与实例；任务仍含大量跨域判断时，调整切分或执行能力。细小机械编辑可合成一个自然工作项。

## 委派与接纳

1. 工具与授权可用时，默认顺序委派子代理完成当前已就绪工作项。向子代理提供可访问的任务、来源和验证重点，让它使用 dev-implement；当前协调者维护共享工作索引。
2. 只有任务、公共接口、写入与验证环境相互独立且有集成收益时并行。遵循项目现有隔离策略；同时修改共享接口、共用有状态测试环境或依赖尚未稳定时串行。
3. 子代理执行当前范围并返回真实变更和验证。发现新事实与当前需求不符、需要新的材料选择时，先暂停受影响修改，报告实际证据、原要求和后果；用户问题由当前协调者统一处理。接纳时核对真实 diff、当前决定、Ticket 验收及设计证据，集成后执行组合验证。共享布局或接口在推广前通过 milestone 检查。
4. 按平台子代理工具确认任务终态；恢复时先核对原任务与工作区，确认旧执行者已停止或可安全续接，再继续同一修改范围。实际结果保存在 Ticket，索引仅链接当前事实。

## 条件不足

明确说明缺少的委派权限、工具或资料。用户允许直接实施且当前代理能可靠完成时可顺序直接执行；已要求隔离执行或当前上下文不足时暂停并交还。使用 Skill 和新建子代理是不同动作，委派记录来自实际工具结果。

## 决定变化后的接续

协调者取得用户结论后，同步受影响规范和 Ticket，保留任务正文与决定来源。正在执行的相关子代理先接收并确认新边界，或用平台能力安全结束旧任务后由新的执行者接手；终态不明时暂停重叠写入。已完成的受影响结果重新验收。

独立且仍符合当前共识的任务可继续；共享方向或安全边界变化可能影响更广范围。工作记录保存实际答复、受影响任务、在途执行者与恢复条件即可。原始审查基线、现有修复额度、保存权限和人类检查点沿用。
