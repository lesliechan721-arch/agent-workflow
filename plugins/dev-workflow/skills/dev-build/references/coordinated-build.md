# 委派子代理实施

多个工作项有独立验收/交接价值、局部实现负担挤占主线协调，或用户明确要求时读取。

## 准备与委派

复用当前Ticket，必要时用dev-breakdown补足结果、规范主题/附件、关键条件、代码事实、实际依赖与验收。主协调者先处理尚未确认的材料选择，任务不可执行时先调查或调整切分。

按歧义、依赖耦合、验证难度和遗漏代价选择足够能力。较弱实施子代理获得必要领域背景与例子；仍有大量跨域判断时调整任务或模型，而非仅增加指令长度。

工具与授权具备时默认顺序委派，给出当前任务、规范版本、允许写入范围和验证重点，使用dev-implement。共享进度由当前协调者维护。只有接口、写入和验证环境确实独立且有集成收益时并行，遵循已有隔离方法。

未提交的项目规范与本地Ticket不会自动出现在另一个checkout。派发前核对真实可达内容；必要时共享或传递受控当前材料，无法保证时顺序在同一有效工作区执行，不能把旧分支内容当当前目标。

## 接纳与变化

子代理实际实施、验证并返回可访问结果，协调者核对diff、适用规范和原型再作集成验证。公共布局或接口推广前按milestone方法检查，任务正文不被进度摘要覆盖。

子代理发现新事实使用户结果、条件或风险变化时，暂停受影响修改并把证据与影响交回当前协调者；不是自行改变规范。决定更新后，相关执行者确认新依据，或安全结束旧任务后重新接手。旧任务终态不明时暂停重叠写入。

工具、资料或委派权限不足时说明缺口。普通可可靠完成的任务可在现有授权内直接实施；明确要求隔离而无法取得时保持受限结论。恢复实际工作区、子代理状态和已有预算，不靠角色名称或消息自述证明完成。
