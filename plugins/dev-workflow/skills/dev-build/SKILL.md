# Dev Build

协调当前授权范围的实施闭环。独立使用时从明确请求与项目资料建立工作，准备、实施与交付核验由同一协调者负责。

## 准备实施

1. 读取用户要求、实际确认与实施授权、当前任务Spec及其附件、适用公共合同、接受设计、相关代码和本地任务。保留任务原始审查基线，区分目标规范与实现现状；项目文件已经写入不代表批准或实现完成。
2. 缺少材料决定时交回当前用户协调者；独立Build使用 `decision-shape` 对齐。需要形成或修订正式设计时使用 `dev-design` 完成受影响部分，再按原实施授权继续。已有充分依据直接复用，避免重新审批相同范围。
3. 需要分解时使用 `dev-breakdown` 形成下一批可执行任务。需要保存、交接或恢复时读取 [本地任务与项目资料](references/local-workspace.md)，默认 `.dev-workflows/<task>/`；准备完成以任务、当前完整Spec及适用合同版本、验收和权限可供接手为准，不要求先提交文档或Ticket。

## 实施与集成

当前上下文足够的机械修改直接执行并验证；受规范、设计、接口或有界修复约束的工作项使用 `dev-implement`。多个工作项有独立交接价值、局部工作明显占用协调上下文或用户要求委派时读取 [协调实施](references/coordinated-build.md)，工具和权限具备后默认顺序委派子代理；独立性与集成收益明确时才并行。

接纳时读取真实diff、任务验收、当前任务规格、适用公共合同及设计证据，再作组合验证。任务正文与关键例外保留，实际结果附着其后；当前协调者维护本地进度。实际命令、使用说明和运维事实随实现验证更新，不另行重新定义产品合同。

公共基础即将被复用、风险或迁移转换、代表性设计推广及高返工集成结果可选为milestone。读取 [里程碑审查](references/review-planning.md)，验证并审查明确的累计范围后再解锁依赖。普通工作项执行相称验证；Git提交不是每个阶段或milestone的前置。

## 交付核验

对原始任务范围的完整当前结果使用 `dev-review-code`，提供原始用户来源、当前规范与附件、接受设计和实际验证。保持两份独立判断；已具备本轮角色条件的执行者直接完成，外层采用本轮结果不重复审查。

按当前任务Spec核对完整结果，代码、类型、行为测试和受影响的公开资料保持一致。长期保留项目特有词汇、重要决定理由，以及真实消费者仍需要的合同或接受设计；不要求将整份任务Spec转为永久文档。当前要求已实现并有证据承接，唯一必要信息已妥善保留后，本地任务才具备可清理条件。未完成要求与限制仍保留，清理需实际请求。实质问题和证据缺口关闭后交付，过程资料保持本地，需求未完成不推送。

## 修复、保存与权限

完整交付授权涵盖本范围合理本地实现和验证；只读或更窄授权保持。已有实质Code问题时读取 [有界修复](references/review-repair.md)，按现有预算与真实进展决定续修或早停，质量标准不随预算耗尽降低。

有实际回退价值或用户要求保存/整理历史时读取 [Checkpoint与提交](references/checkpoints.md)。本地过程文件即可支持同机恢复，不为阶段转换强制commit。提交、push、历史重写和部署分别按适用授权处理。

## 新证据与恢复

新事实改变用户结果、接受设计或风险时，暂停受影响修改和派发，由当前用户协调者通过Shape重新对齐，必要时由Design修订当前任务Spec及受影响公共合同。更新相关Ticket和验收，在途子代理确认收到当前内容或安全结束后再接续同一写入范围；已完成的受影响结果重新核对。

本地Spec、未提交的公共合同和任务资料不会自动进入另一checkout；委派前核对执行者实际能读到的版本。资料冲突先查明，不能通过改规范迁就实现。独立部分可继续，旧预算、原始范围和人类停止点持续有效。

取消任务时先处理本次项目规范与代码中的未完成变更，保护无关工作；本地过程资料仅在明确清理请求与必要内容已归位后处理。
