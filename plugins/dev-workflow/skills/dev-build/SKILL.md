# Dev Build

协调当前授权范围的实施闭环。直接使用时也能从请求和现有资料建立工作，无需父流程私有状态。

## 准备与执行

1. 读取目标、确认或批准依据、有效 Spec/issue、设计与任务。核对材料行为来自用户要求、当前接受记录、适用合同或明确委托；模型提案保持其待确认性质。确认实施授权并保留任务原始审查基线。已有资料位置沿用，必要持久记录采用用户位置或项目约定。
2. 材料决定不足时先按下方对齐要求处理；已确认结果缺少代码入口、依赖或任务安排时，调查或使用 `dev-breakdown` 补成可派发 tickets。当前上下文足够的机械修改直接执行并验证；受规范、设计、接口或有界修复约束的工作项使用 `dev-implement`。
3. 多个工作项具有独立验收或交接价值、单项局部调查与实现会明显占用协调上下文，或用户明确要求委派时，默认委派子代理实施；先确认任务已可派发。读取 [协调实施](references/coordinated-build.md)，默认顺序执行，独立性和集成收益明确时才并行。单个局部任务的资料与验证已充分、当前上下文可可靠完成时，可直接执行。
4. 接纳结果时核对实际 diff、相关测试和设计对照证据。任务正文与验收保持可重派，状态与集成证据附着于任务；只有 tracker 不足以支持恢复时使用 [工作索引](assets/work-index-template.md)。
5. 共享基础即将供多个下游使用、重要风险或迁移转换点、被接受设计的代表性实现即将推广，或一组集成结果的错误会造成显著返工时，选定 milestone。读取 [阶段审查与推进](references/review-planning.md)，按其范围完成验证、授权保存和独立审查后再解锁依赖。普通工作项执行相关验证即可。
6. 整体实现和集成验证完成后，使用 `dev-review-code` 对原始任务范围内的完整当前结果进行双轴独立审查。提供 Spec、任务、被接受的原型和可访问的证据；确认质量与覆盖充分后交付。

## 主动判断与权限

完整交付请求中的本地实现、验证和有界缺陷修复按现有授权执行；只审不修的请求保持只读。已有实质问题需要修复时读取 [Review 修复](references/review-repair.md)，说明适用预算并按证据续修或提前暂停。

选定 milestone 时，主动确认本任务的本地提交授权；其集成结果验证后默认保存 checkpoint，再审查固定范围。提交安全、明确无提交路径与历史整理见 [Checkpoint 与历史](references/checkpoints.md)。委派、成本和外部动作继续受当前平台与项目权限约束。

## 新证据与对齐

新证据产生未确认的用户行为或使既有决定失效时，先核对其影响，暂停依赖该决定的修改和派发。当前协调者说明原决定、新事实、后果及可行选择；独立调用 Build 时直接与用户对齐，有外层用户协调者时交回该协调者。局部选择直接问，访谈、单一体验和多问题塑形分别使用 `decision-grill`、`decision-prototype`、`decision-shape`。

获得实际答复或明确委托后，更新受影响 Spec、Ticket 与验收；材料变更完成相应独立审查与批准。向在途相关子代理传达当前依据，确认它已接收或安全结束后再接续同一范围，重新核对已完成的受影响结果。对齐不刷新预算或清除用户停止点。保持已确认结果等价的局部工程变化可自主处理。

## 交付与恢复

问题与审查结论均对照原始用户来源和当前有效决定。阶段结果不能替代完整交付审查，过去通过也只覆盖其仍然适用的范围。

记录实际结果、未关闭问题、验证限制和相关位置。需要持久报告时由本次协调者提供保存位置和历史要求。恢复时检查真实任务、代码与证据，沿用有效授权、已用预算及人类检查点。
