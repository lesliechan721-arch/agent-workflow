# Dev Build

协调实施到最终代码审查的闭环。目标、范围和用户授权来自当前任务；不自行扩大产品决定。

## 开始与执行

1. 读取当前请求或批准 Spec、必要决定、已有工作与 Review。确认授权和实施边界；记录或在当前上下文保留任务原始审查基线，最终审查不能只看最后一段改动。
2. 一个连贯工作项能在当前上下文完成时，直接使用 `dev-implement`，不先创建计划文件。需要工作分解或交接且没有可用工作项时，使用 `dev-breakdown`；已有 issue/work 直接复用。
3. 需要多个实现上下文或用户要求委派时，读取 [协调实施](references/coordinated-build.md)。先考虑顺序 fresh worker，只有独立性与集成收益明确时才并行。
4. 检查实际变更和验证证据，再接纳工作项。协调执行期间由当前协调者维护共享进度；子任务完成不等于集成完成。更新已验证结果、受阻事项和下一步即可。
5. 公共基础即将解锁大量下游、高风险边界或重要集成形成时，按需请求 `dev-review-code` 做明确范围的 milestone Review。普通切片只需相关验证。
6. 所有目标实现并完成集成验证后，使用 `dev-review-code` 审查原始任务范围内的完整当前结果。阶段 clean 不能代替最终 clean。

## 条件能力

- 已有 blocked Code Review 且自动修复获准时，读取 [Review 修复](references/review-repair.md)。在授权预算内根据实际结果决定继续或暂停；不扩大范围、增加预算或降低交付门槛。未经授权只报告下一步。
- 用户或适用项目政策已允许 checkpoint 提交，或用户明确讨论历史整理时，读取 [Checkpoint 与历史](references/checkpoints.md)。默认不提交。

## 暂停与交付

材料决定、Spec、风险或权限需要改变时暂停受影响工作并说明所缺决定。审查条件不足时，针对明确缺口补证据或独立审查；不通过修改代码伪造审查完成，也不无目的重复 Review。

最新完整最终 Review clean、有效 blocker 已合理关闭且实际验证充分时交付。说明结果、验证、剩余风险和相关工件；修复到达停止边界时如实交还。再次进入 Skill 不刷新授权或预算。
