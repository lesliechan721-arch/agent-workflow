# Dev Arena

并行让多个独立候选解决同一问题，挑出最易演进的基座，再手工融合落选方案里最强的 1–2 个点。避免单一首稿锁定错误形状。

## Phase A：定框与隐藏评分标准

所有候选拿到完全相同的任务说明，任务即合同：

1. 明确每个候选要产出的具体制品（类型签名草图、模块方案、原型代码或算法实现）和共享事实路径。
2. 在派发前写下 **3–6 条具体可打分的评审标准**（rubric）。**评分标准只给裁判和最终选型用，不发给候选**，防止候选应试刷分。
3. 为每个候选分配独立输出目录或独立 git worktree，绝不让两个候选写同一目录。

发给每个候选的任务只包含：共享目标与约束、只读参考路径、专属输出目录，要求附带简短理由（写明考虑过哪些替代方案及为何放弃），并随任务正文内联以下执行底线：

> 直接完成本候选单元，不再二次委派，严禁执行中途向人提问。仅在分配的专属输出目录或 worktree 内写入，不触碰其他候选或共享状态；先定清晰数据形状与边界，不为假想未来加抽象或兼容层；可运行候选须亲手在真实入口验证并附原始输出，严禁削弱有效断言。材料或前提不可达时立刻说明具体路径并停止依赖工作。

允许个别候选失败退出，记录缺席并继续评估其余候选。

## Phase D：通读并选定唯一基座

**必须端到端完整读完所有候选产物，禁止只读摘要。** 逐条按评分标准核对，并与裁判结果对照：一致则确认选择；分歧意味着存在偏见或评分标准模糊，重读双方理由再裁决。

选型第一准则：选**未来维护者最容易扩展且不易破坏不变量**的方案；难分伯仲时选边界更干净、对外 API 更小的方案。

## Phase E：手工嫁接

再通读每个落选方案一遍，只挑真正值得吸收的 **1–2 个亮点**（绝不是大半拼贴）。**按同一心智模型手工重写融合进基座**，禁止机械拼接导致两套抽象打架。

- 若各候选自然收敛到同一形状，说明共识强，直接采用无需嫁接。
- 若各候选彻底发散到互不兼容的方向，说明 Phase A 任务定框不清——**重新定框重跑，不要强行取折中平均**。

## Phase F：验证与交付

对融合后的最终制品做与对象相称的真实检查（类型检查、场景推演、运行原型或测试）。若验证暴露新问题，先查是 Phase A 漏约束还是 Phase E 漏嫁接，直接回修而非打补丁掩盖。

交付：最终单一制品 + 简短综合说明（选定基座及理由、实际参与座次与跨模型多样性、独立裁判结论或环境受限说明、每条嫁接来源、被拒方案及原因、收敛/缺席情况与验证结果）。
