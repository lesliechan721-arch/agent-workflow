# Dev Breakdown

生成一个新上下文实施者可以接手的工作项，而不仅是进度条目。

1. 读取当前目标、相关 Spec/决定、接受设计、已有任务与代码，并核对其确认或委托依据。资料不足可调查，任务安排不足可分解；需新增用户行为或旧决定已不适用时，说明后果并交回用户或协调者。仅把已有共识支持的内容写成可派发任务。
2. 按可独立演示或验证的结果拆分，并标出真正的阻塞关系。通常采用纵向切片；机械大改可使用保持系统可用的迁移批次。前置重构需要当前实施的具体理由。
3. 使用 [任务模板](assets/ticket-template.md) 展开下一批可执行任务：交付结果、相关需求、已确定实施安排、必要接口与设计依据、依赖、验收、范围和自主决定空间。远期工作保持粗粒度，单个自然任务可以直接交付一项。
4. 按目标实施者的知识与能力补足领域事实、代码入口和实例。重要共享接口由协调者先调查并明确；剩余跨域判断太多时调整切分或执行者，确保工作项能够独立开展。
5. 逐项检查：只凭任务、可访问引用和相关代码，能否知道预期行为、集成关系与完成条件？涉及原型时指明要读取的页面、状态和接受范围；短而关键的事实可共置，较大权威材料用有条件的指针。
6. 采用用户指定或仓库已有载体。跨上下文任务通常一项一个 ticket/issue；小任务可同页或对话交付。已有 tracker 直接复用，分解本身不创建运行状态记录。

任务是可变实施安排。范围内的切分和顺序可调整，新增材料决定、成本或权限需求应提交用户确认。本次只交付工作项、依赖和可开展的下一批任务。
