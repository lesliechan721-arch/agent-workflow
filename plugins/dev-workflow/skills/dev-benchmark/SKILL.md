# Dev Benchmark

任何性能数字（改动前后对比、回归声明、Hillclimb 指标或技术选型）在报告或采信前，必须用真实运行证据回答下面七问，绝不靠读代码猜数字。

若用户只要粗略量级估算（quick ballpark），单次运行即可，但**仍必查第 4 问和第 7 问**并标明是单次跑分。**涉及方案二选一时永远不是粗略估算。**

## 运行前准备

1. **先写下准备宣布的那句话**（例如“60k 行导出 p50 提速 30%”），后续七问专门检验这句话能否站得住。
2. **通读测量脚本**：明确它到底计时什么、统计什么、忽略什么。
3. **检查机器空闲度**：查负载与核心数（如 `uptime`、`nproc`/`sysctl -n hw.ncpu`）；机器繁忙且停不掉其他任务时，必须交替运行两侧并如实披露。

## 七项硬核检验（每项必须有运行证据）

1. **为什么不能再快一倍？（找限制因素）** 在**不计入正式成绩的单独剖析运行**中定位瓶颈（CPU 占用、运行时 profiler、I/O wait、系统调用），映射到具体源码。同时盯紧**负载生成器**：压测端先打满，你测的就只是压测端。改动没拉动数字时，先找限制因素再下结论。
2. **两侧都按生产方式调优了吗？** 必须使用 release 构建、生产配置与环境变量、同等连接池/批处理/事务与冷热缓存状态。若某侧跑在未调优默认配置（如每行一事务、debug 构建、漏索引），你比的是配置不是实现——先调优重测，调不动就**不得判赢**（选型时把口号缩小成“按今天默认配置”也不行，因为用户采纳的是方案本身）。
3. **有没有违背物理或阿姆达尔（Amdahl）上限？** 现场算账：对比吞吐与磁盘/网络带宽、ops × 单次耗时与核心数、节省时间与被改环节的原耗时占比。**删掉一个只占总耗时 10% 的环节，整体最多快约 11%**；超出算术上限的数字必然测错了（命了缓存、空转或触发了 bug）。
4. **有没有出错或算错？** 统计失败数、非 2xx、超时与重试，并校验输出内容正确而不仅是非空。报错拒绝往往极快，超时重试往往极慢；脚本没计数就补上计数。
5. **能稳定复现吗？** 两侧至少**各跑 5 轮且 A/B/A/B 交替运行**（抵消预热、惰性初始化、缓存与时间漂移），报告**中位数与极差（range）**。差值小于波动极差就是**无显著差异**；接近时做秩和检验。
6. **在端到端路径上真的重要吗？** 微基准旁边必须给出用户真实等待的端到端路径耗时及该局部的占比（Realistic 数据规模与并发）。一个只占请求 1% 的函数快 100 倍，整体也最多快 1%。
7. **工作真的在计时区间内执行了吗？** 确认请求真到服务端、行真落盘、结果真被消费。警惕惰性生成器未被遍历、Promise 未 await、JIT 死代码消除或静默超时，这些都会产出“工作根本没发生”的假高速。

## 常见失真速查

| 异常信号 | 立刻核查 |
| --- | --- |
| 耗时短到接近框架固定开销 | 跑明显不同规模的对照负载，确认计时器能拉开差距 |
| 候选总是越往后跑越快 | 拆开冷启动/预热/稳态，改为严格 A/B/A/B 交替 |
| 只有 1–2 个极值拉高收益 | 保留全部原始样本；无独立物理原因不删异常值 |
| Profile 与正式计时结论打架 | 查探针开销、样本代表性及限制资源转移 |

## 交付结论

先给四选一明确裁决：**`faster` / `slower` / `no measurable difference` / `inconclusive`**。

给出带单位的指标、轮数、中位数、极差和真实限制因素（例如：“p50 41 ms → 33 ms，两侧各 7 轮交替中位数，极差 32–35 ms，瓶颈在单核 JSON 解析”）。**凡宣称有差异却说不出限制因素、任一侧未按生产调优、或未核对第 4/7 问的，一律判为 `inconclusive` 并指名缺口。**
