# Dev Correct

操作者在这座仓库里反复纠正同类错误。改动仓库结构，让下一个 Agent 根本犯不了这些错。

**默认心智模型**：假设每位后续贡献者都是**只看得见自己打开那几个文件的 Agent**——它会照抄最近的现成代码，走能编译通过的最短路。你的目标是让“单看一个文件觉得对的改法，对整座仓库都确实是对的”。

## 1. 挖出重复错误类别

读取近期提交、revert 记录、评审意见、Agent 指令文件以及解释 workaround 的代码注释，把错误归类。**至少出现过两次的同类错误才算一类**，不为一锤子偶发事故过度建设。

## 2. 按最高有效层级根治

对每一类错误，从第 1 级往下试，选**能生效的最高层级**：

1. **架构消除**：让每份状态只有一个所有者、每件事只有一种受支持做法；隐藏内部实现使错误 import 直接报错；把手工同步的多份名单收敛成单一真相源；删掉会被 Agent 照抄的旧路径与死代码。
2. **类型 / Lint / CI 强拦**：用类型让非法状态无法编译；若错误代码仍能编译，加一条 Lint 或 CI 检查，且**报错信息必须直接写出应该改用的文件、类型或函数名**。若历史代码已有存量违规，设为只拦截新增增量（ratchet）。
3. **行为测试**：补行为级回归测试；同时修正或删掉“行为坏了仍通过”或“只改内部实现就失败”的坏测试。
4. **文档或 Agent 规则（最后手段）**：只用于确实无法编码的判断类约束——记住，Agent 跳过文档时没有任何东西会报错。

## 3. 逐项落地并证明防线有效

优先修最高频的错误类，每类独立收口。**每条新加的类型/Lint/测试防线，都必须在一条真实的历史坏样本上亲眼跑出失败**，确认它真能拦住错误，再恢复正常基线通过（本地与 CI 跑同一条命令）。任何特例必须写在违规行旁，附原因、过期时间与人工批准。

## 4. 维护“规则—执行手段”对照表

在项目 Agent 指令文件中维护一张简表，把每条规则与它的实际强制手段配对：
- 规则已在表里却没有任何机械手段强制、结果又重犯了 → 这次直接升级到第 1–3 级根治；
- 一旦架构或类型已经让某错误不可能发生 → **把对应文字规则从文档删掉**，减少上下文沉淀。

交付：每个错误类的历史证据、选定的硬化层级、为何更高层级不可行，以及新防线在历史坏样本上触发拦截的实测输出。
