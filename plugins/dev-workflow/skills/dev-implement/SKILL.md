# Dev Implement

按当前请求或 Spec 交付可工作的结果。用纵向切片吸收实施中的新发现。

## 产物位置

一个上下文能完成的低风险任务不创建工作文档。跨会话、多切片、并行、迁移或 handoff 需要 `work.md` 且未指定路径时，使用：

```text
docs/dev/<task-slug>/work.md
```

## 开始

1. 确认用户已明确要求实现，或当前 Spec 已获批准。
2. 如果本次是 Review 修复，读取最新 `code-review.md`，区分实现缺陷、Spec 偏离、Spec 本身的问题和非阻塞建议。只处理 blocker、必需影响面和修复直接引入的 regression。
3. 需要跨会话工作记忆时使用 [Work 模板](assets/work-template.md)。

## 实施循环

4. 选择满足当前请求或 Spec、并符合仓库既有结构的最小完整改动。每个非平凡新增内容必须能映射到当前请求或 Spec、项目硬规则、当前 blocker 或直接 regression。
5. 推测性的扩展层、单一使用点的通用框架、没有当前需求的 fallback、与 blocker 无关的重构和新增配置系统默认延后。
6. 在稳定公共 seam 上优先使用 red-green；探索性界面工作使用适合的行为验证。
7. 遵循仓库现有测试价值门。仓库没有规则时，新增测试只保护用户可观察行为、公开合同、已知 regression、安全或数据边界，以及确定性工具合同。
8. 精确文案、排版、私有文件布局、内部 prompt、整文件 snapshot 或 hash 只有在它们本身是消费者读取的公开合同时才可锁定。
9. 运行与变化相称的测试、类型检查、构建或真实行为检查。修复后重新运行相关验证。
10. Review 修复必须覆盖全部 blocker；无法修复的项明确说明原因和所需决定。不要把非阻塞建议静默升级成交付范围。
11. 记录重要工程选择、偏离、验证和剩余风险。

## 停止条件

- 材料目标、范围、公共行为或跨模块契约需要改变。
- 必须通过用户体验、实验或测量才能决定。
- 破坏性、远程、凭据、显著成本或不可逆动作尚未授权。
- Review 已标记自动修复停止，或当前修复无法在既定范围内减少 blocker。

## 输出

```text
结果：complete / blocked
产物：<代码、work.md 或无>
验证：<实际运行及结果>
未解决：<材料决定、Spec 变化、高风险授权、修复升级或无>
建议动作：<补充决定 / 收集证据 / 修订 Spec / 代码审查 / 请求用户决定 / 无>
```

实现或 Review 修复完成后建议代码审查。若材料决定或 Spec 需要改变，先完成对应决定或规格修订；若自动修复已停止，不继续改代码。
