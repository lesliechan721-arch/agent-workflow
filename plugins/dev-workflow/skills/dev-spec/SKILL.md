# Dev Spec

形成完整当前规范，让用户理解需要审核的内容，让新上下文实施者能够凭规范、决定来源及项目事实执行。普通开发任务需要持久规格时，沿用当前任务位置，默认 `.dev-workflows/<task>/spec.md`。已有明确指定的规格或受影响公共合同在其位置维护；本次Spec说明变更范围并引用未修改定义，避免竞争的完整副本。

## 综合与组织

1. 读取当前任务Spec、原始请求、实际确认或委托、适用项目合同、相关领域词汇/重要决定、接受设计和实际代码。区分已决定内容、模型提案、开放问题和事实证据；来源冲突或不可达会影响结果时，说明具体缺口。用户要求未定稿时如实标注，否则先处理影响当前规范的材料缺口。
2. 使用 [规格模板](assets/spec-template.md)，按能力或决策主题组织完整要求。保留行为、条件、例外、精确值、约束强度、重要技术决定及实施自由。建议仍是建议，硬约束保持其效力；schema、类型或逻辑片段更准确时保留决定密集的部分。
3. 每个主题先让用户看懂结果、重要取舍与风险，再呈现完整行为、精确合同和验证依据。多个主题、复杂来源或重组已有规格时，读取 [信息组织与保真](references/information-architecture.md)。附录位置不降低规范效力；所有需用户判断的材料内容都应在清楚的审阅路径上可见。
4. 被接受原型说明版本、可访问入口、适用页面/状态、必须保持的关系、允许变化和演示边界。主文与被纳入资料共同表达规范；任务、来源和环境指针说明需要读取的部分及用途。
5. 从来源检查每项材料决定是否被保留或按真实确认更新，再从规范核对依据。允许面向不同消费者概括，但同一规则的完整定义保持明确权威位置；来源矛盾保持可见。验证说明检查结果而非重复抄写全部规则。
6. 修订按真实问题或用户确认的变化进行。区分本次目标、既有合同与当前实现；本地任务Spec完整表达待实现要求，真实消费者需要的项目文档按相关变化维护，运行命令、性能和兼容等事实依据实际验证再陈述。区分语义变化与等价重组，保留必要技术精度；局部实施安排可交由任务准备，而已确定公共合同继续约束实现。新增材料选择交回用户或当前协调者。

## 交付

提供完整规范入口及适用附件，说明本次实质变化、未决内容和实际来源核对范围。用户批准面覆盖其需要决定的结果与风险，不由文档长短或正文/附录标签缩减。

按请求在对话中交付或写入指定位置、项目约定；普通任务的完整规格及附件仅本地保存；独立落盘前核对目标写入权限及忽略条件，条件未具备时先交付正文并说明。实施者和审查者必须实际取得当前版本，包括接受设计和重要条件。用户明确需要维护长期公共合同或设计资料时按用途处理，不把任务规格默认当作永久文档。任务完成前保留完整依据，后续审查、批准、实施和清理由调用者负责。
