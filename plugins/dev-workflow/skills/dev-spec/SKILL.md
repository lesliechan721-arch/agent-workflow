# Dev Spec

Spec 是已经形成决定的记录。它固定材料性共识，不预测全部实施细节。

## 产物位置

优先使用用户或调用者给定的路径，其次遵循仓库约定。都没有时写入：

```text
docs/dev/<task-slug>/spec.md
```

不要为同一任务另建平行目录。

## 工作流

1. 收集已确认的决定、仓库事实、Prototype 结论和现有约束。
2. 读取并使用 [Spec 模板](assets/spec-template.md)。只写会影响材料结果或验收的内容。
3. 将 Prototype 内容按层投影：
   - 已确认决定进入决策摘要、用户可观察行为、材料决定与不变量、验收；
   - 完整原型、用户反馈、被否决方案和实验过程只在 Evidence 中链接；
   - 未解决的材料问题进入 Open decisions。
4. 技术细节只有在满足至少一项时进入 Spec：用户需要理解或授权；两个合格实现者可能产生材料性不同结果；必须跨上下文保存；判断交付必须依赖它。
5. 其余文件拆分、局部算法、类型设计、测试组织和任务顺序写入 `Agent discretion`，不要提前冻结。
6. 只有独立、稳定且在主文展开会妨碍审核的材料主题，才创建 `decisions/<topic>.md`；主 Spec 保留摘要和链接。
7. 无法完成时不要选择下一 Skill。返回中性阻塞类型：
   - `material-decision`：仍需用户取舍的材料决定；
   - `evidence-needed`：必须通过体验、实验、测量或运行证据决定；
   - `fact-gap`：可以调查但当前证据不足的事实。

## 输出

返回：Spec 路径、已写入的规范性决定、Evidence 链接、Open decisions 和阻塞类型。没有阻塞时明确写“无”。
