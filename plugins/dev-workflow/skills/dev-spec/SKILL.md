# Dev Spec

形成完整当前规范，让用户理解需要审核的内容，让新上下文实施者能够凭规范、决定来源及项目事实执行。

## 综合与组织

1. 读取原始请求、实际确认或委托、接受设计和相关项目事实。区分已决定内容、模型提案、开放问题和事实证据；来源冲突或不可达会影响结果时，说明具体缺口。用户要求未定稿时如实标注，否则先处理影响当前规范的材料缺口。
2. 使用 [规格模板](assets/spec-template.md)，按能力或决策主题组织完整要求。保留行为、条件、例外、精确值、约束强度、重要技术决定及实施自由。建议仍是建议，硬约束保持其效力；schema、类型或逻辑片段更准确时保留决定密集的部分。
3. 每个主题先让用户看懂结果、重要取舍与风险，再呈现完整行为、精确合同和验证依据。多个主题、复杂来源或重组已有规格时，读取 [信息组织与保真](references/information-architecture.md)。附录位置不降低规范效力；所有需用户判断的材料内容都应在清楚的审阅路径上可见。
4. 被接受原型说明版本、可访问入口、适用页面/状态、必须保持的关系、允许变化和演示边界。主文与被纳入资料共同表达规范；任务、来源和环境指针说明需要读取的部分及用途。
5. 从来源检查每项材料决定是否被保留或按真实确认更新，再从规范核对依据。允许面向不同消费者概括，但同一规则的完整定义保持明确权威位置；来源矛盾保持可见。验证说明检查结果而非重复抄写全部规则。
6. 修订按真实问题或用户确认的变化进行。区分语义变化与等价重组，保留必要技术精度；局部实施安排可交由任务准备，而已确定公共合同继续约束实现。新增材料选择交回用户或当前协调者。

## 交付

提供完整规范入口及适用附件，说明本次实质变化、未决内容和实际来源核对范围。用户批准面覆盖其需要决定的结果与风险，不由文档长短或正文/附录标签缩减。

按请求在对话中交付或写入指定位置、项目约定。当前读者应能恢复全部有效要求及其条件，后续审查、批准和实施由调用者负责。
