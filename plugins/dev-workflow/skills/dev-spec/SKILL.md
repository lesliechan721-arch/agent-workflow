# Dev Spec

形成当前范围的完整规范，主 Spec 本身适合用户审核，正文与纳入的规范附件共同支持新上下文实施。需要落盘时按 工作目录（`references/local-workspace.md`） 选择位置，普通持久任务无当前位置时使用 `.dev-workflows/<task>/spec.md`。获准修改的现有公共合同原位维护，未变定义引用其权威来源。

## 确定依据与必要设计

读取当前规格、原始请求、实际确认或委托、项目合同与相关代码、领域决定和接受设计。区分已定要求、提案、开放问题与事实；影响结果的缺失或冲突交回用户或协调者，不自行补造决定。

新增机制先按项目复杂度门槛比较更简单方案：它服务哪个当前需求、消费者或有依据的高概率／高影响风险？直接实现或已有恢复渠道为何不足？没有当前必要性的抽象、持久状态、扩展点和文件级安排不固定为要求。保留必要安全、兼容和恢复约束；已确认设计即使有简化机会，也先提出变更，不静默删除。

## 组织当前规范

修订已有规格时按 任务变化（`references/task-changes.md`） 核对当前有效要求，保留可找回的旧批准依据及必要附件。当前入口保持完整，不用补丁记录代替规范；已结束 Build 的结果不随当前规格改写。

新写或实质重组人审规格时，在确定正文结构前使用 `explain-for-review`，提供读者任务、完整决定与来源、确认状态和输出位置，采用其阅读路径、表达形式与保真方法。当前上下文已加载的方法直接复用；局部修词不重做完整呈现。方法用于本次主 Spec，不默认另建阅读版；规范定义、附件、验收及设计必要性仍由本 Skill 负责，原始来源的写入边界保持。

使用 规格模板（`assets/spec-template.md`） 的适用部分，使主文直接支持用户判断，完整规范支持实施。保留条件、例外、精确值与单位、约束强度、已定技术选择和实施自由。原型保留实际入口、接受版本、页面／状态、须保持的关系、允许变化及演示边界。需要划分规范附件或迁移过程材料时读取 规范与资料组织（`references/information-architecture.md`）。

## 核对与交付

从来源核对有效要求是否完整，再反查新增约束的依据与必要性；核对主文中的关键场景、取舍、风险、验收及完整定义入口。需要额外导航或定位反馈时，由本 Skill 按 Explain 方法在授权位置生成呈现，核对来源版本与状态；来源改变后同步或标明旧视图失效。区分实际语义变化与等价重排、设计目标与运行证据。

有明确草稿请求，或协调者已授权本地草稿以便恢复时，可保存已确认内容及标明的开放问题；其他情况先报告影响规范成立的缺口。草稿不表示批准。

按请求交付正文或文件、完整入口及必要附件、确认依据、实质变化与未决事项。普通任务规格及附件仅本地保存，写入前核对权限、忽略与未跟踪条件；不具备时交付正文并说明。保留必要来源，结束本次规格编写，不启动审查或实施。
