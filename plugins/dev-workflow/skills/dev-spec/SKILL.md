# Dev Spec

Spec 是已经形成决定的记录。它固定材料性共识，不预测全部实施细节。

## 工作流

1. 收集已确认的决定、仓库事实、Prototype 结论和现有约束。
2. 读取并使用 [Spec 模板](assets/spec-template.md)。只写会影响材料结果或验收的内容。
3. 技术细节只有在满足至少一项时进入 Spec：用户需要理解或授权；两个合格实现者可能产生材料性不同结果；必须跨上下文保存；判断交付必须依赖它。
4. 其余文件拆分、局部算法、类型设计、测试组织和任务顺序写入 `Agent discretion`，不要提前冻结。
5. 只有独立、稳定且在主文展开会妨碍审核的材料主题，才创建 `decisions/<topic>.md`；主 Spec 保留摘要和链接。
6. 需要系统推演时使用 `decision-grill`；需要体验证据时使用 `decision-prototype`。这两项能力来自 `ask-me`。

所需 `ask-me` Skill 不可用时，报告缺失的材料决定或证据，并建议安装 `ask-me` 或由用户直接补充；不要临时复制访谈或原型流程。

完成后使用 `dev-review-spec`。中大型、跨会话或多人交接任务在 clean Review 后由用户明确批准当前 Spec，再进入实现。
