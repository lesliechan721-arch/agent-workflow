# Dev TDD

用最小、可信的行为检查锁定合同与回归，绝不为了“有测试”制造脆弱或自证的假测试。

## 先判断：该不该写新测试

- **走先红后绿（TDD）**：用户明确要求 TDD/回归测试，**或**当前缺陷/行为有现成、廉价、稳定的本地测试路径（单测、组件测或轻量集成测）。
- **跳过新增测试，改用最近可执行验证**：若新增测试需要从零搭重型 harness、堆叠脆弱内部 mock、依赖不可控时序/全局状态、或引入大范围无关 fixture 改写，**宁可不加新测试，也不要加烂测试**。改用原复现命令、定向脚本、真实界面/CLI 运行或日志断言取证；若用户曾明确要求 TDD 而本条件不满足，直接如实报告原因，不静默敷衍。
- **已有覆盖直接复用**：现有测试已覆盖该合同就运行并复用，不写同义重复测试。

## 红 → 绿节奏

1. **先写聚焦失败用例**：只测当前缺陷或公开行为合同，不扩写无关用例。
2. **修代码前先跑出真红灯**：确认失败原因是**目标缺陷本身**。以下三种均不算有效红灯，必须先修正测试再改生产代码：
   - 测试直接绿了；
   - 报语法/编译/导入错误；
   - 因无关环境缺失报错。
3. **做最小修复并重跑变绿**：改完后重跑新测试与邻近回归测试。

## 两条假想修改检验（拦截伪测试）

对每条新增、修改或保留的测试做两次心智/实测检验：

1. **破坏行为**（返回错值、漏掉或重复一次外部副作用）：若测试仍然通过，这条测试证明力为零——常见病根是断言过松、用被测代码自己算预期值、或只断言测试自己造的 mock 数据。
2. **改内部实现而保持全部外部可观察结果**：若测试挂了，说明它锁死了私有实现细节（私有 helper、内部调用顺序、中间数据结构）。

**保留通过第一关且扛过第二关的测试，重写或删掉其余测试。**

## 断言硬约束

- 通过公开消费者入口传入具体输入，预期来自需求或独立正确样例，不复制被测算法自证。
- 断言返回值、调用方分支依赖的**错误类型**（非精确文案，除非文案本身是公开合同）、可读回状态及外部系统收到的真实请求。
- 只在不可控外部边界替换 stub/fake，不用内部 mock 证明模块拼接正确。
- 严禁削弱既有有效断言来迁就错误实现。

交付时粘贴具体证据：修前红灯命令与关键失败输出、修后绿灯输出；跳过新测试时写清原因及替代的可执行验证。
