# Dev Debug

按科学方法定位根因：**每一条结论和最终留下的每一行代码都必须追溯到运行证据。**

## 1. 先亲手复现（能跑绝不推给用户）

保存原始失败的版本、实例身份、配置、输入与输出。**默认自己通过真实 CLI、API、测试或界面驱动复现**；即使常规指引建议请用户复现，也必须先自己驱动到极限，只有确认控制表面确实无法触达目标（如私有账号或隔离硬件）时才向用户求助，并说清具体卡点。

难以直接复现时，合成触发输入、收紧并发/超时条件或加临时日志直到稳定触发；缩小复现范围后，核对破坏的仍是同一个合同而非新错误。

## 2. 二分假设与反猜补丁

1. **选切割空间最大的实验**：列出竞争假设，写出各假设下不同的可观察预测，优先跑一次能排除一半以上空间的低成本观测。程序状态看不清就打临时观测读取真实值，不要对着源码盲猜。
2. **证据推翻即回滚**：当运行证据否决某个假设，**立刻撤回该假设引发的全部代码改动**。“可能顺便有用”的防御补丁属于未经证实的假设，绝不保留。
3. **Attack the Premise 硬停信号**：若**两次以上尝试共享同一前提却仍卡在同一检查**，立刻停止继续打补丁——用一句话写出这个共同前提，先设计一个在前提为假时会给出不同结果的直接实验去检验它。
4. **区分合法状态与非法状态**：问清触发症状的状态是否合法。若合法，在未处理它的位置补处理；若该状态**根本不该产生**，在下游加空判、重试、吞错或截断只会把真正 bug 藏起来，继续往前追到最早造出非法状态的代码。

## 3. 按问题类型选现场观测

不稳定竞态先记发生率、负载与事件顺序；盲目加 `sleep` 或重试只会掩盖现象。

| 待区分问题 | 观测手段 | 注意陷阱 |
| --- | --- | --- |
| CPU 忙于哪段工作 | 采样 profile + 调用次数与真实工作量 | 区分仪表扰动与热路径 |
| 对象为何不释放 | 多次快照增量 + 到根保留链 | 单次大对象不等于泄漏 |
| 谁在等、谁占资源 | 线程状态、trace 或调度事件 | 核对完成信号与持锁者 |
| 谁写坏了共享状态 | 在生命周期创建/转移/销毁处定点观测 | 排除旧进程或未重新构建 |

## 4. 交付与清理

仅请求诊断时，恢复全部临时探针/补丁（或按约定隔离保留）后即停。交付：原表面可重放复现命令、因果证据链（从最早错误决定到用户症状）、已排除假设、建议修复位置及仍未区分的候选项。暂时没再复现、重启后恢复或退出码为 0 都不能证明根因已解决。
