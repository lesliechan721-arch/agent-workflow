# Dev Workflow

```text
完整开发：dev-workflow → dev-design → dev-build → 交付
                         对齐／规格      准备／实施／集成
                                           │
                          milestone／最终范围 → dev-review-loop
                                                   ├── dev-review-code
                                                   └── dev-implement
```

Design 可独立用于“先设计，以后实施”；Build 也可从已有有效目标直接工作。Design 由 decision-shape 组织需求整体覆盖、问答、原型与知识维护，再将完整决定交给规格编写和独立审查。专业能力可独立调用；已有有效结果直接复用，小任务可在对话中完成，必要对齐、验证和最终核验保持。

## 能力

| Skill | 当前结果 |
| --- | --- |
| dev-workflow | 连接 Design 与 Build，处理跨阶段变化 |
| dev-design | 形成有确认依据的设计，选择对话或完整规格交付 |
| dev-spec | 形成可直接人审的主规格，保留完整定义与必要设计 |
| dev-review-spec | 独立核对规格保真、人审可读性、设计必要性与可实施性 |
| dev-breakdown | 准备可独立接手的工作项与真实依赖 |
| dev-build | 协调实施与集成，采用有界核验结果推进交付 |
| dev-review-loop | 对当前范围组织独立审查、必要修复、验证与复审 |
| dev-implement | 实现一个已明确的工作项或有界修复 |
| dev-review-code | 当前范围的需求／设计与工程质量两份独立判断 |

修订／修复预算遵循当前授权，未指定的新授权默认最多三轮；规格修订由 Design 协调，代码修复由 Review Loop 协调。已有较低限制、已用次数和人类停止点保持。只读审查不自动取得修改权限。采用 Skill 不等于新建代理，角色隔离按实际审查要求执行。

## 资料

领域词汇、重要理由和确有消费者的公共合同按需维护。完整任务规格、原型和过程证据默认只在 `.dev-workflows/<task>/` 保存，目录用途见 [工作目录](references/local-workspace.md)。设计恢复使用当前设计产物；实施／修复需要协调时才创建 Work。普通开发完成前不推送，完成后也需要实际授权。

主 Spec 直接呈现行为、取舍、风险和验收，必要技术细节可按需进入，过程记录不挤占主线。安装时同时提供 decision-kit 和 human-content：前者用于取得实际决定，后者的 Explain 方法由 Spec 在组织人审正文时直接采用，也按需用于候选解释或反馈呈现。不默认生成第二份“人读版”规范，局部修词不重走整套流程。阅读或导出评论不构成批准。安装、模型成本、提交与外部操作遵循项目和平台权限；用户只要一个阶段时在该阶段结束。

规格复审按累计变化选择范围，局部修订可由仍独立的原审查者复核；需要全面重审或明确要求新视角时使用新的独立上下文。沿用旧证据需核对其来源与持续适用性，作者自检不替代独立结论。

已知、获准的有界工作先实施与验证，再核验结果；需要发现问题时先审查。完整范围的双轴证据可以由本轮查证与经核对仍适用的旧证据组成，复用基于自原审查版本以来的累计变化。
