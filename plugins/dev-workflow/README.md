# Dev Workflow

以明确阶段和可交接资料组织开发。用户处理材料决定与必要授权；模型调查事实、选择方法、组织实施并提供实际证据。专业能力仍可独立调用。

```bash
aw install dev-workflow -p both
```

## 阶段主线

需求对齐 → 形成并确认规格 → 准备实施 → 实施与集成 → 交付核验。

阶段按实际成果推进：确认与接受记录、当前规范及附件、可派发任务、真实集成结果、完整独立审查。已有有效成果复用；材料变化只重开受影响决定与依赖。阶段标题、文件存在或旧报告不能证明当前条件满足。

小任务可以在对话中完成必要对齐和规范表达，以一个自然工作项实施并独立核验，默认无持久流程文件。实际风险直接对应权限、隔离、备份与验证；长期交接或正式审阅需要出现时保存现有共识，再从相应阶段继续。

## 能力

| Skill | 结果 |
| --- | --- |
| dev-workflow | 整体阶段、资料位置、用户检查点与回流 |
| dev-spec | 组织完整当前规范与人审路径 |
| dev-review-spec | 独立核对来源保真、审核完整性、可实施与验证 |
| dev-breakdown | 形成下一批可独立实施的任务与真实依赖 |
| dev-implement | 在当前范围内实施并提供实际验证 |
| dev-build | 唯一协调实施准备、集成、最终核验和代码修复 |
| dev-review-code | 独立核对当前范围的需求/设计与工程质量 |

需求对齐使用依赖插件 ask-me 的 `decision-shape`，由它按需澄清、组织访谈或原型；已有充分有效的共识直接复用。阶段并不要求每次都加载所有Skill。

## 典型用法

```text
使用 dev-workflow 完成这个需求。先查明项目事实，与我确认会改变结果的重要选择，再实施和核验。
```

```text
使用 dev-build 继续已批准的 Spec，准备可交接任务、实施并集成验证。不要提交、推送或部署。
```

只需要规格、任务分解、单项实现或只读审查时，可以直接请求对应 Skill，不必启动完整工作流。

## 资料与人审

Spec按主题组织完整行为、精确合同、接受设计和验收。规范性附件与正文同样有效；材料决定和风险在完整审阅路径中可见。决定记录保留确认来源与成立条件，Ticket承接适用要求和实施安排，Work按需索引进度，Review记录实际证据与限制。

已有路径优先；没有约定的持久任务可采用docs/dev/<task-slug>/，由协调者给专业能力具体位置。小任务仍可生成源码、测试或临时原型。

## 审查、修订和保存

规格独立审查完成后仍需用户确认适用规范。完整代码审查保留两份独立判断；已委派审查者直接完成本轴，缺少隔离或验证条件则报告限制。

已授权的Spec修订和代码修复分别由其协调者按当前预算及证据续行；默认上限三轮、旧较低授权和停止点保持。预算不替代质量或用户批准。

长对齐交接可保存已确认主题；实施前将当前确认的规范、接受依据和首批任务形成基线。选定实施milestone后完成验证、授权checkpoint和独立审查再放行依赖。相邻成果可合并保存；本地提交、远程推送、历史重写和部署有各自授权。
