# Dev Workflow

把需求设计、实施交付和独立核验连接起来，也可以只选择其中一个阶段。同一任务支持多轮 Build，已有决定与有效成果可以继续使用，不必每次重新建立一套补丁需求。

## 安装与开始

```bash
aw install dev-workflow -p both
```

安装同时提供 decision-kit 和 human-content，分别用于取得有效决定和组织可审阅的材料。

四个流程入口由用户手动选择：`$dev-workflow`、`$dev-design`、`$dev-build`、`$dev-review-loop`。Codex 关闭这些入口的隐式调用，Claude Code 关闭模型自行调用。选择一个入口后，它在自身授权范围内采用完整的共享方法，不要求用户再次启动每个内部阶段。

```text
使用 $dev-design 把当前需求形成可交接设计，这次不实施。
使用 $dev-build 完成这些已确认问题，复用当前代码和验收，不提交。
使用 $dev-build 继续上次任务，修复这次反馈；保留前轮记录，只安排当前差异。
使用 $dev-workflow 从当前需求推进到实现交付；需要新的产品选择时先与我确认。
```

## 能力与边界

| Skill | 交付什么 | 不负责什么 |
| --- | --- | --- |
| dev-workflow | 手动协调阶段、跨阶段变化与用户检查点 | 不复制下游实施或审查方法 |
| dev-design | 手动组织对齐、规格、独立审查与有界修订 | 不启动产品实施 |
| dev-build | 手动组织任务、实施、集成和本轮交付 | 不代替用户决定新需求 |
| dev-review-loop | 手动协调明确代码范围的核验与有界修复 | 不接管设计、多任务实施或整体产品交付 |
| dev-spec | 当前完整、可直接人审和交接的规格 | 不自行取得产品批准或启动实施 |
| dev-breakdown | 可独立接手的工作项、真实依赖与验收 | 不创建 Build 轮次或执行工作项 |
| dev-implement | 一个明确工作项或有界修复及实际验证 | 不扩大为完整开发流程 |
| dev-review-spec | 规格保真、可读性、必要性及可实施性的独立判断 | 不改写规格或批准产品选择 |
| dev-review-code | 当前代码需求／设计符合度和工程质量的独立证据 | 不自动授权修改 |
| dev-simplify-code | 用户手动选择后的行为保持式代码简化 | 不接入自动实施链 |

Build 接受请求、问题清单、工作项或规格，没有 Spec 文件不阻止目标充分的工作。只有需要独立交接时才补足分解；已有任务足够就复用，单个自然工作项不强拆。只需普通修改、分解或只读审查时，可直接采用相应能力。

## 多轮实施与资料

Task 保存同一用户目标的当前上下文。当前 `spec.md` 及附件保留完整有效要求；已结束 Build 的范围、批准依据和交付结果保留为历史，不随当前规格改写。

中断恢复、本轮缺陷修复及交付中的获准调整继续原轮次。前轮已交付或明确结束后，再次授权实施时开始下一轮；只有真正独立的目标才另建 Task。后续 Build 根据当前代码、当前要求、反馈和前轮结果安排差异，不重做所有旧 Ticket。

优先采用用户位置或现有 tracker。需要本地过程资料时，默认使用 `.dev-workflows/<task>/`；按需把各轮 Work、Ticket、代码审查与验证证据放到 `builds/<round>/`。短工作可只在对话中完成。旧任务目录直接沿用，不自动搬迁。规格替换前保留必要旧版本和接受设计，不能假定未提交的本地资料已有 Git 历史。

## 授权与核验

需要新的产品决定时暂停受影响工作，说明原依据、已验证结果、缺口与影响；独立部分可以按已有授权继续。仅设计请求在设计结束后停止，设计认可、阅读文档和下载视图都不自动产生实施授权。

规格修订和代码修复各自沿用实际授权及累计预算；未指定的新自动修订／修复授权默认最多三轮，旧的更低限制和停止点保持。换会话、Skill 重入或新建 Build 目录不会重置同一未完授权。

独立核验仍需要合格的独立判断来源。共享方法不等于新的审查者；旧证据按累计影响核对后复用，不机械重做全部审查，也不把作者自检或读取 Skill 当作独立通过。条件不足时交付真实缺口。

普通任务过程资料只在本地保存，不暂存、提交或推送。公共合同仅在有实际用途且获准时原位维护；提交、推送、清理、网络、模型成本和其它外部动作遵循项目与平台权限。
