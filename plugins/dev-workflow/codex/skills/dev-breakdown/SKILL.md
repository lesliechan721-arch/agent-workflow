# Dev Breakdown

生成一个新上下文实施者可以接手的工作项，而不仅是进度条目。

1. 读取当前目标、相关 Spec/决定、接受设计、已有任务与代码，并核对其确认或委托依据。资料不足可调查，任务安排不足可分解；需新增用户行为或旧决定已不适用时，说明后果并交回用户或协调者。仅把已有共识支持的内容写成可派发任务。
2. 按可独立演示或验证的结果拆分，并标出真正的阻塞关系。先选能贯通关键接口的最小纵向切片，再展开依赖它的结果；不按文件、技术层或代理数量机械拆分。机械大改可使用保持系统可用的迁移批次。前置重构需要当前实施的具体理由。
3. 使用 [任务模板](assets/ticket-template.md) 展开下一批可执行任务：交付结果、相关需求、已确定实施安排、必要接口与设计依据、依赖、验收、范围和自主决定空间。先检查已有任务，合格的直接复用；只补不充分的部分。远期工作保持粗粒度，单个自然任务可以直接交付一项，不给每项附加独立 Review 或提交阶段。
4. 按目标实施者的知识与能力补足领域事实、代码入口和实例。重要共享接口由协调者先调查并明确；剩余跨域判断太多时调整切分或执行者，确保工作项能够独立开展。
5. 逐项检查：仅凭任务、明确引用的规范主题及附件、决定来源和项目代码，能否知道预期行为、重要条件、集成关系与验收？原型指明页面/状态和接受范围；关键例外可共置，完整定义引用当前权威。核对各材料要求由哪些任务实现或验证，跨项要求有集成检查；复杂时用简短覆盖索引，小任务无需新增文件。
6. 沿用调用者给定的本轮工作位置；需要落盘时按 [工作目录](references/local-workspace.md) 保存，不自行分配 Build 轮次。独立分解尚无 Build 时可用任务根的 `tickets/`，记录不进入 Git。任务引用实际将使用的完整任务 Spec 及适用合同版本，短关键提醒可共置；分解本身不另建完整决定或规范副本。小任务可在对话交付；用户明确要求外部 issue 时按其位置与权限执行。

任务是可变实施安排。范围内的切分和顺序可调整，新增材料决定、成本或权限需求应提交用户确认。本次只交付工作项、依赖和可开展的下一批任务。
