# 任务与工作目录

需要落盘、跨上下文交接或恢复时使用。优先采用用户或调用者给定位置，其次沿用当前任务目录，再按仓库约定；都未提供时使用下列位置。短任务可只用对话，已有 tracker 足够时直接复用，目录和文件均按需创建。

```text
.dev-workflows/<task>/
├── spec.md                 # 当前完整要求，或标明未决的设计草稿
├── spec/                   # 当前规范附件
├── spec-history/           # 替换旧批准依据前，按需保留旧版及必要附件
├── prototypes/<question>/  # 原型与可定位的接受证据
├── reviews/                # 设计审查与修订记录
└── builds/
    ├── 001/
    │   ├── work.md         # 本轮协调与恢复索引
    │   ├── tickets/        # 本轮独立交接的工作项
    │   ├── reviews/        # 本轮代码核验
    │   └── evidence/       # 本轮验证、复现与必要日志
    └── 002/                # 前轮已结束后的下一次实施交付
```

Task 保存同一用户目标的当前上下文；Build 轮次保存一次有边界的实施交付。Review 修复批次属于当前核验范围，不为每批创建 Build 目录。

## 选择实施轮次

| 当前事实 | 归属 |
| --- | --- |
| 会话中断、上下文恢复，原实施范围尚未结束 | 沿用原轮次，先恢复代码、在途任务、预算和停止点 |
| 本轮缺陷修复、核验，或本次交付中获准的要求调整 | 留在本轮，更新受影响任务和验证 |
| 前轮已交付或明确结束，用户再次授权实施同一目标 | 开始下一轮，引用前轮结果；不覆盖旧 Work、Ticket 和交付证据 |
| 用户目标确实独立，需要分别管理范围与交付 | 新建 Task，而非仅因发现 bug 或需求变化就拆任务 |

Build 协调者确定轮次并向下游提供写入位置；Breakdown、Implement 和 Reviewer 沿用该位置，不自行分配轮次或争写共享索引。独立 Breakdown 尚无 Build 时，可在任务根的 `tickets/` 交付；独立审查或修复采用给定位置，不强制创建 Task 或 Build。

旧任务根已有 `work.md`、`tickets/` 时按原路径恢复，不自动搬迁；下一次真正的新交付才按需采用 `builds/<round>/`。轮次结束保留当时的范围、依据与真实结果；当前规格的修订按 [任务变化](task-changes.md) 保留可找回的旧批准依据。

过程资料仅本地保存，不暂存、提交或推送。临时脚本放当前工作位置的 `tmp/`，清理仅按明确请求。新目录、换会话或重入方法都不产生新授权，也不重置同一未完授权的修复额度。
