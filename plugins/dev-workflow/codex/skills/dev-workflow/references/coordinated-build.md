# 跨上下文实施

需要跨上下文实施或委派时读取。

## 派发

采用 Build 已核对、可独立接手的当前工作项和本轮写入位置。共享接口尚未明确时先调查，或由前置纵向切片产出并验证，不能让多个实施者各自猜定。

按歧义、依赖耦合、验证难度和遗漏代价选择足够能力。较弱实施者获得必要领域背景与例子；跨域判断仍过多时调整任务或执行能力。

工具与授权具备时默认顺序委派。每项提供当前任务、适用规范/接受设计、允许写入范围和验收重点，使用 `dev-implement`。只有接口、写入、验证环境独立且有集成收益时才并行；当前协调者维护共享 Work／tracker。

本地Spec、附件、未提交合同和Ticket不会自动进入另一 checkout。派发前核对实际可读的当前版本；需要时传递受控材料。另一 checkout 取得不了当前资料时，可在具有这些资料的同一有效工作区顺序执行；任何路径都缺资料时先报告。工具或委派权限不足时说明；当前代理在已有授权内能可靠完成的工作可直接执行，明确要求隔离却无法满足时保持受限。

## 在途变化与恢复

实施者发现材料变化时返回证据和影响，暂停受影响修改。决定更新后，同步相关任务与验收；原执行者确认取得新依据，或安全结束后再接续同一范围。已完成的受影响结果重新核对，真正独立且不受风险影响的部分可继续。

恢复先核对实际工作区、执行者状态和已有预算。原任务终态不明时暂停重叠写入；完成结果须有可访问变更与验证，不以消息自述代替。接纳后保留任务定义及本次实际结果。
