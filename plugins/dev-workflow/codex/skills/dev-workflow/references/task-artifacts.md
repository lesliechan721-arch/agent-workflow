# 任务资料与交接

持久化、长原型、跨上下文、任务恢复或准备保存基线时读取。阶段是否完成由实际共识与成果决定，资料用于保留这些事实。

## 一个当前位置

优先明确路径，其次当前任务位置，再按项目约定；新持久任务没有约定时可采用 `docs/dev/<task-slug>/` 并说明。给 Prototype 具体原型位置，给实施者和审查者可访问的任务、规范主题、附件与证据。已有 issue、ADR 和设计资料按明确指针复用。

临时会话中的关键证据在失效前保存到任务或组织认可的位置，保留来源与适用版本。专业 Skill 的独立默认位置仅在没有调用位置时使用。

## 不同资料的消费者

| 资料 | 保存的独有内容 | 下一接收方 |
| --- | --- | --- |
| Shape／决定记录 | 当前答案、条件、例外、必要理由、确认来源、开放问题和委托 | 用户、规格作者及后续需要解释决定者 |
| 原型与接受说明 | 可重放产物、版本、接受关系、允许变化和演示边界 | 规格作者、实施者与审查者 |
| Spec及规范性附件 | 按主题组织的完整当前行为、重要设计、精确合同、验收与自由 | 用户审核和后续执行的规范入口 |
| Ticket／issue | 对应需求、当前完整工作结果、适用规范、实施安排和验证 | 独立实施者 |
| Work／tracker | 任务索引、实际进度、原始审查范围、在途执行者与下一步 | 当前或接手的协调者 |
| Review与证据 | 被审范围、实际判断、问题、关闭证据与限制 | 用户和修复协调者 |

每项规则有明确当前定义。决定记录保存来源与成立条件；Spec综合当前规范；Ticket可以共置关键提醒，但不能产生另一份独立定义。冲突按实际来源查明，不凭文件名或新旧顺序静默覆盖。实施结果和状态更新保留原任务定义。

## 阶段交接与人审

交接让接收者恢复当前目标、确认依据、必要规范与项目事实、已完成结果、开放问题、授权及下一步。按实际需求持久化；现有等价工件足够时直接复用，小任务可在对话完成。

对齐按主题确认，保存用户实际回答及成立条件。规格呈现主题全貌和审阅路径，材料风险与兼容变化可见；精确技术规范可以展开或放附件，但约束效力保持。用户要求审核的技术选择同样进入显式审阅范围。批准对应实际展示的内容、版本及委托，不以模型自述或摘要替代。

修订给出实质变化及其影响，等价移动和措辞整理与材料变更分开。新决定更新相应规范、Ticket和验收，向受影响子代理传达当前依据并确认接收；已完成的相关结果重新核对。旧预算与用户停止点继续有效。

## 实施前保存点

长 Shape／原型迭代、跨会话或交接前，当前协调者主动保存已确认主题、接受证据和明确的开放问题；需要本地 commit 时先取得该范围授权。Spec批准后若将独立交接或暂停，可保存对应规范与确认依据。

Spec确认与首批任务准备连续进行时，合为一次实施前基线即可：当前规范及被纳入资料、批准来源和可派发任务。Build在首次实施前按其Checkpoint规则处理该保存点，外层采用同一结果，不重复提交。

资料保存前核对语义保真、引用可达、相互一致、状态如实及敏感内容隔离。代码尚未实施时，用资料核对和实际原型验证说明保存质量，不要求未产生的产品测试结果。相应Git能力按精确范围、正常hooks和现有授权执行；无提交或非Git路径须明确其恢复方式。

保存不产生新的用户决定或批准。明确WIP仍可记录未决问题；普通相邻步骤、每轮问答和每份报告无需各生成一次提交。后续milestone保存由Build协调，原始交付审查范围保持。
