# Dev Workflow

管理当前开发任务的整体目标、资料位置、用户检查点与交付范围。

## 选择最低足够路径

- **Fast**：范围小、低风险且可逆，必要澄清、实现与验证能在当前有效上下文完成；默认不建立持久流程文档。
- **Standard**：需要跨上下文共识、正式规格与批准、任务交接或进度恢复。
- **Assured**：安全、权限、生产数据、迁移或不可逆副作用需要项目提供额外隔离、证据、授权和回滚保障。

先暂定，发现范围或风险变化时说明并升级。子代理使用与风险等级分别判断。

## 从当前缺口继续

1. 读取用户请求、当前确认或批准、接受设计及适用项目约束，区分已确定要求、明确委托的选择、模型提案与开放问题。说明当前理解和真正需要用户决定的内容；已有依据充分时直接复用，文件名或模型写出的“已确认”不是额外确认。
2. 需要持久化、恢复或即将调用会保存或迭代产物的能力时，先读取 [任务资料](references/task-artifacts.md)，选定本任务位置并贯穿后续能力。转交前提供具体产物位置与访问条件；纯对话澄清无需预建目录。
3. 新功能或行为变化缺少当前有效共识时先对齐。事实自行调查；会改变用户结果、范围、验收、兼容或风险的选择，依据用户答复或明确委托确定。局部选择直接询问，有界访谈使用 `decision-grill`，需体验或实验才能决定时使用 `decision-prototype`，多个关联决定或问答与证据往返时使用 `decision-shape`。只重开受影响问题；Fast 同样适用。
4. 待决定的材料问题解决或在明确委托内确定后，才将其作为规范、可派发任务或正式实施的依据；获准的调查和原型可先开展。Fast 沿当前答复直接进入 Build。Standard/Assured 用 `dev-spec` 综合规范、`dev-review-spec` 对照原始来源独立审查；问题关闭且覆盖充分后，请用户批准当前 Spec 及纳入的设计，取得适用批准后再实施。
5. 使用 `dev-build` 主动组织分解、合适实施者、集成验证、正式 Code Review 和授权范围内的修复。完整交付请求涵盖合理的本地实施与检查；委派、成本和副作用仍遵循当前权限。
6. 任一阶段的新证据引出材料选择或使旧依据失效时，暂停受影响工作，说明原决定、新事实、后果与可行选项并组织对齐。取得结论后更新受影响规范、任务和验收；已批准内容发生材料变化时重新审查并确认适用批准，相关执行者取得当前依据后恢复。预算和人类停止点继续有效；交付依据当前完整结果的审查覆盖。

## 用户与记录

模型自主调查事实、组织方法并决定保持公开结果等价的局部工程实现；完整交付授权不替代尚未委托的产品取舍。用户原始请求已明确的内容无需重复确认。需要用户选择时，给出足够背景、推荐及主要代价，等待实际回答后再开展依赖该决定的产品修改。

Fast 的源码、测试和临时原型是工作产物；其正式 Code Review 可在对话中完成。持久路径由协调者提供给专业能力，正式报告的保存和历史策略属于本任务。

已有实质 Spec 问题且修订在当前授权内时，读取 [规格修订](references/review-repair.md)，由当前协调者在适用预算内判断继续或暂停。修订与独立复审完成后，仍请用户批准当前 Spec 及纳入的设计。代码修复由 Build 协调者处理，旧授权与停止点在恢复后继续有效。
