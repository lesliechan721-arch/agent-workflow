# Dev Workflow

管理当前开发任务的整体目标、资料位置、用户检查点与交付范围。

## 选择最低足够路径

- **Fast**：范围小、低风险且可逆，必要澄清、实现与验证能在当前有效上下文完成；默认不建立持久流程文档。
- **Standard**：需要跨上下文共识、正式规格与批准、任务交接或进度恢复。
- **Assured**：安全、权限、生产数据、迁移或不可逆副作用需要项目提供额外隔离、证据、授权和回滚保障。

先暂定，发现范围或风险变化时说明并升级。子代理使用与风险等级分别判断。

## 从当前缺口继续

1. 读取用户目标、已确认对话、Shape、Spec、任务及审查。按内容判断共识和当前进度，复用已有有效资料。
2. 需要持久化、恢复或即将调用会保存或迭代产物的能力时，先读取 [任务资料](references/task-artifacts.md)，选定本任务位置并贯穿后续能力。转交前提供具体产物位置与访问条件；纯对话澄清无需预建目录。
3. 局部疑问直接提问；有界访谈使用 `decision-grill`，独立体验/实验问题使用 `decision-prototype`，需要多轮问答与证据切换时使用 `decision-shape`。Fast 同样先补足必要共识。
4. Fast 的行为、边界和验证足够后进入 Build。Standard/Assured 用 `dev-spec` 综合规范，并用 `dev-review-spec` 对照原始来源审查；必要覆盖充分且影响批准的实质问题已关闭后，再请用户确认当前 Spec 及被纳入的设计依据。否则先处理问题或补充证据，不进入批准和 Build。材料变化重新确认。
5. 使用 `dev-build` 主动组织分解、合适实施者、集成验证、正式 Code Review 和授权范围内的修复。完整交付请求涵盖合理的本地实施与检查；委派、成本和副作用仍遵循当前权限。
6. Build 暴露材料问题时回到相应决定；因预算耗尽或人类检查点停止时交还用户。根据两轴审查的实际覆盖与未关闭问题判断交付，已有有效整体审查直接复用。

## 用户与记录

模型负责判断何时对齐、分解、审查或建议 checkpoint；用户负责材料选择与必要授权。说明当前路径、采用的方法和需要用户决定的一件事。

Fast 的源码、测试和临时原型是工作产物；其正式 Code Review 可在对话中完成。持久路径由协调者提供给专业能力，正式报告的保存和历史策略属于本任务。

已有需修订的 Spec Review 且修订获准时读取 [规格修订](references/review-repair.md)。代码修复由当前 Build 协调者处理，旧授权与停止点在恢复后继续有效。
