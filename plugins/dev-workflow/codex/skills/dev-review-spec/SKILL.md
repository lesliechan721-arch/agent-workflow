# Dev Review Spec

审查文档质量，不批准产品选择，也不启动修订或实施。

## 当前角色与独立性

当前未参与目标的实质设计、起草或修订，且未继承作者推导与预设结论时，直接审查。原始需求、确认、原型、代码、测试和旧 finding 是正常依据；提出问题不等于参与修订。

带有作者工作历史时，由组织者安排干净的独立审查上下文。已经受委派且合格的审查者直接完成本轮范围，不重复委派。角色不清时核对实际参与和历史；缺少隔离能力时说明限制，作者自检不能冒充独立审查。

## 确定检查范围

固定目标、版本、纳入的附件与接受设计。首次完整审查读取全部规范及必要来源，包括任务已提供但文档漏引的材料。已有报告或明确复审时，先用 [按影响复审](references/rereview.md) 确定本轮检查、证据复用和执行者；不能把只核对旧问题称为完整通过。

## 按来源核对

| 判断 | 本轮范围内检查什么 |
| --- | --- |
| 语义保真 | 对照原始请求、实际确认／委托及项目合同，核对来源覆盖、条件、例外、精确值与单位、约束强度、重要设计、内部一致性和自主空间；提案不当作批准 |
| 人审可读性 | 沿主 Spec 能否理解改变、关键场景、取舍、风险与验收，实质变化是否可见；不能靠额外阅读页弥补主文或用附件隐藏后果。图或视图须与完整来源的版本、状态和含义相符 |
| 设计必要性 | 按项目复杂度门槛检查新增机制的当前需求、消费者或风险依据，并比较更简单实现与恢复渠道。无必要的抽象、持久状态、扩展承诺及过早固定的实施安排应说明具体代价；保留必要安全、兼容与恢复约束，不以篇幅、术语或个人架构偏好判错 |
| 实施与验收 | 新上下文能否取得完整定义并验证结果；原型版本、页面／状态、保留关系、允许变化及演示边界是否足够；局部工程自由不强制提前决定 |

正文与纳入附件中的规范同等有效，仍受原始确认约束。活动任务可完整保存在本地；拟长期交付的资料不能在任务目录删除后丢失唯一必要定义或设计。目标可先于实现，已有支持、运行或兼容性声明则需实际证据。

## 报告

报告先说明结论与覆盖，长报告可使用 [规格审查模板](assets/spec-review-template.md)。实质问题给出位置、来源差异、具体错误结果或审阅障碍、影响和关闭条件；建议与未知分开。已确认机制的简化机会只能提议变更，不能自行撤销共识。

结束前核对目标未变，说明本轮检查、沿用证据及当前完整范围的缺口；保留已确定问题，不用测试全绿替代规范依据。默认在对话中交付，明确要求保存时采用指定位置或项目约定。被审文档与实现保持不变。
