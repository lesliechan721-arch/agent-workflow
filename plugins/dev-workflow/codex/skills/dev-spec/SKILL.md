# Dev Spec

形成当前交付的规范入口，使新上下文实施者和审查者能理解预期结果、重要设计与验证依据。

## 综合当前共识

1. 读取用户原始要求、已确认对话或 Shape、有效反馈、接受的原型和适用项目契约。沿引用区分确认、明确委托、模型提案与未决事项；文档自述“已确认”需有实际来源。来源缺失、冲突或新事实使旧依据失效时，先说明受影响的决定。
2. 使用 [规格模板](assets/spec-template.md)，覆盖范围内的用户行为、角色与关键状态、接口/数据语义、重要实现决定、失败和兼容边界、验收及实现自由。保留已作出的工程决定；schema、类型或短逻辑片段比文字准确时使用它们。
3. 涉及已接受原型时，明确产物与版本、适用页面和状态、须保持的关系与行为、允许变化及演示排除项。可视资料本身可作为规范的一部分；文字概括说明它具体约束什么以及怎样查看。
4. 从原始来源核对材料决定和设计要求的覆盖，再从规格核对各项依据。仍缺会改变交付的材料决定或必要证据时，先交付缺口及其影响，保留原有规格；用户明确要求未定稿时才按该要求写入并标明待确认部分。事实调查与用户产品选择分别处理。
5. 规范性内容正面表达当前合同。已确定的接口、模块责任和测试边界保留；尚未固定的局部组织、算法或任务顺序交由实现者选择。独立公共契约可引用现有权威资料，较大的独立设计主题可按需要拆附录。
6. 修订聚焦已有来源支持的问题或用户实际确认的变化。未决选择交回用户或当前协调者，确认后同步受影响的验收与引用；受委托的局部工程决定可在其边界内明确。完成前核对源决定、原型、规格和项目硬约束一致。

## 完成与交付

新上下文可从本规格和明确可访问的引用理解完整当前要求、重要技术约束及完成标准；仍可能改变方向的材料问题或证据缺口应明确说明。

按请求交付正文或文件。写入位置采用用户/调用者给定路径或项目约定；仅要求内容时在对话中给出。说明实际交付位置及未解决问题，后续执行由调用者决定。
