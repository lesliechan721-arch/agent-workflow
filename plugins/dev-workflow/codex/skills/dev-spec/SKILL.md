# Dev Spec

Spec 是已经形成决定的记录。它固定材料性共识，不预测全部实施细节。

## 产物位置

优先使用用户或调用者给定的路径，其次遵循仓库约定。都没有时写入：

```text
docs/dev/<task-slug>/spec.md
```

## 工作流

1. 收集已确认的决定、仓库事实、Prototype 结论、现有约束和适用的 Spec Review findings。
2. 使用 [Spec 模板](assets/spec-template.md)。只写会影响材料结果或验收的内容。
3. Prototype 的稳定结论进入规范性章节；仍支撑当前决定的原型、研究和 ADR 作为 Evidence 链接。被替代方案、用户反馈和实验过程只有在安全、兼容、迁移、回滚或高概率重复决策需要时才保留为 Evidence。
4. 技术细节只有在满足至少一项时进入 Spec：用户需要理解或授权；两个合格实现者可能产生材料性不同结果；必须跨上下文保存；判断交付必须依赖它。
5. 文件拆分、局部算法、类型设计、测试组织和任务顺序写入 `Agent discretion`。
6. 修订 Review findings 时，只修复当前 blocker、必需影响面和直接连带问题，不把单个 finding 扩展成通用流程规则。
7. 完成前把规范性章节归一为当前有效合同：正面陈述当前选择、约束和验收；讨论顺序、reviewer 指令和已被替代的方案不进入规范性章节。

## 完成条件

- 用户可观察行为、范围、材料决定、验收、风险和实现自由清楚。
- Open decisions 为空，或只包含明确委托给实现阶段的非材料事项。
- Spec 内部和它引用的证据没有材料冲突。
- 规范性章节只描述当前有效结果，不回放中间方案或 Review 过程。

## 输出

```text
结果：complete / blocked
产物：<Spec 路径>
未解决：<材料决定、证据缺口或无>
建议动作：<补充决定 / 收集证据 / 规格审查 / 无>
```

材料决定未解决时建议补充决定；需要体验或实验依据时建议收集证据；Spec 完成或修订后建议规格审查。
