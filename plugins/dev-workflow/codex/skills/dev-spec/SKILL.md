# Dev Spec

形成当前范围的完整规范，供用户审阅和新上下文实施。优先沿用指定位置或项目约定；普通任务需要持久规格且无当前位置时，使用 `.dev-workflows/<task>/spec.md`。受影响的现有公共合同在原位置维护，本次变更引用其适用定义。

## 综合

1. 读取当前规格、原始请求、实际确认或委托、相关项目合同与代码、领域决定和接受设计，区分已定要求、提案、开放问题与事实证据。影响结果的来源缺失或冲突先明确；新增材料选择交回用户或当前协调者。
2. 使用 [规格模板](assets/spec-template.md)，按能力或决策主题组织结果、行为与验收。保留条件、例外、精确值、约束强度、已定技术选择和实施自由；schema、类型或短逻辑更准确时采用。所有需用户判断的后果完整可见，正文与纳入的规范附件同等有效。
3. 原型保留实际产物及查看入口，明确接受版本、适用页面/状态、须保持的关系、允许变化和演示边界。多个主题、复杂来源或重组规格时读取 [信息组织与保真](references/information-architecture.md)，只引用本次适用且可访问的内容。
4. 从来源检查材料要求是否完整保留，再核对新增规定是否有依据。修订说明实际语义变化及其范围，等价重排单独说明；目标先于实现时如实表达，运行或兼容性结论依实际证据。

## 草稿与交付

用户明确要求未定稿，或当前协调者已有本地草稿写入授权且需要恢复时，可以保存已确认内容和标明的开放问题；草稿不构成批准。其他情况先报告影响规范成立的缺口。

按请求返回正文或文件。普通任务规格及附件仅本地保存；写入前核对权限和忽略条件，不具备时先交付正文并说明。交付完整入口、必要附件/设计、确认来源、本次变化及未解决事项，使接手者无需原作者私有记忆即可理解当前要求。保留当前仍需的依据，结束本次规格编写。
