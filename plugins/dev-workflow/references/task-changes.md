# 任务变化

新事实可能影响当前要求、接受设计或风险，或影响尚不确定时读取；修订已有规格，以及交付后继续工作需处理历史依据与新范围时也读取。先判断是否缺少有效决定，再处理受影响内容；文件归属由 工作目录（`references/local-workspace.md`） 决定，不与问题分类绑定。

## 先判断差异

| 当前事实 | 处理 |
| --- | --- |
| 实现不符合仍有效的要求，修复不改变用户结果、接受设计或风险 | 作为缺陷，在有效修复授权与预算内处理，不改规格来迁就错误实现 |
| 局部工程选择变化，但合同、验收及风险等价 | 在原自主空间内实施，补相称验证；不重开需求设计 |
| 新事实使用户行为、接受设计、范围、成本或风险需要新决定 | 暂停受影响工作，交付缺口，由用户或当前用户协调者决定后续设计；独立部分可继续 |

缺口应包含原要求及确认来源、已完成且验证的结果、尚未满足内容、新事实和影响、待决定的问题，以及已有授权、累计预算和停止点。沿用对话、Work 或现有报告，不为它新增状态协议。缺少运行证据与确定产品缺陷分别记录；暂停不等于取消或回滚。

## 当前依据与历史

同一 Task 的规格保存当前完整要求。新决定取得有效确认后原位修订，说明变化及确认来源；缺陷修复不改规格迁就实现，未变含义和确认直接复用。当前公共合同同样只按获准的产品变化更新。

替换旧批准依据前，核对已结束 Build 和当前修订是否仍需引用它。已有可访问、可定位的历史版本足够时复用；否则按需保留旧规格、纳入的规范附件和接受设计。仅有一个以后会变化的 `spec.md` 链接不够，默认本地资料也不能假设由 Git 保存历史。旧 Work 的依据须能找回原内容；归档不要求每轮复制完整 Spec，也不增加摘要或状态协议。

已结束 Build 的范围、接受记录与交付结果保持历史原样，后来发现问题可在后续记录中注明，不将旧结果改成已经满足新要求。同一目标的后续修复或需求调整仍可在原 Task 继续，不必另造补丁需求。只有独立新目标才另建 Task。

Build 和 Review Loop 返回缺口，不自行启动设计。用户或已获设计授权的 Workflow 协调受影响主题的设计；设计阶段采用其自带方法，其他执行者不通过读取共享方法自动升级为完整流程。原完整实施授权不自动允许改变产品取舍。

取得新依据后，同步相关规格、视图、任务、在途执行者与验收，再恢复受影响实施；重验已失效的结果，复用仍有效的部分。新一轮实施从当前代码、当前要求、本次反馈和前轮结果确定差异，不重做全部旧工作项。同一未完授权沿用累计预算和停止点；后续工作按用户实际新授权确定预算，不能靠改名取得额度。
