# 任务变化与后续工作

实施中新事实影响已定要求，或处理已交付／中止任务的后续问题时读取。任务规格记录当时的承诺；当前公共合同描述现行产品，两者的维护方式不同。

## 先判断差异

| 当前事实 | 处理 |
| --- | --- |
| 实现不符合仍有效的要求，修复不改变用户结果、接受设计或风险 | 作为缺陷，在有效修复授权与预算内处理，不改规格来迁就错误实现 |
| 局部工程选择变化，但合同、验收及风险等价 | 在原自主空间内实施，补相称验证；不重开需求设计 |
| 新事实使用户行为、接受设计、范围、成本或风险需要新决定 | 暂停受影响工作，交付缺口，由用户或当前用户协调者决定后续设计；独立部分可继续 |

缺口应包含原要求及确认来源、已完成且验证的结果、尚未满足内容、新事实和影响、待决定的问题，以及已有授权、累计预算和停止点。沿用对话、Work 或现有报告，不为它新增状态协议。缺少运行证据与确定产品缺陷分别记录；暂停不等于取消或回滚。

## 选择修改对象

尚在执行的同一任务，经有效确认后可修订当前规格；用已有版本、保留副本或追加修订保留原批准依据与变更原因。不能覆盖原基线后声称原要求已满足。更新后的规格与任务、在途执行者和验收必须同步，再恢复受影响实施。

已完成或明确中止的任务规格、接受记录和交付结果保持历史原样。后续工作引用它们及当前代码事实：恢复原合同的缺陷可直接建立有界修复请求；改变需求或设计则建立关联的后续任务，由 `dev-design` 形成新依据。小修复无需复制完整旧 Spec，也不必创建新的正式规格。不得为绕过修复额度把同一未完授权改名为新任务。

Build 返回缺口而不自行启动设计。当前用户协调者仅在已有授权涵盖该设计工作时使用 `dev-design`，否则交付选择并等待决定；原完整实施授权不自动允许改变产品取舍。后续设计以实际完成状态为起点，明确复用、保留和替换的结果，不重做无关部分。

当前公共合同在获准改变产品行为时原位更新；历史任务只作为来源引用。新任务采用其实际授权与预算，同一任务恢复沿用旧额度。
