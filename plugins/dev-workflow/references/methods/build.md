# 实施协调与交付

供已启动的 Build 或 Workflow 采用。当前协调者拥有本轮范围、依赖推进、集成和交付；工作项实施与独立判断由对应能力负责。采用本方法不增加产品决定权、执行者或新的授权。

## 确定本轮工作

1. 读取当前请求、实际确认与实施授权、适用规范和接受设计、相关代码及已有结果。输入可为请求、问题清单、工作项或 Spec；没有 Spec 文件不阻止目标充分的工作，文件自称批准也不构成确认。
2. 区分首次实施、未完恢复和交付后的继续工作。需要持久协调时按 [工作目录](../local-workspace.md) 确定归属，沿用用户位置和已有 tracker；多任务、在途执行者或恢复需要时采用 [工作索引](../../assets/work-index-template.md)，短任务不强制落盘。
3. 固定本轮承诺范围、代码基线、当前有效要求与验收。后续 Build 从当前代码、本次反馈和前轮结果确定待完成差异，复用未受影响且仍有效的成果，不重新执行所有旧 Ticket。未完成范围恢复保留原始基线、累计预算和停止点；恢复已有修复范围时，在产品写入前按 [代码修复](../code-repair.md) 核对额度，预算耗尽也先核对。
4. 核对已有工作项。多上下文实施前须具备可独立接手的任务、真实依赖、共享接口、写入范围及验收；不足时使用 `dev-breakdown` 补足，只补缺少的安排。单个连贯工作项不强拆，文件数量不是分解依据。关键产品决定缺失时按下文变化处理。

## 实施与集成

当前上下文足够的机械修改直接执行和验证；受规范、设计或接口约束的工作项使用 `dev-implement`。需要独立交接、局部实施挤占协调上下文或用户要求委派时，读取 [协调实施](../coordinated-build.md)，传递本轮实际依据和位置。

接纳实际 diff、任务验收和设计对照，再作组合验证。进度更新保留任务正文，已收到“完成”消息不等于集成完成；普通工作项执行相称验证。

公共基础即将被复用、重要风险或迁移转换、代表性设计推广、高返工代价集成时，先对当前累计范围进行里程碑核验。以工作区或已有 commit 的当前版本为审查对象，协调同一范围的并发写入；结果或有效依据变化时重验受影响结果。按下节提供该阶段的完整承诺范围并采用 [有界核验修复](review-loop.md)，后续未承诺功能不纳入本次核验。阶段验收、必要独立覆盖、问题关闭及用户额外条件满足后再解锁依赖；真正独立且不受风险影响的任务可继续。Git 提交不是阶段条件。

## 核验与交付

当前实施和集成验证后，采用 [有界核验修复](review-loop.md)，从本轮原始代码基线核验全部当前承诺范围；提供当前有效要求、接受设计、该基线、授权、已用预算，以及各旧报告的原版本和范围。核验方法拥有审查、必要修复及覆盖核对，Build 采用结果，不重放同一循环；局部通过不能替代整体覆盖。

交付前核对实际结果、未关闭问题及证据限制，受影响公共资料与实现一致。保留本轮范围、可找回的依据和真实结果；当前 Task 的完整规格可以继续演进，不将旧轮次改写成已经满足新要求。公共资料只维护确有后续用途的概念、理由、合同和接受设计，任务规格不必全部转为永久文档。

## 变化与恢复

已明确属于现有合同内、且不改变用户结果、接受设计或风险的实现缺陷，在原授权与预算内修复，不改规格迁就实现。变化可能影响要求、接受设计或风险，或对此尚不确定时，读取 [任务变化](../task-changes.md) 判断是否需要新决定。需要修订规格，或交付后继续工作需处理历史依据与新范围时，也读取该资料。需要新决定时暂停受影响工作，按该文档交付缺口；不自行启动设计。新依据有效后同步任务和在途执行者，重验受影响结果。

恢复先核对真实工作区和在途任务；终态不明时暂停重叠写入。取消仅按授权处理本任务未完成变更，保护无关工作；提交、推送、清理和其它外部动作分别按实际授权执行。
