# Dev Breakdown

形成当前足够的实施安排，不重写需求，也不预测全部实现细节。

1. 读取请求和已有决定、工作项及相关代码。已有可靠分解时复用或只修订受影响部分。
2. 按可以独立演示或验证的结果拆分，记录真实的先后依赖。机械大改可按安全迁移批次处理，不强迫所有工作使用同一种切片方式。
3. 展开到下一批工作能在一个 fresh context 中开展即可；远期保持粗粒度。只剩一个自然工作项时直接说明，不为了分解而生成 work 文件。
4. 每个工作项说明交付什么、依据在哪里、什么工作阻塞它、如何验证，以及已知共享接口或冲突区域。文件路径是定位依据，不是固定逐文件实施程序。
5. 只在错误会向大量下游传播或风险明显增加的边界建议 milestone Review。是否 checkpoint 提交由已有授权决定，分解本身不授予提交权限。
6. 用户需要持久交接时遵循其路径或仓库约定，使用 [工作记录模板](assets/work-template.md)；已有 tracker 则使用它，不重复建一份状态。

分解和任务顺序属于可变实现安排，不要求另一次规格批准。暴露材料决定、范围变化或新增成本/权限时，说明问题并等待确认。不要修改产品代码或启动 worker。

向用户说明建议的工作粒度、真实依赖和下一批可开展的工作；格式按当前载体组织。
