# Dev Build

协调当前授权范围的实施闭环。直接使用时也能从请求和现有资料建立工作，无需父流程私有状态。

## 准备与执行

1. 读取目标、有效 Spec/issue、设计依据、任务和 Review；确认实施授权，保留任务原始审查基线。已有任务产物位置继续沿用；确需新增持久记录时采用用户位置或项目约定，并说明选择。
2. 一个自然工作项可直接使用 `dev-implement`。需要交接或多结果实施时，评估已有任务是否具备目标、约束、来源与验收；不足则用 `dev-breakdown` 补成可派发 tickets。规范决定与实际代码调查由协调者先对齐。
3. 需要多个实现上下文时读取 [协调实施](references/coordinated-build.md)，按任务难度和可用能力匹配实施者。优先可靠的顺序执行，独立性和集成收益明确时采用并行。
4. 接纳结果时核对实际 diff、相关测试和设计对照证据。任务正文与验收保持可重派，状态与集成证据附着于任务；只有 tracker 不足以支持恢复时使用 [工作索引](assets/work-index-template.md)。
5. 公共基础、高风险边界或重要集成需要独立检查时，读取 [审查安排](references/review-planning.md)，先审明确的当前范围，再解锁依赖。普通工作项执行相关验证即可。
6. 整体实现和集成验证完成后，使用 `dev-review-code` 对原始任务范围内的完整当前结果进行双轴独立审查。提供 Spec、任务、被接受的原型和可访问的证据；确认质量与覆盖充分后交付。

## 主动判断与权限

完整交付请求中的本地实现、验证和有界缺陷修复按现有授权执行；只审不修的请求保持只读。已有实质问题需要修复时读取 [Review 修复](references/review-repair.md)，说明适用预算并按证据续修或提前暂停。

达到有恢复/审计价值的保存点，或需要讨论历史整理时，读取 [Checkpoint 与历史](references/checkpoints.md)。模型选择时机；已有授权则执行，否则主动请求具体授权。委派和外部动作受当前平台与项目权限约束。

## 交付与恢复

材料决定、Spec、风险或权限需要改变时暂停受影响工作；证据不足时安排对应验证或说明缺失条件。Review 的无问题结论只覆盖其实际检查范围，阶段结果不能替代完整交付审查。

记录实际结果、未关闭问题、验证限制和相关位置。需要持久报告时由本次协调者提供保存位置和历史要求。恢复时检查真实任务、代码与证据，沿用有效授权、已用预算及人类检查点。
