# Dev Implement

依据现有共识完成一个受约束、可独立验证的工作项。输入可以是当前请求、Spec、issue 或委派说明；按内容确认范围、验收和必要来源。用户明确选择本 Skill 时，也可直接完成其指定的小任务。

## 实施

1. 读取当前任务、适用 Spec/issue 主题及规范性附件、重要决定、必要代码和验收；实际查看原型页面/状态、接口或样例。摘要不能替代被引用的条件、例外和精确合同。委派时只接纳当前范围；关键行为未决定或依据不可取得时说明缺口。
2. Review 修复先读取当前 blocker 和关闭条件，只修分配给本次任务的 blocker、必要影响面和直接 regression；未能关闭的项目必须披露。
3. 选择满足当前合同和仓库结构的最小完整改动。新增抽象、fallback、配置或相邻重构须有当前消费者、项目硬要求或真实缺陷依据。
4. 最终产物表达当前有效行为、接口和必要理由，保留安全/兼容约束及非显然陷阱。实现说明按当前消费者需要组织。
5. 在稳定行为边界上优先使用 red-green。遵守项目测试价值门；没有规则时，测试保护可观察行为、公开合同、已知 regression、安全/数据边界或确定性工具合同。
6. 验证约束面向消费者依赖的公开合同。已确认的可见布局和交互属于验收对象；DOM/CSS 组织等局部实现可等价调整。精确字节、全文快照或 hash 检查仅在精确内容本身是公开合同时采用。
7. 实际运行与变化相称的测试、检查或行为验证，修复后再验证。涉及已接受设计时，在相应数据、视口和操作状态下对照真实实现与设计依据。分别报告实际检查、观察结果和未覆盖部分。

## 边界

当前工作项过大、新事实产生未确认的用户行为，或使现有需求、设计和跨模块契约的依据失效时，暂停受影响修改，给出真实证据、原要求及后果。受委派者交回当前协调者，独立执行时直接向用户确认。得到实际答复或明确委托并取得更新后的任务依据后继续；保持已确认结果和风险等价的局部工程选择可自主处理。破坏性、远程、凭据、显著成本和不可逆动作仍需明确授权。

独立工作时可保存必要任务笔记；协作时只更新分配给自己的产物，不争写其他任务的共享进度。是否执行后续工作项、Review、提交或部署由调用者和项目政策决定。

完成时说明变更、实际验证、未解决问题和重要发现。子代理还需提供调用者可以访问的变更位置或提交引用；无需固定 JSON 返回格式。
