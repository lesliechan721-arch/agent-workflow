# 信息组织与语义保真

综合多个决定主题、长规格、较多规范附件，或重组已有文档时读取。

## 先固定含义

按来源辨认决定的对象与范围、条件/例外、精确值、硬约束/建议、必要理由、确认依据及实施自由。已有内容缺依据时说明其性质，移动位置不等于重新批准。技术假设与实际项目事实分别核对；事实变化可能触发重新对齐。

从来源到新文档检查完整含义，再从新要求回到真实来源。复杂迁移可以临时记录原位置到新位置的映射，作为本次自检或审计；它不是所有任务必须维护的规则登记表。

## 按主题，再按读者展开

主文先说明当前目标、适用范围和主题导航；本次实质变化与确认摘要在交付说明或本地任务呈现。每个主题将结果、取舍与风险、行为及例外、精确技术定义、验收和实施自由放在关联位置。使用最能表达关系的表格、场景、类型或原型；完整性不是必须列多少条 user story。

用户需要审核什么取决于当前决定与委托，不由“产品/技术”标签或正文/附件位置决定。所有材料后果显式可见；精确协议细节可按需展开，但仍约束实施。读者可选择阅读顺序，规范内容不能因摘要而减少。

## 资料职责与引用

当前任务Spec及明确引用组成完整目标，默认在本地任务空间保存；它说明本次将改变什么，未变合同指向原定义。已有公共规范在其原位置维护适用变化，任务中仅补未被覆盖的要求。领域词汇和重要决定保存必要含义与理由；当前确认来源及开放问题保存在Spec或对应接受记录，Ticket组织实施，Work仅按需索引实施／修复事实。冲突先按实际确认和适用范围查明，不能仅以文件位置或代码现状决胜。

当一个独立技术主题很长、常被不同任务单独读取时可拆规范性附件。每个指针说明本任务读取什么、为什么需要及版本/适用范围。来源记录、参考事实和规范性附件分别标明用途；已决定内容不会因放入附件变成建议。

## 生命周期与修改

完整任务规格是开发期间的实施依据，不因本地存放而缩写为摘要。交付后的代码、类型、测试和已有公开资料承载实际行为；只有长期消费者仍需要的规范、理由或接受设计继续维护。整理长期知识不要求复制整份Spec到项目目录，尚未实现或未被其他可靠资料承接的重要信息在清理前保留。

## 修改与验证

重新排版、合并同义重述、转换表格或移动附件，先比较语义再比较长度。尤其核对“必须/建议/允许”、空值与缺失、边界时刻、凭据身份、保存与生效、目录展示与实际授权等容易被合并的区别。

自检用代表性读者问题恢复全部材料结果，并让实施者按相关主题找到精确约束。发现缺口修正该信息位置；新的产品取舍返回用户，不用补写更多通用规则代替。
