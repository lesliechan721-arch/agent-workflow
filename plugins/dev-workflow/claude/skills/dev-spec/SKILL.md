# Dev Spec

Spec 是已经形成决定的记录。它固定材料性共识，不预测全部实施细节。

## 产物位置

优先使用用户或调用者给定的路径，其次遵循仓库约定。都没有时写入：

```text
docs/dev/<task-slug>/spec.md
```

## 工作流

1. 优先读取调用者提供的 Shape/决策记录、accepted Prototype verdict、当前仓库事实和项目权威。没有持久 Shape 时，才使用当前对话中已经明确确认的决定；不要从压缩后的历史猜测缺失内容。
2. 检查是否仍有会材料性改变结果的开放决定或证据缺口。存在时停止规格化，并说明需要继续塑形的内容。
3. 使用 [Spec 模板](assets/spec-template.md)。只写会影响材料结果或验收的内容。
4. Prototype 的稳定结论进入规范性章节；仍支撑当前决定的原型、研究和 ADR 作为 Evidence 链接。被替代方案、用户反馈和实验过程只有在安全、兼容、迁移、回滚或高概率重复决策需要时才保留为 Evidence。
5. 技术细节只有在满足至少一项时进入 Spec：用户需要理解或授权；两个合格实现者可能产生材料性不同结果；必须跨上下文保存；判断交付必须依赖它。
6. 文件拆分、局部算法、类型设计、测试组织和任务顺序写入 `Agent discretion`。
7. 修订 Review findings 时，只修复当前 blocker、必需影响面和直接连带问题，不把单个 finding 扩展成通用流程规则。
8. 完成前把规范性章节归一为当前有效合同：正面陈述当前选择、约束和验收；讨论顺序、reviewer 指令和已被替代的方案不进入规范性章节。

## 完成条件

- 用户可观察行为、范围、材料决定、验收、风险和实现自由清楚。
- 没有仍会材料性改变结果的开放决定或证据缺口。
- Spec 与当前 Shape、accepted verdict 和项目权威没有材料冲突。
- 规范性章节只描述当前有效结果，不回放中间方案或 Review 过程。

完成时说明 Spec 路径和仍未解决的材料问题。若当前共识不足以写 Spec，停止并指出需要继续塑形的具体内容。
