---
name: isolating-work-with-git-worktrees
description: "当任务需要独立 Git 工作目录以保护当前工作区或并行检出另一分支时使用，例如用户明确要求 worktree、需要在不触碰当前未完成工作的情况下处理另一个独立任务，或需要同时处理多个分支。若现有环境已提供所需隔离则复用。不要仅因工作区有未提交修改或任务涉及代码修改而触发；用户要继续当前 checkout 中的同一任务且没有隔离需求时，使用当前工作区。也不要用于不需要独立 checkout 的只读检查、例行 worktree 管理或需要独立 refs/对象库的完整仓库隔离。"
---

1. **确认隔离边界。** 检查当前环境是否已有满足要求的 worktree 或 sandbox；有则复用，不重复创建。Worktree 隔离工作目录和部分 per-worktree 状态（如 HEAD/index），但共享对象库和多数 refs；需要仓库级隔离时改用独立 clone。只有平台明确提供独立 refs 与对象库时，才将其隔离环境视为等价方案。

2. **安全创建。** 优先使用平台原生的 worktree/隔离能力；没有时才使用 `git worktree`。手动创建时遵循用户或项目已有路径约定；没有约定时，默认使用仓库根目录下的 `.worktrees/<分支或任务名>/`，不要自行选择其他位置。创建前确认 `.worktrees/` 已被忽略；若未忽略，先报告并取得明确处理方式，不得擅自修改并提交 `.gitignore`。确认基点、分支和路径；不得 stash、reset、discard 当前无关修改，也不得用 force 抢占已有 worktree 或已检出分支。若隔离是任务条件，创建失败时不得静默退回当前工作区。

3. **建立可信起点。** 在开始任务操作前，确认隔离工作区的路径、基点、分支和初始状态。只运行任务所需的 setup 与基线检查；若已有失败，先报告，不要归因于本次工作。

4. **保持隔离直到交付。** 将任务操作及其产生的修改限制在该工作区，并报告路径与分支。由创建它的平台机制管理生命周期；手动清理时，仅在用户要求且无未保存工作后使用 `git worktree remove`，不要直接删除目录、强制清理或顺带删除分支。
