# Git Reconcile

保护与本次整合无关的本地修改，绝不丢弃、覆盖或混入结果；绝不执行 `git push`。仅分析时不改变任何 refs、index、worktree 或仓库对象。

1. **查明双侧意图与交互。**
   - 解决文本冲突禁止只看冲突块凭直觉选边：对照变更前基线与双侧提交历史（提交说明、代码与测试），先辨明每处差异是“一侧刻意删除”还是“另一侧新增或重构”。
   - Clean merge 只证明文本兼容，不证明组合行为成立。枚举双侧改动的公共接口、数据结构/单位、默认值、共享状态、配置与依赖；凡一侧修改了定义或语义，跨文件及同文件检索另一侧新增或改动代码中的引用与消费者，核对组合交互。

2. **协调双方意图。**
   - 意图兼容时保留双方行为，只做该交互所需的最小集成适配，不顺手做无关重构。
   - 意图不兼容但用户目标或仓库一手证据已指定优先级时，按依据取舍并说明权衡。
   - 若双方业务规则、策略或默认值直接冲突，且用户目标与仓库一手证据均无法裁决优先级，立即停在未完成状态（不提交、不继续、不擅自中止破坏现场，禁止发明折中值或自行拍板），列出双方提交与代码依据及待决问题。

3. **交互验证与原子收尾。**
   - 执行整合时，将冲突解决与必要的集成修正作为整体验证：运行项目要求的检查；若两侧原有测试未覆盖双方组合路径，补充或运行覆盖该交互的针对性验证。
   - 仅在用户授权完成、无未解决条目且验证通过后再原子收尾，否则保持未完成并报告阻塞项：
     - `merge`：确认交互无误前不提前提交，最终将冲突解决与必要集成修正收敛在**同一个**双父 merge commit，不拆成先合并再补修的多次提交。
     - `rebase` 与 `cherry-pick`：沿原操作正常继续，保留各提交语义与必要集成修正，不改用额外普通提交或破坏原有提交链。
   - 收尾后确认无遗留冲突标记、无未暂存集成修正且未混入无关文件。
