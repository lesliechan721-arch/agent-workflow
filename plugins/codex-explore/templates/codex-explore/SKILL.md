# Codex Explore

这个工作流只负责把容易污染主会话上下文的只读证据探索交给子代理。加载后先做 Gate 判断；不满足条件时交回主代理，按普通任务处理。

## Gate

只有同时满足以下条件，才继续委派子代理：
- 用户明确要求使用 `codex-explore` 做只读探索，或问题必须先做只读证据探索才能可靠推进。
- 当前 `spawn_agent` 工具公开 `agent_type`，且其 schema 公布可选值时包含 `{{explorerRoleKey}}`，可以显式选择 Codex Explore 自带的探索 role。
- 候选材料范围较大、边界未知，或位于陌生、外部、本轮尚未建立上下文的代码库、文档、网页、日志或用户材料中，需要搜索、筛选和核验证据；主代理直接处理会阅读大量可能无关的候选内容，明显占用或污染当前会话上下文。典型信号是跨 6 个以上文件、3 个以上模块、多来源资料、长日志、需要跨多个官方文档或网页检索，或大段用户材料；数量只作辅助判断。
- 能把探索工作写成具体问题，划定允许使用的资料来源，并和主代理必须亲自处理的工作清楚分离。

交叉验证或独立核对假设不能单独触发本工作流；最终答案只有一个事实并不是停止理由。正反例与数量阈值冲突时，优先判断是否需要隔离大量可能无关的探索上下文。

以下情况立即停止使用本工作流，不要启动子代理：
- 来源和候选材料已知，预计只需用 `rg` 加定向读取 2 到 3 个文件或少量明确片段即可完成，且不会读取大量无关内容。
- 用户只是顺带提到 `codex-explore` 或 `plugins/codex-explore`，但没有要求用它做只读探索，且问题本身不需要隔离探索上下文。
- 任务目标本身是实现、修改、格式化、提交或其它写操作，并且无法清楚分离出只读证据探索；或者要委派的子任务需要提权、登录、购买、发布、发送消息或调用有副作用的接口。

触发例：
- 探索 `/path/to/external-project` 这类陌生或外部源码，确认某个 API、工具名、配置项或行为约定。
- 在大型日志、多个官方文档或网页资料、用户提供的大段材料中筛选证据，最终只汇总关键结论。
- 核对一个平台事实，虽然最终答案很短，但必须先全局检索并排除多个候选解释。

停止例：
- 打开已知文件 `src/tools/foo.ts` 查看一个常量名。
- 在当前仓库 2 到 3 个已知文件里查一个字段。

## 委派规则

只使用 Codex Explore 自带的探索 role，其默认模型是 `{{explorerModel}}`，推理强度是 `{{modelReasoningEffort}}`；模型、推理强度和 developer instructions 由专用 role 提供，不在 `spawn_agent` 调用中重复覆盖。调用前以当前 `spawn_agent` 工具实际公开的 schema 为准，不按 Codex 版本号或配置文件猜测，也不得传入 schema 未公开的字段。如果工具不公开 `agent_type`、schema 明确不允许 `{{explorerRoleKey}}`，或运行时报告该 role 不可用，立即停止使用本工作流；不得启动默认子代理或改用内置 `explorer`、其它 role。

任务涉及网络、文档或时间敏感事实时，遵守当前会话的工具、联网、官方文档优先和上层安全策略。子代理继承当前会话可用的工具和权限；不能访问来源时说明限制，不能凭记忆补事实。

调用 `spawn_agent` 时始终传 `agent_type: "{{explorerRoleKey}}"` 和完整的 `message`。其它调度参数只在 schema 公开时传入：
- 公开 `task_name` 时，用小写字母、数字和下划线概括具体探索目的，如 `trace_wait_agent`；同一父任务下重名时才追加 `_2`、`_3`，不使用无语义的序号名称。
- 公开 `fork_turns` 时，传 `"none"`，避免全历史 fork 影响专用 role。

除非用户另有要求，默认启动 1 个子代理。只有多个探索问题互不重叠、彼此能独立完成且确实值得拆分时，才启动 2 到 3 个；不得超过当前可用并发槽位，任何情况下最多 4 个。

每个子代理的 prompt 至少写清：
- 范围：目录、文件、模块、网页、文档集、日志片段、数据范围或行为边界。
- 资料来源：代码库、用户内容、官方文档、公开网页、命令输出，或这些来源的组合。
- 具体问题：明确要回答什么，不要只写“看看这个模块”或“查一下资料”。
- 委派边界：明确子代理是叶子探索代理，不得调用任何子代理调度或管理工具（包括 `spawn_agent`、`send_input`、`send_message`、`followup_task`、`wait_agent`、`resume_agent`、`close_agent`、`interrupt_agent`、`list_agents`），也不得再拆子任务；如果范围过大，只说明需要主代理缩小问题。
- 只读边界：明确不得创建、编辑、移动、删除、格式化或回退文件，不得安装依赖，不得请求提权，不得登录账号、购买、发布、发送消息，或调用任何有副作用的外部接口。
- 期望输出：要求返回关键结论、证据路径或链接、必要行号、来源时间、不确定点，以及建议主代理下一步查看的内容。

## 等待与整合

### 运行与等待合同

子代理启动后，主代理不再同步调查同一个问题或同一批候选材料，只做调度、等待、整合、少量核验及不依赖子代理结论的其它工作。

主代理以当前会话中已有的工具返回和完成通知为准，识别子任务是否终态、是否有结果及结果是否已校验；无需为此创建额外文件、清单或外部状态。结果不必立即分析或校验，但未经校验不能用于最终结论。状态不明确时只用当前工具提供的查询能力核对。

按 `wait_agent` 的实际 schema 和说明选择合同，不按 Codex 版本号或配置猜测：
- 要求 `targets` 且返回 `status`：只传未终态的子代理引用，合并全部返回状态，后续只等剩余目标。
- 不接受 `targets` 且只返回消息或 activity 摘要：不传目标；非超时返回不是子代理结果，应处理随后到达的完成通知。`list_agents` 可用于状态对账，不能代替结果内容。
- 其它形态严格遵守实际 schema，不混用参数或返回语义。

同一终态可能同时出现在等待结果和完成通知中；按子任务引用去重，不重复整合或消耗恢复额度。

### 等待与调度

等待分为“常规等待”和“催促后等待”。首次最小等待为 `{{minimumInitialWaitMinutes}}` 分钟（`timeout_ms={{minimumInitialWaitTimeoutMs}}`），催促后等待为 `{{convergenceWaitMinutes}}` 分钟（`timeout_ms={{convergenceWaitTimeoutMs}}`）；它们都是单次调用窗口，不是整批子代理的总时限。

首次常规等待优先使用用户指定的单次时长，否则选择不短于首次最小等待的整数分钟；后续默认复用，任务或用户要求实质变化时才重选。只传 schema 公开的参数并遵守上下限。每次调用重新计时；工具未公开批次 deadline 或已用时间时，不计算剩余批次时间，也不承诺精确总时限。

每次等待返回或收到完成通知后，主代理只需识别原因、更新当前可见状态，再自行决定继续等待、预分析或校验已有结果、阶段性整合，或处理其它独立工作。已有结果可能改变调度时可先分析；需要共同对比或会造成重复工作时可继续等待。这些只是提示，不是固定步骤，其他子代理会继续运行。

只有 `timed_out: true` 或实际 schema 的等价结果才算真正超时。常规等待超时后不判定失败，也不重启、停止或接管同一范围；只向未完成代理发送一次非中断收敛请求，要求基于已有证据尽快返回并说明缺口。公开 `interrupt` 参数时显式传 `false`；没有安全消息能力时直接进入催促后等待。

催促后等待固定使用配置窗口；提前唤醒后仍由主代理决定下一步，继续等待就复用该窗口。只有该阶段真正超时，才停止未完成代理、判定超时失败并向用户报告缺失；不得自动重新委派，也不得由主代理静默探索同一范围。没有停止能力时说明代理可能仍在运行。

等待期间收到新用户输入时先处理；如果用户没有取消或替换原任务，随后回到原等待阶段。只有用户取消或替换任务、催促后等待超时，或确认剩余结果无论为何都不会改变结论且不属于用户要求的覆盖范围时，才能提前停止代理；不得只因先到结果看似足够而取消，提前停止须说明原因。

### 异常与结果校验

每个子任务的启动重试、异常重试、空输出补问和缺失项补问合计最多一次；等待和一次收敛请求不占额度。恢复仍使用 `{{explorerRoleKey}}` 并遵守当前 schema，不得无限重试或降级到其它代理。

- `spawn_agent` 没有创建子代理：只在错误明确属于临时传输或容量问题时用相同 role 和 prompt 重试；其它情况或重试失败均判定失败。
- 子代理进入异常终态：取消、关闭或不存在直接失败；明确属于临时运行故障的错误可重试。重试时使用原 prompt，公开 `task_name` 时换唯一名称；不要把异常前的零散内容当作结果。
- 成功终态但没有输出：先确认收到的是最终状态而不是 mailbox 更新摘要。有恢复额度且当前工具支持向原子代理补发任务时，按实际 schema 请求其只返回约定结果并再次等待；否则判定该子任务失败。
- 输出不符合 prompt 中的输出合同：仅缺少可补充内容时使用恢复额度追问；答非所问、关键结论无证据、声称写入、无法追问或补问后仍不合格时，判定无效。

多个子代理分别判断；失败不影响其它有效结果，也不能被其它结果掩盖。失败或无效内容不得整合，向用户说明类型和缺失；不得在同一轮重新委派或由主代理探索失败范围，只有用户明确同意后才能继续。专用 role 不可用时同样处理。

### 整合与清理

整合结果时，只保留关键结论、证据路径或链接、必要行号、来源时间和不确定点。不要把子代理的完整回复直接转给用户。

只有在子代理结论存在明显矛盾、缺少关键证据、或最终答案需要精确引用时，主代理才补读少量材料核验；补读范围应限于子代理指出的具体文件、行号、链接或最小必要上下文。不要把“核验”扩展成重新探索。

正常结束并读取结果后，只有当前工具列表提供 `close_agent` 时才关闭已结束代理。仍在运行的代理只在前述允许条件下按实际能力停止；没有对应工具时不发明清理步骤。`close_agent` 会关闭目标；`interrupt_agent` 若只中断当前 turn，代理仍可复用，不能当作正常关闭；`wait_agent` 也不等于关闭 agent。
