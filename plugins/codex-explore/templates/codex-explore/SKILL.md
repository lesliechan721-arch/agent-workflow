# Codex Explore

这个工作流只负责把容易污染主会话上下文的只读证据探索交给子代理。加载后先做 Gate 判断；不满足条件时交回主代理，按普通任务处理。

## Gate

只有同时满足以下条件，才继续委派子代理：
- 用户明确要求使用 `codex-explore` 做只读探索，或问题必须先做只读证据探索才能可靠推进。
- 当前 `spawn_agent` 工具公开 `agent_type`，且其 schema 公布可选值时包含 `{{explorerRoleKey}}`，可以显式选择 Codex Explore 自带的探索 role。
- 候选材料范围较大、边界未知，或位于陌生、外部、本轮尚未建立上下文的代码库、文档集、网页、日志或用户材料中，需要先搜索、筛选、排除和核验证据；典型信号是跨 6 个以上文件、3 个以上模块、多来源资料、长日志、需要跨多个官方文档或网页检索，或大段用户材料。这些数量只是辅助信号，不能单独决定是否委派。
- 如果由主代理独自完成，为了找出可靠答案预计会打开或阅读大量候选文件、搜索结果、日志、网页或用户材料，其中相当一部分可能与最终答案无关，会明显占用或污染当前会话上下文。
- 能把探索工作写成具体问题，划定允许使用的资料来源，并和主代理必须亲自处理的工作清楚分离。

交叉验证或独立核对假设不能单独触发本工作流，也必须满足上述材料范围和上下文污染条件。

以下情况立即停止使用本工作流，不要启动子代理：
- 来源和候选材料已知，预计只需用 `rg` 加定向读取 2 到 3 个文件或少量明确片段即可完成，且不会读取大量无关内容。
- 用户只是顺带提到 `codex-explore` 或 `plugins/codex-explore`，但没有要求用它做只读探索，且问题本身不需要隔离探索上下文。
- 任务目标本身是实现、修改、格式化、提交或其它写操作，并且无法清楚分离出只读证据探索；或者要委派的子任务需要提权、登录、购买、发布、发送消息或调用有副作用的接口。

触发例：
- 探索 `/path/to/external-project` 这类陌生或外部源码，确认某个 API、工具名、配置项或行为约定。
- 在大型日志、多个官方文档或网页资料、用户提供的大段材料中筛选证据，最终只汇总关键结论。
- 核对一个平台事实，虽然最终答案很短，但必须先全局检索并排除多个候选解释。

停止例：
- 打开已知文件 `src/tools/foo.ts` 查看一个常量名。
- 在当前仓库 2 到 3 个已知文件里查一个字段。

最终答案只有一个事实并不是停止理由。如果仍须在陌生或外部的大量材料中搜索、筛选和核验证据，仍应使用本工作流。正反例与数量阈值冲突时，优先判断是否需要隔离大量可能无关的探索上下文。

Gate 通过后，进入委派流程。

## 委派前判断

只把具体问题、允许使用的资料来源和行为边界都清楚，并且可以独立产出结论的只读探索交给子代理。候选材料本身可以较多或边界未知。

如果任务涉及网络、文档或时间敏感事实，必须遵守当前会话的工具、联网、官方文档优先和上层安全策略。子代理继承当前会话可用的工具和权限；不能访问来源时要说明限制，不能凭记忆补事实。

## 委派规则

只使用 Codex Explore 自带的探索 role，其默认模型是 `{{explorerModel}}`，推理强度是 `{{modelReasoningEffort}}`。调用前以当前 `spawn_agent` 工具实际公开的 schema 为准，不要按 Codex 版本号或配置文件猜测，也不得传入 schema 未公开的字段。

调用 `spawn_agent` 时始终传 `agent_type: "{{explorerRoleKey}}"` 和完整的 `message`。其它调度参数只在 schema 公开时传入：
- 公开 `task_name` 时，传当前父任务下唯一的 `codex_explore_1`、`codex_explore_2` 这类名称。
- 公开 `fork_turns` 时，传 `"none"`，避免全历史 fork 影响专用 role。

模型、推理强度和 developer instructions 由专用 role 提供，不在 `spawn_agent` 调用中重复覆盖。如果工具不公开 `agent_type`、schema 明确不允许 `{{explorerRoleKey}}`，或运行时报告该 role 不可用，立即停止本工作流，不得启动默认子代理或改用内置 `explorer`、其它 role。

除非用户另有要求，默认启动 1 个子代理。只有多个探索问题互不重叠、彼此能独立完成且确实值得拆分时，才启动 2 到 3 个；不得超过当前可用并发槽位，任何情况下最多 4 个。

每个子代理的 prompt 至少写清：
- 范围：目录、文件、模块、网页、文档集、日志片段、数据范围或行为边界。
- 资料来源：代码库、用户内容、官方文档、公开网页、命令输出，或这些来源的组合。
- 具体问题：明确要回答什么，不要只写“看看这个模块”或“查一下资料”。
- 探索深度：只能使用 `quick`、`medium`、`very thorough`。
- 委派边界：明确子代理是叶子探索代理，不得调用任何子代理调度或管理工具（包括 `spawn_agent`、`send_input`、`send_message`、`followup_task`、`wait_agent`、`resume_agent`、`close_agent`、`interrupt_agent`、`list_agents`），也不得再拆子任务；如果范围过大，只说明需要主代理缩小问题。
- 只读边界：明确不得创建、编辑、移动、删除、格式化或回退文件，不得安装依赖，不得请求提权，不得登录账号、购买、发布、发送消息，或调用任何有副作用的外部接口。
- 期望输出：要求返回关键结论、证据路径或链接、必要行号、来源时间、不确定点，以及建议主代理下一步查看的内容。

## 等待与整合

### 运行边界

子代理启动后，主代理只负责调度、等待、整合和必要的少量核验，不再同步调查同一个问题或同一批候选材料。子代理运行时只能处理与其结论无依赖、不会覆盖其探索范围的其它工作；下一步依赖子代理结果时就等待。

### 等待策略

必须等子代理进入最终状态并读取结果。调用 `wait_agent` 时按当前工具实际公开的 schema 传参；按任务规模、资料量、探索深度和子代理数量设置合理的 `timeout_ms`，不要因短暂无返回而关闭、重做或反复短轮询。`quick` 可以短等，`medium` 和 `very thorough` 通常按分钟级等待。`wait_agent` 可能只返回 mailbox 更新摘要；这种摘要不是子代理结果，应继续等待最终状态通知。

### 异常与结果校验

每个子任务的启动重试、异常重试、空输出补问和缺失项补问合计最多一次。恢复时仍须使用 `{{explorerRoleKey}}`，并遵守当前 schema；不得无限重试或降级到其它代理。

- `spawn_agent` 没有创建子代理：错误明确属于临时传输或容量问题时，可以用相同 role 和 prompt 重试；参数不合法、role 不可用、权限不足或原因不明确时不要重试。无法重试或重试仍失败时，判定该子任务失败。
- 子代理进入异常终态：`cancelled` 直接判定失败；`failed` 等状态仅在错误明确属于临时运行故障时重试。重试时使用相同 role 和原 prompt，schema 公开 `task_name` 时换用新的唯一名称；无法重试或重试仍失败时，判定该子任务失败。不要把异常前的零散内容当作完整结果。
- 等待超时：超时不等于失败。先确认子代理是否仍在运行；仍在运行就按合理时长继续等待，不得仅因一次 `wait_agent` 超时重复启动子代理。只有进入异常终态后才按上一条处理。
- 成功终态但没有输出：先确认收到的是最终状态而不是 mailbox 更新摘要。有恢复额度且当前工具支持向原子代理补发任务时，按实际 schema 请求其只返回约定结果并再次等待；否则判定该子任务失败。
- 输出不符合 prompt 中的输出合同：仅缺少可补充内容、有恢复额度且当前工具支持时，按实际 schema 向原子代理追问缺失项。答非所问、关键结论无证据、声称执行了写操作、无法追问，或补问后仍不合格时，判定结果无效。

多个子代理并行时分别判断结果；一个子任务失败不影响其它有效结果，也不能由其它子任务掩盖缺失证据。子任务失败或结果无效时，不要整合或转述不可核验的内容，向用户简短说明失败类型和缺失内容。如果用户明确要求必须由 Codex Explore 子代理完成，先询问是否接受主代理继续；否则结束本工作流，由主代理按普通任务处理。这条回退规则同样适用于专用 role 不可用。

### 整合边界

整合结果时，只保留关键结论、证据路径或链接、必要行号、来源时间和不确定点。不要把子代理的完整回复直接转给用户。

只有在子代理结论存在明显矛盾、缺少关键证据、或最终答案需要精确引用时，主代理才补读少量材料核验；补读范围应限于子代理指出的具体文件、行号、链接或最小必要上下文。不要把“核验”扩展成重新探索。

### 完成与清理

工作流结束时，无论成功、失败或结果无效，只有当前工具列表提供 `close_agent` 时，才用它关闭本工作流启动且已经结束的所有子代理。没有 `close_agent` 时无需清理；`interrupt_agent` 只用于取消仍在运行的任务，不能代替 `close_agent`，`wait_agent` 也不等于关闭 agent。
