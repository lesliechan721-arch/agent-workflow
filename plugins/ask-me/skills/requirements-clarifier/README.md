# requirements-clarifier

在实施具体结果前，补齐会显著影响成品、权限、范围或验收的关键歧义。

## 什么时候使用

- 只读检查后仍有多个合理理解，选错会造成明显返工。
- 已有计划仍缺少会影响用户可见结果的局部决定。

不要仅因为任务非平凡就提问。事实可以查明、项目已有明确惯例或选择只影响内部实现时，不使用本 Skill。需要把一个计划或决定通过多轮访谈想透时，使用 `decision-grill`。

## 怎样调用

模型可以按任务自动调用，也可以显式使用 `$requirements-clarifier`。

示例请求：

- “实现前检查还有哪些会改变验收结果的需求没有说清。”
- “先查仓库约定，只问我必须决定的权限边界。”

## 会发生什么

1. Agent 先读取对话、代码、配置和文档中的可发现事实。
2. Agent 只询问仍需用户决定的高影响歧义，并说明默认值或待验证事项。
3. 回答足够实施后，Agent 把明确需求交回实现流程。

## 权限和边界

- 澄清阶段不修改文件或开始实现。
- 不重复询问已经说明的事实，也不让用户替技术事实拍板。
