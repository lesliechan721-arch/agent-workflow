# Decision Grill

围绕一个计划、决策或想法进行逐轮访谈。把重要分支说清，直到双方形成共享理解。

当前任务的产物是经过讨论的共享理解。它不是一次性分析答案，也不是 agent 为完成其它任务安排的内部计划。

若用户只要说明、比较、评估、推荐或一次性评审，直接回答原问题，不进入访谈。若当前任务是实现或修改具体结果，只需补齐局部需求歧义，使用 `requirements-clarifier`。用户或外层工作流明确要求围绕该决定进行逐轮访谈时，本 Skill 可以覆盖实施语境。

## 建立决策树

1. 先只读查看当前对话、已有决定以及相关代码和文档。能查到的事实自行确认，不把事实问题交给用户。
2. 将主题拆成相互依赖的重要决定。重点检查：
   - 目标、边界和成功标准；
   - 主要方案和核心取舍；
   - 关键假设和现有证据；
   - 失败、恢复、迁移和回退；
   - 验证方式和重新评估条件。
3. 事实由 agent 查明。需要用户权衡并承担后果的决定交给用户。不要替用户作出仍属于用户的决定。
4. 需要测试、压测、原型或外部证据才能回答的问题列为待验证事项。
5. 用户已经作出的决定，只有在依据明显不足、与其它要求冲突或主要后果尚未想清楚时才重新讨论。不要为了完整而穷举低影响细节。

## 推进当前前沿

- 当前前沿只包含前置决定已经明确、现在可以诚实回答的问题。
- 优先问能影响多个后续分支的上游决定。互相独立时每轮最多三题，一题只讨论一个取舍。
- 适合列选项时使用 {{questionTool}}；选项不能准确表达问题或工具不可用时，直接简洁提问。
- 只有存在明确依据时才给出推荐，并说明主要收益和代价。
- 收到回答后重新计算当前前沿。不要提前询问依赖尚未回答问题的下游决定。

## 收尾

当重要分支都已有决定、明确委托、转为待验证，或被明确延后并接受风险时结束；不要继续进入低影响细节。

输出简短的决策记录，按需包含：**主题与边界 / 已定决定 / 明确委托 / 待验证 / 延后及风险 / 未解决**；省略空项。明确委托必须保留责任人、期限和条件。

逐项给出决定不等于确认最终记录。除非用户明确确认记录准确，或明确要求跳过确认并直接交接，否则使用 {{questionTool}} 请用户确认记录是否准确反映共享理解。用户指出错误时，重新打开对应分支。用户确认后把控制权交还原工作流。

确认前不修改文件、不做原型，也不自行开始实施。
