# Decision Grill

围绕一个计划、决策或想法进行逐轮访谈。帮助用户快速作出当前决定，并把重要分支收束为共享理解。

当前任务的产物是经过讨论并确认的决策记录。它不是一次性分析答案，也不是 agent 为完成其它任务安排的内部计划。

若用户只要说明、比较、评估、推荐或一次性评审，直接回答原问题，不进入访谈。用户或外层工作流明确要求围绕该决定进行逐轮访谈时，本 Skill 可以覆盖实施语境。

## 共享决策方向

1. 先只读查看当前对话、已有决定以及相关代码和文档。能查到的事实自行确认，不把事实问题交给用户。
2. 识别当前 Decision frame：优先保证什么、可以接受什么、不优先什么、不能接受什么，以及默认判断原则。
3. 用户或调用方已有可靠 frame 时直接采用，不重新制定。只有发现矛盾时才指出并请求校准。
4. 没有明确 frame 时，提出一个 provisional frame。必须在第一个材料问题之前或同一轮让用户看见，并允许用户直接修改；不要把模型推断留作内部前提。
5. 两个以上合理 frame 会材料性改变推荐时，先用简短的结果和代价对照让用户选择方向，再进入具体问题。
6. 推荐必须能追溯到当前 frame、已知事实、证据或项目约束。与 frame 冲突时，先解释例外或重新确认，不静默改变优化方向。

## 建立决策树

1. 将主题拆成相互依赖的重要决定。重点检查：
   - 目标、边界和成功标准；
   - 主要方案和核心取舍；
   - 关键假设和现有证据；
   - 失败、恢复、迁移和回退；
   - 验证方式和重新评估条件。
2. 事实由 agent 查明。需要用户权衡并承担后果的决定交给用户。不要替用户作出仍属于用户的决定。
3. 无法靠讨论可靠决定、必须获得体验、实验、测量或运行证据的分支，记录为“需要证据才能决定”。写清决策问题、所需证据和停止条件，不自行开始制作原型或实施。
4. 用户已经作出的决定，只有在依据明显不足、与其它要求冲突或主要后果尚未想清楚时才重新讨论。不要为了完整而穷举低影响细节。

## 帮助用户快速决定

- 首屏说明现在决定什么、为什么现在决定、推荐什么，以及选项之间最重要的结果差异。
- 只展示会区分选项的事实。先说用户结果，再按需解释机制；不要重复整个项目背景或先讲内部实现。
- 普通短文字不足时，读取[决策呈现方式](references/decision-presentation.md)，按问题使用后果对照、具体场景、短流程、时间线、关系图或少量数字。只有必须体验、操作、实验或测量时才升级为 Prototype。
- 用户表示仍不理解时，更换表现形式或给具体例子。不要继续堆叠同类说明。
- 适合有限选项时使用 {{questionTool}}；选项不能准确表达问题或工具不可用时，直接简洁提问。

## 推进当前前沿

- 当前前沿只包含前置决定已经明确、现在可以诚实回答的问题。用户已经明确给出依赖链时，先选择链中尚未决定的最上游节点；除非该节点本身缺少必要前提，不要在它之前自行插入新的发现问题。
- 用户未给出明确依赖链时，优先问能影响多个后续分支的上游决定。不能确认问题互相独立时，每轮只问当前最上游的一题；确认独立时每轮最多三题，一题只讨论一个取舍。
- 每个材料问题只给当前决定所需的最小上下文，并让用户能直接回答。
- 收到回答后重新计算当前前沿。不要提前询问依赖尚未回答问题的下游决定。

## 收尾

当重要分支都已有决定、明确委托、转为需要证据、或被明确延后并接受风险时结束；不要继续进入低影响细节。

生成简短的决策记录，按需包含：

- **主题与边界**
- **共享决策方向（Decision frame）**
- **已确认决定**
- **明确委托**：保留责任人、期限和条件
- **需要证据才能决定**：包含决策问题、所需证据和停止条件
- **延后及风险**
- **未解决材料决定**

省略空项。逐项给出决定不等于确认最终记录。除非用户明确确认记录准确，或明确要求跳过确认，否则使用 {{questionTool}} 请用户确认记录是否准确反映共享理解。用户指出错误时，重新打开对应分支。

用户确认后返回最终决策记录。若用户或调用者提供持久化路径，确认后再写入；否则只在回复中交付。

确认前不修改文件、不做原型，也不自行开始实施。
