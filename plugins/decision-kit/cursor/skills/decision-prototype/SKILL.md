# Decision Prototype

用一个低成本、可丢弃的演示解决一个明确的产品或体验取舍。先定要校准的问题，再选最低足够的原型形态；不必先证明文字讨论失败。

## 角色边界

- **协调者**：定义问题、组织构建、收集用户真实反馈并记录结论；原型构建子代理完成不等于用户接受。
- **已受派的构建子代理**：按给定 brief、范围和写入路径直接构建并验证演示，交付产物位置、打开方式和缺口后结束，不再二次分派。

## 定义问题与选型

一句话写明：本次要决定什么、用户要观察什么、什么结果足以结束。先查代码与已有接受版本，能直接复用就不重做；纯理解已有材料交给 `explain-clearly`。

按主要不确定性加载对应分支：
- 状态转换、权限行为或数据关系需操作演示：读取 `references/logic-prototype.md`。
- 布局、信息层级或交互体验有未定方向：读取 `references/ui-prototype.md`。
- 某项用户取舍需要真实性能、兼容或行为观察：写最小隔离脚本跑出真实输出/耗时，围绕产品后果请用户判断。
- 简单文案、单图或接口示例：直接对话展示，不建原型目录。

## 构建与保存

1. 需要保存或迭代时使用 `assets/prototype-brief.md`。路径依次沿用调用者指定位置、当前任务目录、仓库约定，独立调用默认 `.dev-workflows/<decision-id>/prototypes/`；演示文件放 `artifact/`，明确标注为临时原型，不覆盖生产源码。
2. 比较多个界面或行为方案时，优先将 2–3 个实质不同变体放进**同一个切换器**（顶部按钮或快捷键切换，标注各方案名），让用户并排体验。
3. 使用标准网页 Review 时才生成 `prototype.json`，写入前必读 `assets/prototype.schema.json` 校验字段，不从示例猜字段；不把 Review Shell 复制进原型目录。
4. 协调者除极小静态修改或无子代理条件外，通过子代理构建并验证原型；只打磨影响本次决定的部分，不为一次性原型搭维护型测试套件。

## 取得反馈与记录结论

简单问题直接在对话展示；需要交互页面、多轮结构化反馈或局部标注时读取 `references/prototype-review.md`。

局部修订时递增 revision，不把旧反馈改写为新版本接受；用户拒绝当前方向时记录拒绝原因并换方向。

已有原型目录时按 `assets/prototype-verdict.md` 写入 `verdict.md`（未持久化则在对话交付短结论），写清：接受版本、适用页面/状态、必须保持的关系、允许变化的细节、演示简化边界与可重放入口。明确告知原型为一次性产物，复用为生产代码需单独决定并按工程标准重评估。
