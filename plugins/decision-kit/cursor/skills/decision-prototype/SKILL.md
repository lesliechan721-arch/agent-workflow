# Decision Prototype

负责一个明确问题的可体验证据与反馈，不接管整个需求探索。先确定要校准什么，再选择最低足够的原型与反馈方式；不必先证明文字讨论已经失败。

## 当前职责

负责用户问题与反馈时，按下文选择证据、组织构建并取得用户决定。当前已是受委派的原型构建子代理时，以本轮 brief、范围和授权为依据，直接使用相关原型方法完成构建与验证；交付产物位置、查看方式、实际结果和缺口后结束。本轮用户反馈与接受结论由负责用户交互的协调者处理。

原型构建子代理遇到材料问题或超出范围的工作时向委派者说明；已有构建分工不因加载本 Skill 再转派同一任务。

## 定义问题

读取当前请求、相关事实和已有共享决策方向。用一句话说明本次需要决定什么、用户要观察什么，以及什么结果足以结束。能直接调查的事实先调查，不让用户凭偏好确认技术事实。

新页面、关键操作或复杂状态在细化规格前，常需要让用户看见同一句描述可能代表的不同结果。已有接受版本或可用实验足以回答时直接复用；不为增加原型调用而制造新问题。只需要理解已有材料而不选择新行为时，返回解释需要，不把阅读页当作新的产品候选。

同一决定中的文案、位置和状态展示可以一起调整；出现新的目标、主要取舍或相互独立的决定时，先缩小问题，不继续堆高保真度。

## 选择证据

从主要不确定性出发，只加载当前需要的方法：

- 状态转换、权限行为或数据关系需要具体演示来校准：读取 逻辑原型（`references/logic-prototype.md`）。
- 布局、信息层级或操作体验存在尚未确认的方向：读取 界面原型（`references/ui-prototype.md`）。
- 性能、兼容性或技术可行性：运行最小实验，保存环境、操作和实际结果；未测试的环境不在结论覆盖范围内。
- 简单文案、单图或接口示例：直接展示即可，不为方法分类创建额外工件。

只有另一种方法能补足当前缺失证据时才组合使用，不要求逻辑与界面互斥。产物应有清楚、低成本的查看或运行入口；单文件、现有项目路由或一条运行命令都可以。

## 构建与保存

1. 需要保存或迭代时，使用 原型说明（`assets/prototype-brief.md`）。优先采用用户或调用者给定位置，其次沿用当前主题的原型位置，再按仓库约定；独立调用且都未提供时使用 `.dev-workflows/<decision-id>/prototypes/`，仅本地保存；原型工件放入 `artifact/`，清楚标记为临时原型，不覆盖生产实现。
2. 使用标准网页 Review 或用户明确要求时，才使用 `prototype.json` 描述当前候选。生成或修改前读取 Prototype schema（`assets/prototype.schema.json`），按实际字段校验；不要从示例猜字段。Review Shell 和会话文件不复制到原型目录。
3. 当前负责原型协调时，除极小静态示例、局部文案或样式微调，或子代理不可用外，委派子代理构建并验证原型；明确本轮问题、原型构建职责、写入范围和验证要求。协调者负责用户决定并可做必要验证；多个构建任务使用清楚、互不冲突的写入安排。
4. 只完善影响当前决定的内容。不为一次性演示建立维护型测试套件；运行检查、实验断言和测量可以是必要证据。反复使用的 Review 工具测试不属于本次原型范围。

## 取得反馈

由负责用户交互的协调者执行；原型构建子代理的完成不等于用户接受。

简单且不需定位的问题直接在当前对话展示。需要可交互页面、多轮结构化反馈或局部标注时，读取 网页反馈（`references/prototype-review.md`）；原型形态不由反馈工具决定。

候选必须回答当前问题，不为凑数量制造变体。需要比较方向时通常给少量实质不同的候选，并允许都不接受。逻辑演示可以只有一个模型，用户通过操作评价它。

用户要求局部修改时，围绕同一问题更新原型并取得新反馈；使用网页配置时递增 revision，不把旧反馈改写成新 revision 的反馈。用户拒绝当前方向时，保留拒绝及必要原因，重新确认候选方向，不记录为接受。用户提出新的材料问题时先说明问题，不继续扩大当前原型。

## 形成结论

已有原型目录时，按 原型结论（`assets/prototype-verdict.md`） 写入 `verdict.md`；未持久化时直接交付简短决定记录。它保存当前答案、成立条件、证据指针和未解决问题。记录被接受的版本及适用页面、状态或实验环境，明确哪些关系或行为已确认、哪些允许变化、哪些属于演示简化。接受范围不清且会改变后续结果时，请用户确认。`brief.md` 保留构建问题与边界。

没有用户决定或足够证据时明确保留未决状态。客观实验只报告实际结果及未验证范围，不冒充用户接受。反馈暴露新的概念、业务规则或范围变化时，连同具体问题交回协调者，不在当前原型里扩建整个产品。

接受内容将成为长期规范时，交付需稳定保存的实际产物与接受范围；临时反馈记录和候选仍属于过程资料。用于后续实施或审查的证据保持可访问；会话型反馈中影响结论的观察保留在结论记录或稳定证据位置。原型仍可作为一次性证据；复用为生产实现需用户明确选择，并重新评估结构、验证和风险。
