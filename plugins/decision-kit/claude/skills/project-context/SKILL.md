# Project Context

负责领域模型的澄清及长期知识维护，不负责整个需求流程。概念先用场景查清，已确认且值得保留的知识及时归位；不是设计结束后才整理名词。

## 澄清模型

读取当前问题、已有词汇与决定、相关合同和代码。检查同一名称是否指向不同主体，关系、身份、生命周期和必须保持的业务规则是否一致。缺少定义也可能是缺口，不必等用户明确要求“写词汇表”才识别。

用一个正常场景和一个有区分力的反例检验模糊含义。例如，一个登录账号离开某租户后，账号本身是否仍存在？场景应揭示概念边界，不为凑覆盖扩展整个产品。提出清楚名称与候选含义，并指出不同答案会改变什么行为。

可查事实自行确认。代码与用户描述不一致时，分别说明当前实现和期望目标；代码不能自动否决新需求，也不证明目标已实现。改变产品含义的选择，独立调用时向用户确认，受委派时把具体问题交回协调者取得答复；明确委托的部分按其边界处理，不自答产品选择。

## 及时维护有用知识

| 当前内容 | 去处与边界 |
| --- | --- |
| 已确认的领域概念 | 在现有词汇或领域文档中保留定义、区别、关系、适用范围及必要业务规则，不塞入接口实现或任务进度 |
| 重要决定 | 同时具有真实取舍、缺少背景会被误解、以后更改代价显著时，记录必要理由、备选、条件与后果；普通选择不创建 ADR |
| 本次行为要求或未决选择 | 返回调用者的当前记录或规格，不复制成长期知识，也不把候选写成已接受定义 |

需要确定位置或形式时读取 [项目知识布局](references/knowledge-layout.md)，按需采用 [词汇示例](assets/context-template.md) 或 [决定模板](assets/adr-template.md)。确认与写入授权齐备后就更新，不等整个主题完成；没有权限时交付建议内容和目标位置。已有知识完整且准确时直接复用，不为证明调用成功而改文件。

核对主体、条件、例外、精确值和约束强度没有因归纳改变。新含义替代旧定义时，同步当前授权内的直接引用并保留必要理由；范围外引用交回调用者，不擅自扩大修改。

## 交付

交付明确含义、确认来源、实际维护位置或待写建议，以及仍需用户决定的问题。已接受目标、当前实现和实际验证分别说明。记录自身应能恢复必要边界，不依赖私有对话；结束本次知识工作，不批准规格或启动实施。
