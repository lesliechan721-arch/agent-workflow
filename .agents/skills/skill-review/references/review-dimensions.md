# Review Dimensions

本量表用于 full/release 评审。每个维度都要给出分数、置信度、证据定位和一句理由。不要为了填满表格而制造不适用问题。

## 1. 规范与包完整性（8）

检查：

- `SKILL.md` 是否存在，YAML frontmatter 是否有效。
- `name` 是否符合格式并与父目录一致。
- `description`、`compatibility`、`metadata`、`allowed-tools` 是否符合规范及实际用途。
- 相对文件引用是否存在，核心资源是否可解析或执行。
- 包结构是否清楚，没有把必需文件放在不可发现位置。

高分特征：可用官方 validator 或等价工具验证；结构和引用完整。低分特征：无效 frontmatter、目录不匹配、关键引用断裂、兼容性声明与实际依赖冲突。

## 2. 问题基础与实际价值（8）

检查：

- Skill 是否来自真实任务、项目材料、失败 trace、运行手册或反复纠正，而非泛化常识。
- 目标问题是否可观察、可复现、可衡量。
- 是否明确成功标准和范围外事项。
- 不加载 Skill 时，模型是否真的会稳定出错或浪费显著成本。
- Skill 是否提供模型本来不知道的领域价值。

高分特征：问题、失败模式和改进目标有实证。低分特征：只写“遵循最佳实践”“正确处理错误”等通用声明，或无法说明为什么需要此 Skill。

## 3. 触发条件与 description（12）

检查：

- description 是否同时说明“做什么”和“何时使用”。
- 是否使用用户意图和现实表述，而非内部实现字段堆砌。
- 是否覆盖隐式表达、复杂任务中的嵌套场景和必要关键词。
- 是否描述关键 near-miss、相邻 Skill 边界和不应触发场景。
- 是否简洁且低于规范上限。
- 是否有 realistic 的正负触发 eval、多次运行和固定 train/validation 划分。

高分特征：触发率有验证，误触发与漏触发均低。低分特征：过宽、过窄、只描述功能、不描述使用时机，或通过不断加入样例关键词过拟合。

## 4. 范围、边界与组合性（10）

检查：

- 是否是一个连贯工作单元，而非多个不相关职责的集合。
- 授权、业务判断、工具调用和结果生产是否清晰分层。
- 与其它 Skill 是否重复、冲突或可能同时管理同一流程。
- 是否因看到新 schema 字段、理论边界或单次异常而扩大范围。
- 是否清楚说明停止条件、交接和范围外事项。

高分特征：边界清晰、可组合、不会劫持相邻任务。低分特征：一个 Skill 同时承担触发、授权、运行时调度、领域判断和所有异常恢复。

## 5. 指令设计与控制校准（10）

检查：

- 是否提供可复用方法、步骤或默认值，而不是某个实例的答案。
- 脆弱操作是否足够明确，灵活任务是否保留合理判断空间。
- 是否提供清楚默认值而非等价菜单。
- 是否使用短模板、示例、gotcha、checklist 或 validation loop 替代冗长抽象说明。
- 指令顺序、优先级、输出合同和错误处理是否明确。
- 是否存在重复、互相矛盾、无法执行或过度绝对化的要求。

高分特征：精确度与任务脆弱度匹配。低分特征：通篇 `must` 但没有程序、选项过多、每个边界都写成例外，或 role/prompt 重复父流程。

## 6. 上下文效率与渐进式披露（10）

检查：

- `SKILL.md` 是否只保留每次激活都需要的核心内容。
- 每条内容是否回答“没有它模型会稳定出错吗”。
- 详细材料是否放入聚焦的 reference，并明确“何时读取”。
- 文件引用是否一层可达，避免深层链式加载。
- 资源是否按需加载，而不是仅把复杂度藏到 reference。
- Skill、role、prompt、reference 是否重复同一规则。
- 是否关注控制逻辑密度，而不仅是 500 行/5000 token 上限。

高分特征：核心短、按需加载清楚、无重复。低分特征：正文百科全书化，reference 无读取触发，或通过拆文件掩盖一套同样复杂的自然语言状态机。

## 7. 职责归属与自然语言状态机风险（10）

检查：

- Skill 是否只维护策略、默认值、领域约定和少量稳定不变量。
- 参数类型、枚举、返回结构是否交给 schema。
- 真实状态、事件顺序、并发、幂等、取消和生命周期是否交给 runtime。
- 确定性、重复、可测试逻辑是否交给 script。
- role 是否只保留叶子职责、固定配置和最小返回约束。
- 是否存在计时器、额度、pending、跨 actor 握手、乱序事件或取消/关闭竞态的自然语言状态机。

高分特征：职责分层正确，复杂机制使用一等能力。低分特征：核心正确性依赖模型记住多维状态或父子代理通过自然语言字符串维护分布式协议。

出现高风险信号时读取 `references/architecture-boundaries.md`。

## 8. 脚本与确定性自动化（8）

评分对象是“脚本决策是否正确”，不是脚本数量：

- 重复、复杂且确定的逻辑是否被脚本化。
- 不需要脚本时是否保持简单，而非为了完整性增加代码。
- 脚本是否通过相对路径被清楚引用。
- 是否自包含或明确、固定依赖。
- 是否非交互、支持 `--help`、有可操作错误和有意义退出码。
- stdout 是否结构化，diagnostics 是否走 stderr。
- 是否考虑幂等、输入约束、安全默认值、dry-run 和输出上限。
- 是否有测试或安全样例运行。

详细检查见 `references/scripts-and-resources.md`。

## 9. references、assets 与资源组织（6）

检查：

- reference 是否聚焦、按需读取、大小合理。
- assets 是否用于模板、数据或静态资源，而非隐藏指令。
- `SKILL.md` 是否明确列出资源用途和读取条件。
- 是否存在断裂、过期、不可达、重复或从未引用的资源。
- 资源中的命令是否使用 skill 根目录相对路径。
- 版本化外部事实是否有来源和更新策略。

没有资源且确实无需资源，可以得到高分。

## 10. 评测、验证与证据驱动迭代（10）

检查：

- 是否有 trigger eval、behavior eval 和 regression eval。
- 是否针对真实失败设置可观察断言。
- 是否读取执行 trace，而不只看最终输出。
- 是否比较无 Skill、最小 Skill 和当前 Skill，确认新增文本确有收益。
- trigger eval 是否包含约 20 个现实正负样本、near-miss、多次运行和 train/validation。
- 修复是否有对应测试，是否避免只针对一个 prompt 过拟合。
- 是否记录可删除内容和停止迭代条件。

高分特征：每个重要规则都有行为证据。低分特征：只有静态文字审美，没有 eval 或 trace；每轮 review 只追加规则。

## 11. 可靠性、安全与兼容性（4）

检查：

- 环境、系统包、网络、权限和产品要求是否准确声明。
- 不可用能力是否有明确失败而非静默降级。
- 外部搜索、敏感数据、凭据和副作用边界是否安全。
- `allowed-tools` 等实验字段是否考虑实现差异。
- 声称支持的产品/版本是否有验证或合理兼容策略。
- 失败时是否保留用户控制，不伪造成功。

## 12. 可维护性与变更纪律（4）

检查：

- 共享规则是否有单一来源，避免复制到多个 role。
- 修改是否替换或删除旧逻辑，而非永久追加例外。
- 是否有 delta review、复杂度预算和发布停止规则。
- 文件、role、模型、脚本和引用是否能静态检查一致性。
- 连续迭代时，质量提升是否超过上下文与维护成本。

高分特征：变更有证据、净复杂度受控。低分特征：每轮 review 都增长正文和分支，却没有 behavior 指标改善。
