# Architecture Boundaries and State-Machine Risk

当 Skill 涉及生命周期、异步事件、重试、跨 agent 通信、权限或复杂工具编排时读取本文件。

## 默认职责矩阵

| 内容 | 默认归属 |
| --- | --- |
| 使用时机、领域策略、项目约定、稳定默认值、非显然 gotcha | Skill |
| 参数类型、合法值、必填字段、返回结构 | Tool schema |
| 真实状态、事件顺序、超时、取消、并发、幂等、后代关系 | Runtime |
| 确定性解析、生成、转换、一致性和静态校验 | Script |
| 叶子职责、固定配置、最小输出约束 | Role |
| 未证实、低概率、组合爆炸的边界 | Eval / issue |

Schema 可见不等于 Skill 必须为每个字段建立政策。只有当字段选择表达稳定产品策略时才写入 Skill。

## 自然语言状态机信号

单个信号不自动构成缺陷；组合出现时做架构审查：

- 三个以上命名状态或状态字符串。
- timeout、累计窗口、重试/恢复额度、pending 标记。
- “只允许一次”“同时最多一个”等计数不变量。
- 两个 actor 通过消息协商状态。
- 活动、终态、迟到消息、取消、恢复和关闭顺序分支。
- 多段连续“只有 A 才 B；否则 C；若 D 再 E”。
- 同一流程经过两轮 review 后仍不断追加例外。

风险分级：

- **低**：少量稳定不变量，例如“只有明确终态才视为完成”。
- **中**：模型需记住阶段、额度或多个互斥条件。
- **高**：跨 actor 协议、竞态、乱序处理、隐式持久状态或安全关键状态迁移。

## 高风险时的处理顺序

1. 删除非核心功能或可选协议。
2. 把流程缩减为少量策略不变量。
3. 使用产品/runtime 的一等状态能力。
4. 把真正确定的计算、验证和生成逻辑移入脚本。
5. 把尚未证实的边界放入 eval 或产品 issue。
6. 只有无法通过上述方式解决且确有实证时，才增加最小自然语言约束。

不要仅把完整状态机移到 `references/`；那只降低常规加载成本，不提高状态执行可靠性。

## Role 边界

Role 应主要回答：

- 叶子代理负责什么、不负责什么。
- 固定模型、effort 或工具边界。
- 最小结果/证据格式。

Role 不应复制父代理的等待、探测、恢复、取消和关闭协议。相同协议复制到多个 role 是耦合和漂移信号。

## Finding 写法

发现职责错位时，不要只建议“补一句”。报告应包含：

- 当前逻辑实际属于哪一层。
- 为什么自然语言无法可靠承载。
- 最小删除或抽象方案。
- runtime/script/eval 的替代位置。
- 如何验证重构后仍解决原始失败。
