# `aw` TUI 体验返工落差修复 Spec

日期：2026-05-19
状态：需求确认稿
前置需求：`docs/dev/specs/aw-tui-ux-polish-followup.md`
文档规范：`docs/dev/spec-plan-writing-guide.md`

## 文档定位

这份 Spec 只定义 `aw-tui-ux-polish-followup.md` 已实现后，自测发现的 TUI UI/UX 落差修复需求。它补充原 Spec 的页面体验边界、公开 TUI 合同和验收标准，不重写原需求，也不写执行计划、阶段拆分、测试文件清单或迁移步骤。

本文件优先处理“页面看起来和用起来仍不像原 Spec 设计”的问题。CLI 版本、SemVer、平台选择、SkillTrigger 配置模型等已在前置 Spec 中定义，本文件只在这些合同影响 TUI 页面呈现时补充修复口径。

## 背景

前置需求要求把 `aw` TUI 从命令式状态浏览器收紧成插件管理控制台：首页扫视插件，详情页承载操作，状态作为详情下级页面，写操作回到详情页并展示最近结果，TUI 不展示命令建议或内部诊断噪声。

当前实现已经修复了一部分底层合同，例如状态符号已从 icon id 改成终端可见符号，配置页也开始承载内建 SkillTrigger 字段。但自测仍能明显感到页面骨架偏离原设计：主页和详情页仍像文本摘要加 prompt 列表，状态/诊断概念仍残留，结果页仍把用户带到另一条分叉流程，配置页和详情页混入 schema、catalog、selector 等内部信息。这些问题不是单个文案瑕疵，而是 TUI 信息架构没有完全按原 Spec 收口。

本轮目标是把已确认的 UI/UX 合同补到可验收粒度，让后续实现不再按现有文本向导模型继续堆功能。

## 现状探查结论

这一节只记录影响需求边界的事实，不描述实现步骤。

### 首页仍是文本列表，不是块状卡片

- `packages/cli/src/commands/console.ts` 中 `buildHomeLines()` 仍把首页渲染成分组标题下的三行文本：状态符号 + 标题、描述、平台摘要 + 主操作。
- `buildHomeChoices()` 又把同一批插件渲染成 prompt choices，label 是状态 + 标题 + 状态文案，description 继续拼版本、平台、主操作和描述。
- 这会让首页同时出现“正文列表”和“选择列表”两套摘要，视觉上仍是 CLI 列表，不是前置 Spec 中的插件卡片。

### 详情页混入技术诊断信息

- `renderDetailLines()` 会调用 `detailAuditLines()`，后者从状态诊断里筛选 `current catalog`、`selector`、`catalog 缓存`、`远程校验`、`CLI 版本限制` 等信息直接放到插件详情页。
- 这些字段适合 verbose 状态详情或 JSON，不适合插件操作中心。详情页因此像诊断摘要页，而不是“当前状态 + 平台 + 操作”的管理页面。

### 状态与诊断概念仍没有完全收口

- `PluginConsoleFeatureKind` 仍包含 `diagnose`，`createPluginConsoleExecutableActions()` 仍能创建 `openDiagnose`，`featureLabel()` 仍有 `查看诊断`。
- `handleExecutableAction()` 中 `openDiagnose` 最终映射到 `runStatusAction()`，说明用户体验上已经想合并到状态，但模型和文案仍保留旧诊断入口。
- `runStatusAction()` 仍是一个独立页面循环；状态摘要、状态详情和详情页之间没有形成原 Spec 里的单一详情下级体验。

### TUI 正文仍展示 nextSteps

- `renderStatusDetailLines()` 会把 `location.nextSteps` 逐条渲染到状态详情页正文。
- 当前 `NextStepInstruction` 已经结构化，TUI 格式化也会隐藏 command 字段，但页面正文仍把“下一步”当说明文本展示，而不是把建议动作落到可执行菜单项。
- 已确认本轮修复后，TUI 正文不再展示下一步建议；推荐只通过功能菜单标记和菜单说明表达。

### 结果页仍保留分叉流程

- `showResultPage()` 会渲染独立结果页，并提供 `状态 · 某位置`、`返回首页`、`退出` 等选择。
- 这与前置 Spec 的“写操作完成后默认回到插件详情页，并只保留最近一次操作结果”不一致。虽然当前已有 `recentResults` 机制，但独立结果页仍打断用户回到当前插件确认状态的主线。

### 配置页仍像调试页

- `renderConfigViewLines()` 会在配置管理页展示 `schema source`、`schema identity`、`schema plugin version`、`schema manifest digest`、`install record`、`current catalog`、`minAwVersion` 等内部字段。
- 前置 Spec 要求配置页是长期配置管理页，展示目标、作用层、字段、来源、最近结果和操作。上述内部字段应进入状态详情、verbose 输出或 JSON，而不是默认配置页。

### 安装向导仍残留旧 SkillTrigger 和字符串 nextSteps 模型

- `console-wizard.ts` 中仍有 `ConsoleSkillTriggerDecision`、`selectSkillTrigger` step、`SkillTriggerPreference` 和 `nextSteps: string[]`。
- 当前 `createSkillTriggerDecision()` 虽然返回 `show: false`，但旧安装期触发策略仍在向导模型中流转。前置 Spec 已明确删除安装期 SkillTrigger 选择，触发策略只能通过 AW 内建配置项管理。
- 字符串 `nextSteps` 会诱导 TUI 后续继续把阻断原因写成命令式说明，和结构化下一步合同不一致。

### 危险确认机制部分到位，但信息结构仍需收口

- 当前 TUI 已有 `promptOptionConfirmation()`，默认选中取消，不是纯 `y/N` 文本确认。
- 但动作模型仍依赖 `confirmText` 作为危险动作说明，确认页正文容易退回成一段问题句，而不是原 Spec 要求的“将要删除 / 不会删除 / 配置处理 / 目标范围”的结构化确认页。

## 目标、范围与非目标

### 目标

1. 首页按状态分组展示块状插件卡片，不再呈现正文列表和选择列表两套重复摘要。
2. 插件详情页回到操作中心定位，不展示 catalog、selector、schema digest、install record 等内部诊断字段。
3. TUI 只保留 `状态` 概念，不展示 `诊断` 功能、`查看诊断` 文案或 `openDiagnose` 等用户可感知入口。
4. 状态页作为插件详情页下级页面，摘要和详情都不展示命令建议，也不把 nextSteps 作为正文建议区。
5. 推荐动作只通过功能菜单项的推荐标记和菜单说明表达。
6. 写操作完成后直接刷新并返回当前插件详情页，在详情页顶部展示最近一次操作结果。
7. 单插件写操作不再停留独立结果页，也不在完成后提供 `返回首页` 或 `状态 · 某位置` 的分叉选择。
8. 配置管理页只展示用户可理解的配置目标、作用层、字段、来源、最近结果和操作，不展示内部 schema/catalog 诊断信息。
9. 安装、升级和修复类 TUI 向导的公开页面和 page model 不再包含安装期 SkillTrigger 选择或 `selectSkillTrigger` 步骤。
10. TUI 阻断、失败和下一步提示统一使用结构化状态与 UI 动作，不能使用裸字符串命令或字符串 nextSteps 作为页面合同。
11. 危险确认页继续使用选项确认并默认取消，但正文必须结构化展示影响范围，而不是只显示一段 `confirmText`。
12. 所有页面继续遵守前置 Spec：不展示 raw command、不展示 CLI 命令建议、不展示内部 stdout/stderr 原文。

### 范围

- 首页分组、块状卡片、选择体验和刷新入口。
- 插件详情页信息架构、推荐动作展示、最近结果区域。
- 状态摘要页和状态详细信息页的入口、文案和菜单。
- 写操作完成、失败和取消后的 TUI 导航。
- 配置目标选择页、配置管理页和配置字段列表的默认展示信息。
- 安装/升级/修复向导中与 SkillTrigger、nextSteps 和阻断提示有关的 TUI 公开模型。
- 危险确认页的展示合同。

### 非目标

- 不重新设计 CLI 命令合同、SemVer 规则、本地 catalog gate、平台选择语义或 SkillTrigger 存储语义。
- 不要求本轮把底层内部类型一次性全部删除；但旧字段不能进入 TUI 公开页面、console item、prompt 文案或用户可见序列化模型。
- 不为终端 TUI 引入图形化框架、鼠标交互或 Web UI。
- 不新增多插件批量管理后台能力。
- 不在本 Spec 中指定实现阶段、测试文件或具体重构顺序。

## 已确认决策

- 首页采用块状卡片：每个插件用固定多行块展示标题、状态、版本、平台摘要和主操作，分组之间留空。
- 写操作完成后不保留独立结果页；默认刷新当前插件详情页，并在详情页顶部展示最近一次操作结果。
- TUI 中 `nextSteps` / 建议动作只通过菜单项的 `推荐` 标记和菜单说明体现；页面正文不展示“下一步”建议区。
- 旧 `diagnose` 的公开边界沿用前置 Spec：TUI、帮助、文档和用户可见输出不再引用诊断入口；如保留隐藏迁移 stub，也只能输出确定性错误，不能执行诊断。

## 术语与状态模型

### 块状插件卡片

块状插件卡片是终端中的多行信息块，不要求画边框。每张卡片至少包含：

- 第一行：状态符号、插件名、版本或版本变化、主操作。
- 第二行：一句短描述；没有描述时整行省略。
- 第三行：平台与位置摘要；异常、历史残留和配置残留必须点名。
- 必要时第四行：一条短异常摘要或配置残留摘要。

卡片之间用空行分隔。卡片内字段位置保持稳定，不能因为某个插件字段缺失导致其它卡片的关键信息难以扫描。

### 操作中心

插件详情页是操作中心，不是状态详情页、诊断页或命令提示页。操作中心只回答三件事：

- 这个插件当前整体状态是什么。
- 它在哪些平台或位置有安装、可升级、异常、历史残留或未安装状态。
- 用户现在可以执行哪些 TUI 动作。

更细的证据、诊断事实和恢复评估进入 `状态` 下级页面。

### 最近结果

最近结果是当前插件最近一次 TUI 写操作的结果摘要，只保留一条。它显示在详情页状态摘要之后、平台与安装之前。

最近结果必须来自刷新后的插件数据和写操作 receipt / target result，不从旧结果页文案反解析。

## 用户体验需求

### R1：首页必须是单一块状卡片列表

首页主体和 prompt 选择不能各自展示一套完整插件摘要。实现可以选择以下任一方式，但用户看到的页面必须只有一套主要卡片：

- 主体区域展示完整块状卡片，选择列表只显示插件名或短标签。
- 选择控件本身支持多行展示时，由选择控件承载卡片，主体区域只显示标题和分组。

首页卡片按 `异常`、`可升级`、`已安装`、`未安装` 分组，空分组不展示。每个分组标题带数量。组内顺序保持稳定；若没有更明确排序规则，沿用当前 console item 顺序，不能在同一轮刷新中跳动。

首页不展示 `主操作：` 这类字段名。主操作应作为卡片第一行右侧或末尾的短动作词，例如 `处理`、`升级`、`详情`、`安装`。

首页不展示命令、诊断矩阵、schema/catalog 字段、install record 路径或 verbose 级别信息。

### R2：首页选择体验不能重复或抢占卡片信息

用户在首页上下移动时，选中项必须能和卡片对应起来。若选择列表只显示短标签，短标签必须包含状态符号和插件名；详细描述不应重复完整卡片内容。

首页底部操作只保留 `刷新` 和 `退出`。`Esc` 在首页等同退出，`q` 退出。刷新后保留可定位的选中插件；若插件消失，回到当前分组第一个插件。

### R3：详情页必须移除默认技术诊断信息

插件详情页默认不展示以下内部信息：

- `catalog`、`current catalog`、`catalog 缓存`
- `selector`
- `schema source`、`schema identity`、`schema manifest digest`
- `install record` 路径
- `tracking`、`ledger`、`snapshot`
- `minAwVersion`、远程校验细节、内部 fallback 原因

如果这些信息对排障有价值，只能进入状态详细信息页、CLI verbose 输出或 JSON。详情页可以显示用户可理解的状态摘要，例如“本地插件列表不可用，当前只显示已发现安装”，但不能暴露内部字段名。

### R4：详情页推荐动作只通过菜单表达

详情页正文不展示“建议”“下一步”或 `nextSteps` 区块。推荐动作通过功能菜单项标记，例如 `状态（推荐）`、`升级（推荐）`。

菜单项 description 可以说明推荐原因，但只能是用户可理解的 UI 语义，例如“先查看异常位置和可恢复动作”。不能写 `运行 aw status ...`，也不能把 CLI command 当说明。

若没有可推荐动作，不显示推荐标记，不用文案解释“暂无建议”。

### R5：TUI 不再保留用户可见诊断入口

TUI 功能菜单、目标选择、结果区域、状态页和配置页都不能出现 `诊断`、`查看诊断`、`openDiagnose` 或 `diagnoseCommand` 语义。

需要查看更细信息时，统一使用 `状态` 和 `详情`：

- 详情页功能菜单入口叫 `状态`。
- 状态摘要页里的深层入口叫 `详情`。
- 状态详细信息页标题使用 `详情` 或 `状态详情`，不使用 `诊断`。

内部如果短期仍保留 legacy diagnose 类型，必须在进入 TUI page model 前映射为状态语义，并且不得进入用户可见 label、description、JSON console item 或测试快照。

### R6：状态页只展示状态和可执行 UI 动作

状态摘要页默认只展示有现场证据的位置，不列纯未安装 catalog 位置。状态详情页可以展示结构化诊断事实，但仍不展示 raw command、stdout/stderr 原文、堆栈或内部对象字段。

状态页正文不渲染 `nextSteps` 列表。可继续动作必须进入操作区，例如 `修复`、`清理`、`配置`、`返回`、`退出`。没有可执行动作时，只展示状态说明和 `返回` / `退出`。

### R7：写操作完成后直接回到刷新后的详情页

安装、升级、卸载、清理、修复、重新安装、认领、接管共享运行时、处理重复安装、配置保存、配置重置和重新应用配置完成后，TUI 必须：

- 重新加载当前插件的 console item。
- 回到当前插件详情页。
- 在详情页顶部展示最近结果。
- 只保留最近一次结果；新的写操作覆盖旧结果。

单插件写操作完成后不出现独立结果页，不提供 `返回首页` 作为默认下一步，也不提供 `状态 · 某位置` 的分叉入口。用户如需看状态，通过详情页功能菜单进入 `状态`。

失败和取消也回到详情页。取消结果可以用短提示显示一次，但不能写入最近结果为成功，也不能把用户带到结果页分叉。

### R8：最近结果必须短、准、可继续

最近结果区域只展示：

- 操作名和成功/失败/部分完成状态。
- 每个真实目标的简短结果。
- 失败时的一句用户可理解原因。
- 可继续动作只通过功能菜单推荐标记体现。

最近结果不展示命令、不展示内部错误栈、不展示完整 receipt JSON、不展示旧 result page 的“可继续查看目标状态”文案。

多目标操作必须按真实目标展示结果，不能只写“所有平台成功”或“整体失败”。配置删除结果按 config store 分组展示，不能按 execution target 重复制造噪声。

### R9：配置管理页默认只展示配置管理信息

配置管理页顶部只展示：

- 插件名。
- 当前配置 target。
- 当前作用层。
- 可应用位置；没有可定位 runtime target 时省略或用一句 no-op 说明。

字段列表只展示用户可理解的字段标题、当前值状态和来源。SkillTrigger 内建字段使用自然标题，例如 `codex-explore 触发方式`，不展示 `aw.skillTriggers.<skill>.trigger` 或 `$aw` 存储路径作为主标题。

以下信息默认不在配置页展示：schema identity、schema digest、manifest digest、catalog channel、minAwVersion、install record path、内部 source identity。配置页遇到 schema unavailable 或 store-only 旧配置时，展示用户语义，例如“当前插件列表已无法解释这层旧配置，只能整层清理”。

### R10：配置页操作区必须贴合当前作用层

`生效` 视图只读，不展示会让用户误以为能直接写入生效层的 `更新`、`清空` 或 `重置` 操作。

`个人`、`项目` 和 `本地` 视图只展示当前层可执行的操作：

- 可写字段存在时展示 `更新`。
- 当前层有可清理值时展示 `清空` 或 `重置`。
- 存在可定位 runtime target 时展示 `应用` 或 `重新应用配置`。
- project local 层不得展示可改写 SkillTrigger 内建字段的操作。

没有可执行操作时，只显示 `返回` 和 `退出`，不展示 disabled 操作堆叠。

### R11：安装向导不得暴露安装期 SkillTrigger

安装、升级、修复、重装和相关 TUI 写向导的公开 step、页面文案、确认页和结果区域都不得出现安装期 SkillTrigger 选择。

向导中不得出现 `默认 / 手动 / 自动` 的触发策略选择页。触发策略只能在配置页中作为 AW 内建配置字段查看和修改。

如果内部仍需要读取历史 `skillTriggerPreference` 以兼容旧数据，读取结果只能进入状态或配置的 legacy/ignored 投影，不能影响安装向导步骤、默认选择或写操作最近结果。

### R12：TUI 阻断提示不得使用字符串 nextSteps 作为页面合同

TUI 预检阻断、失败原因和恢复建议必须来自结构化状态：

- 可由 TUI 执行的动作进入菜单。
- 纯说明进入阻断原因正文。
- CLI command 只允许出现在 CLI 人类输出或 JSON command 字段，不进入 TUI。

安装向导、目标选择、依赖确认、配置保存和写操作失败页都不能直接渲染 `nextSteps: string[]`。需要兼容内部旧字段时，必须先转换为结构化 `manual` 或 `uiAction` 语义，再按 TUI 规则展示。

### R13：目标选择页继续执行前置 Spec 的两步安装模型

未安装插件进入安装时，TUI 必须先选平台，再选 scope。第一页只展示 `Codex`、`Claude Code`、`全部支持平台` 这类平台选项；第二页只展示 `个人`、`项目` 等位置选项。

安装目标页不得把平台和 scope 的笛卡尔积混在同一个列表，也不得同时展示 `全部支持平台` 和若干 `Codex · 个人` / `Claude Code · 项目` 组合候选。

已安装插件执行升级、卸载、清理、修复等动作时，可以直接展示真实 location target，但批量项必须是明确语义，例如 `所有可升级目标`。高风险恢复动作不能出现模糊批量项。

### R14：危险确认页必须展示结构化影响范围

危险确认页继续使用选项页，默认选中 `取消`。正文至少按动作类型展示必要结构：

- 操作对象：插件和真实目标。
- 将要删除、覆盖、接管或重建的内容。
- 不会影响的内容。
- 配置是否保留或删除。
- 多目标动作的每个真实目标。

确认页不能只显示一段 `确定要 ... 吗？`。`confirmText` 可以作为兼容输入，但不能成为最终页面的唯一正文。

### R15：内部术语只进入深层状态或开发者输出

TUI 首页、详情页、配置页、确认页、结果区和普通状态摘要页不展示以下词作为普通用户文案：

- `catalog`
- `ledger`
- `tracking`
- `snapshot`
- `selector`
- `schema identity`
- `manifest digest`
- `install record`
- `diagnose`

确需在状态详细信息页展示时，优先翻译成用户语义；只有开发者排障必需且没有自然中文等价时，才保留原技术词，并用一句话说明它代表什么。

## 公开合同和命令边界

### Console item 与 TUI page model

TUI page model 必须提供足够结构化的信息，让 renderer 能区分：

- 首页卡片字段。
- 详情页状态摘要。
- 详情页菜单推荐标记。
- 状态摘要和状态详情。
- 最近结果。
- 配置字段 entries。
- 危险确认影响范围。

实现不能通过拼接 CLI 人类输出、诊断文本或旧 result page 文案来生成 TUI 页面。

### `diagnose` 公开边界

TUI 公开模型中不得再出现 `diagnose` 作为 feature kind、action kind、label、menu choice 或 result target。`aw diagnose` 的 CLI 边界继续按前置 Spec 处理，本文件不重新定义。

### `nextSteps` 边界

TUI 可以消费结构化 `NextStepInstruction` 来决定推荐哪个菜单项，但不得把 `nextSteps` 当页面正文列表展示。

如果某条 `NextStepInstruction` 是 `cliCommand` 且没有可映射 UI action，TUI 只能展示其 `label` / `description` 代表的状态说明；不能显示 command，也不能生成“复制命令执行”的建议。

### 配置页边界

配置页以 `ConfigFieldEntryV2` 或等价结构化字段为主数据源。配置页不能把 schema 元数据、catalog 元数据或 install record 路径作为普通字段展示。

JSON 和 CLI verbose 可以继续暴露调试所需字段；TUI 默认页面不承担这个职责。

## 验收标准

1. 启动 TUI 首页时，用户看到的是按状态分组的块状插件卡片；页面中不再出现同一插件的完整摘要被正文和 prompt description 重复展示。
2. 首页卡片能一眼看到状态、插件名、版本或版本变化、平台摘要和主操作；没有命令建议和内部字段。
3. 进入插件详情页后，页面不展示 `current catalog`、`selector`、`schema identity`、`manifest digest`、`install record` 等技术诊断行。
4. 详情页菜单可以标记推荐动作，但正文没有“下一步”或建议区块。
5. TUI 任意用户可见页面不出现 `诊断` 或 `查看诊断` 入口；需要深层信息时通过 `状态` -> `详情` 进入。
6. 状态详情页不渲染 raw command，不渲染字符串 nextSteps，不提示用户复制命令。
7. 执行一次成功的安装、升级、卸载、清理、修复、重装或配置保存后，TUI 直接回到刷新后的插件详情页，并在顶部显示最近结果。
8. 写操作完成后不出现带 `返回首页`、`状态 · 某位置`、`退出` 分叉的独立结果页。
9. 写操作失败后也回到当前插件详情页，最近结果只显示简短失败原因；后续处理动作通过菜单推荐标记呈现。
10. 配置管理页默认只展示配置 target、作用层、字段、来源、最近结果和当前层可执行操作，不展示 schema/catalog/install record 调试信息。
11. `生效` 配置视图只读，不展示 `更新`、`清空`、`重置` 等写操作。
12. 安装、升级、修复、重装向导中不出现 SkillTrigger 触发策略选择，也不在公开 steps 中出现 `selectSkillTrigger`。
13. 未安装插件的安装目标选择仍是“先平台、再位置”两步，不展示平台和 scope 组合矩阵。
14. 危险动作确认页默认选中取消，并结构化展示影响范围；页面不能只是一句确认问题。
15. TUI 页面中不出现 `aw ...` 命令建议。CLI 人类输出和 JSON 的命令字段不受本条约束，但不能被 TUI renderer 直接复用为页面文案。
16. 旧 `diagnose`、字符串 `nextSteps`、`confirmText`、schema/catalog 元数据如果仍作为内部过渡字段存在，不得进入 TUI 用户可见输出。
