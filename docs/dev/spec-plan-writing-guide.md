# Spec 与 Plan 文档写法约定

本文档维护开发过程中的需求 Spec 和执行 Plan 写法约定。具体需求文档和计划文档只保留当前事项本身的内容，通用结构约定统一放在这里，便于后续开发复用。

## 职责分工

- Spec 定义需求范围、现状探查结论、用户体验边界、公开合同边界和验收标准。它回答“为什么要做、现状约束是什么、要做到什么程度、哪些行为算正确、哪些行为明确不做”。
- Plan 定义执行步骤、实现切分、涉及文件、测试范围和收口顺序。它回答“怎么做、先后依赖是什么、改哪些文件、用哪些测试证明完成”。
- 现状探查属于 Spec，因为它发生在计划之前，是需求边界和技术决策的依据。
- 执行顺序、批次拆分、测试用例、迁移说明和执行者拆分属于 Plan。
- 如果计划中的实现决策会改变需求边界，应先回到 Spec 调整需求，再更新 Plan。

## Spec 建议结构

1. 文档定位：说明本文件只写需求，不写实现计划。
2. 背景：解释问题和用户价值。
3. 现状探查结论：记录会影响需求边界、技术约束或方案取舍的事实。可以包含关键代码路径作为证据，但不写执行阶段和测试清单。
4. 目标、范围与非目标：提前收住边界。
5. 术语与状态模型：定义需求中会复用的词。
6. 用户体验需求：按页面、流程或用户任务描述行为。
7. 公开合同和命令边界：写消费者可感知的合同和安全边界。
8. 验收标准：用可验证行为表达完成条件。

## Plan 建议结构

1. 文档定位：说明本文件只写执行，不重新定义需求。
2. 实施约定：列出跨阶段必须遵守的工程约束。
3. 阶段依赖总览：用表格说明顺序、依赖和可并行关系。
4. 阶段依赖关系图：用 Mermaid 图把阶段间阻塞关系画出来。
5. 阶段详情：每阶段固定写目标、主要文件、待办、测试验收和阶段验收。
6. 测试用例明细：把关键行为合同拆成可勾选测试项。
7. 并行实施建议：说明哪些阶段适合拆给不同执行者。
8. 最终回归：明确文档、测试、迁移说明和手工链路。

## TODO 写法

- Plan 中的执行项、测试项和验收项统一使用 `- [ ]`，实现完成后再改为 `- [x]`。
- 一个 TODO 尽量表达一个可验证结果，避免把多个无关行为塞进同一项。
- 文件清单可以使用 TODO 样式，表示实现阶段需要检查或修改的起始范围；如果发现同一职责在其它文件中，也要补充到计划或提交说明里。
- 阶段完成前，该阶段的待办、测试验收和阶段验收都应完成。
