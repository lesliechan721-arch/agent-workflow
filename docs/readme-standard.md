# 插件与 Skill README 规范

本规范适用于 `plugins/` 下会进入 production bundle 的 README。README 是插件用户在安装前和安装后都能读取的产品说明，不是 Agent 执行合同、仓库维护手册或评测报告索引。

## 文档职责

| 文件 | 主要读者 | 职责 |
| --- | --- | --- |
| `.agents-plugin/plugin.json` | CLI 与平台 | 名称、版本、平台、配置和能力等机器元数据 |
| 插件 `README.md` | 插件用户 | 安装价值、能力概览、典型使用和用户可观察边界 |
| Skill `README.md` | Skill 用户 | 适用场景、工作方式、结果和限制 |
| `SKILL.md` | Agent | 触发条件、执行流程、不变量和完成条件 |
| `evals/**` | 维护者 | 触发、行为、组合与回归评测 |
| `reports/**` | 维护者与审核者 | 已发布的正式质量证据 |

README 说明用户能获得什么、何时使用以及会产生什么影响。不要复制 `SKILL.md` 的内部算法、完整触发规则或逐步执行合同。

## 通用原则

- 先说明用户问题和产品价值，不以仓库文件结构、manifest 字段或内部组件开头。
- 使用简体中文说明；名称、命令、Skill 标识、配置键和代码保持原始英文。
- 内容应同时适合 Git 仓库浏览和安装后的 runtime 文件树。
- 用户完成安装和使用所需的信息必须直接写在 README 中，不能依赖安装制品中可能不存在的作者材料。
- 可以在末尾链接同一源码目录的 `SKILL.md`、`evals/` 或维护者入口，方便 Git 仓库读者继续查看；这些链接不能替代用户说明。仓库外材料只使用稳定公开链接。
- 不要求所有 README 使用完全相同的标题。按实际能力选择章节，避免为了模板生成空段落。
- 不以“完整合同见 `SKILL.md`”代替用户说明。README 本身必须足以帮助用户决定是否使用。
- 平台、scope、版本和配置 schema 以 manifest 为真值；调用策略以平台原生元数据和 `SKILL.md` frontmatter 为真值。README 只做一致的人读摘要。
- 不写迁移过程、CI 结果、contract test、runner、batch、trace、coverage、被评估 commit 或正式报告摘要。
- 正式报告以 `reports/**/summary.json` 为事实源。`review:publish` 发布报告并封存批次，但不修改 production README。

## 插件 README

插件 README 应帮助用户回答：为什么安装、会得到哪些能力、怎样开始、什么情况下不适合、会产生什么影响。

通常应覆盖：

1. **价值说明**：一两句话说明插件解决什么用户问题。
2. **安装或快速开始**：给出可直接使用的 `aw install` 命令；只支持单平台时使用实际平台。
3. **能力概览**：列出包含的 Skill、Slash Command、配置或其它用户可见能力，并说明各自适用场景。
4. **真实示例**：提供至少一个用户可以直接模仿的请求；多能力插件通常提供两个以上。
5. **选择与边界**：说明相邻能力如何选择、主要不适用场景、写入、Git、网络、子代理、外部命令或其它副作用。
6. **平台与配置**：仅在存在平台差异、scope 差异、配置、人工依赖或安装前提时增加。
7. **维护者入口**：可选。保持简短，只链接源码、测试或维护文档，不在这里登记质量报告。

推荐结构示例，不是固定 heading 合同：

````md
# <显示名称>

<一句话说明安装后的价值。>

## 安装

```bash
aw install <plugin> -p <platform>
```

## 包含的 Skill

| Skill | 什么时候使用 |
| --- | --- |
| `<skill>` | <用户任务> |

## 典型用法

```text
<真实用户请求>
```

## 边界

- <用户可观察副作用>
- <明确不会执行的操作>
````

## Skill README

Skill README 应帮助用户回答：什么时候使用、它会怎样工作、会得到什么结果、有哪些重要限制。

通常应覆盖：

1. 标题和一句话任务说明。
2. 主要适用场景。
3. 高价值的不适用场景，尤其是容易与相邻 Skill 混淆的请求。
4. 用户可观察的工作方式、确认点或最终结果。
5. 写入、Git、网络、子代理、外部命令和授权边界。
6. 调用方式或客户端差异，仅在用户需要知道时说明。
7. 可选的 `SKILL.md`、`evals/` 或维护者入口链接。

简洁 Skill 可以使用“适合使用 / 工作方式 / 不适合使用 / 边界”；显式入口或副作用较大的 Skill 可以增加“怎样调用”和更完整的示例。不要为了统一格式把所有 Skill 扩写成同样长度。

## 内容边界

### README 应保留

- 用户任务和可观察结果。
- 选择哪个 Skill 的高价值判断。
- 必要的安装、调用、配置和权限说明。
- 会改变用户决定的限制与风险。
- 简短、真实、可直接复用的示例。

### README 不应承载

- 完整执行步骤、内部 Gate 和恢复协议。
- 用于 Agent 的长规则或反合理化文本。
- Eval case、grader、runner 和内部测试命令说明。
- `coverage`、weighted score、confidence、source commit 或最近正式报告。
- `reports/**` 的索引或“最近验证”登记区。
- 只对仓库维护者有意义的发布过程。

## 维护规则

- 新增、删除或重命名 Skill 时，同步插件 README。
- 改变平台、scope、调用策略、配置、权限或用户可观察结果时，同步对应 README。
- README 属于 production source。已有插件修改 production README 时，按项目版本规则提高插件稳定版本。
- 脚手架负责生成可用起稿，不以固定 heading 或 prose snapshot 代替人工内容审查。
- 作者验证继续检查 README 存在、非空、链接有效并与 manifest/调用元数据一致。
- 正式报告发布和 README 维护是两条独立流程；任何评审或发布命令都不得自动改写 README。
